# 03 — Panel ↔ Agent protocol and node authentication

> Status: **proposal under review** · Decisions: ADR-0002, ADR-0003.

## Protocol design

### Transport: comparison

| Option | Pros | Cons |
|---|---|---|
| **SignalR (WebSockets) opened by the agent** | Same stack as the browser; automatic reconnect; typed hubs (`Hub<T>`); *client results* (.NET 7+) for acks; the .NET client sends `Authorization` as a header (not in the query string); WebSockets pass through every reverse proxy (IIS/ARR, nginx, Caddy, Cloudflare). | The contract is method names + DTOs (no IDL); versioning needs discipline. |
| gRPC bidirectional streaming | Protobuf IDL, excellent schema evolution. | Needs HTTP/2 end to end: poor support behind IIS/ARR and common Windows proxies; extra protobuf toolchain. |
| Raw WebSocket with custom framing | Full control. | Reimplementing reconnect, multiplexing, keep-alive and acks. More room for bugs. |

**Recommendation: SignalR over WebSockets** (transport pinned to WebSockets, no long-polling fallback). Typing is guaranteed in C# with shared contracts in `Pulsar.Contracts` and — key for security — **commands travel in signed envelopes**, so integrity does not depend on the transport.

Hub protocol: JSON (System.Text.Json with source generators). MessagePack only if console measurements justify it.

### Panel endpoints for agents

| Endpoint | Purpose | Auth |
|---|---|---|
| `GET  /agent/v1/panel-identity` | Panel public key(s) + fingerprint. | Public |
| `POST /agent/v1/enroll` | Enrollment with a single-use token. | Enrollment token |
| `POST /agent/v1/auth/challenge` | Requests a nonce. | None (rate limited) |
| `POST /agent/v1/auth/token` | Returns a session token (opaque, 15 min) after verifying the signature. | Node signature |
| `POST /agent/v1/credentials/rotate` | Node key rotation. | Session token + the current key's signature + proof with the new key |
| `WSS  /agent/v1/hub` | Persistent channel. | Session token |
| `GET/PUT /agent/v1/transfers/{ticket}` | Large transfers (uploads/downloads/backups). | Session token + single-use ticket |

All of these live outside `/api/v1` with a different authentication policy: **a browser credential never works on agent endpoints and vice versa**. A panel with an agents' endpoint (Phase 16) serves them on its port too, with the node key as TLS client certificate ("Client certificates" below). `HttpConnectionDispatcherOptions.CloseOnAuthenticationExpiration = true` on the agent hub forces periodic re-authentication.

### Signed command envelope

The panel holds an ECDSA P-256 signing key (`panel_signing_keys`). Every panel → agent command:

```csharp
// Pulsar.Contracts
public sealed record SignedCommand(
    string KeyId,            // panel key used
    byte[] Payload,          // UTF-8 JSON of CommandEnvelope (exact signed bytes)
    byte[] Signature);       // ECDSA P-256 / SHA-256 over Payload

public sealed record CommandEnvelope(
    int ProtocolVersion,
    Guid CommandId,          // UUIDv7, idempotency
    Guid NodeId,             // recipient: the agent rejects it if it is not itself
    Guid SessionId,          // session issued by /auth/token
    long Sequence,           // monotonic per session (anti-replay)
    DateTime IssuedAtUtc,
    DateTime ExpiresAtUtc,   // secondary defense; tolerates configured clock skew
    Guid? OperationId,
    Guid? ActorUserId,       // for node-side logs/correlation
    AgentCommand Command);

[JsonPolymorphic(TypeDiscriminatorPropertyName = "$type")]
[JsonDerivedType(typeof(StartServerCommand), "server.start")]
[JsonDerivedType(typeof(StopServerCommand), "server.stop")]
// …one stable discriminator per command
public abstract record AgentCommand;
```

Verification in the agent (`CommandDispatcher`), in this order, rejecting on the first failure:

1. `KeyId` is a panel key pinned at enrollment.
2. Valid signature over `Payload` (verified **before** deserializing the command).
3. `NodeId` == self; `SessionId` == current session.
4. `Sequence` not seen and inside the anti-replay window (sliding window of 1024, as in IPsec; tolerates minor reordering without accepting repeats).
5. Not expired (with clock tolerance).
6. Compatible `ProtocolVersion`; known discriminator (otherwise `UnsupportedCommand`).
7. Semantic validation of the command (known IDs, paths, variables against the manifest, sizes).

So even if TLS or a reverse proxy is compromised, **commands cannot be injected or replayed**: injected, because only the panel signs them; replayed, because a command names its session and the agent uses only sessions the panel granted (see "Authentication on every connection"), each with its own sequence window, and judges expiry on the panel's clock as that grant says it. Whatever terminates TLS on the way can answer a sign-in itself, but not with a grant, so it cannot pass off a recorded command's session id or time as the current ones. ECDSA P-256 signing costs microseconds; command volume is low.

Agent → panel events are not signed individually: they travel through a session authenticated by proof of possession of the node key and their impact is informational (state, console, metrics). The panel still checks that every event's `ServerId` belongs to that node.

### Semantics: command → ack → events

- The panel invokes `IAgentClient.ExecuteAsync(SignedCommand)` with *client results* and waits for a `CommandAck` (10 s timeout). The ack only says **accepted/rejected**, not "finished".
- Long work is reported through events carrying an `OperationId`.
- Commands are idempotent by state (e.g. `Start` on a server that is already `Running` → `Accepted` with `AlreadyInState`). The agent does not remember `CommandId`s: a command is never run twice because it is bound to its session, whose sequence window refuses a repeat, and expires a minute after it was issued (verification steps 3–5). The agent judges that on the panel's clock as the grant measured it, with 30 s of tolerance, and the measure may run up to 30 s behind if whatever sits on the way held the token answer that long (a longer one is refused): a command held back on the way can still arrive about two minutes after it was issued, once and in its own session, never as a replay.

```csharp
public sealed record CommandAck(Guid CommandId, AckStatus Status, string? ErrorCode, string? Message);
public enum AckStatus { Accepted, AlreadyInState, Rejected, Busy, UnsupportedCommand, InvalidSignature }
```

`ServerRuntimeSpec` contains the **manifest** (its exact text), variable values (secrets included: the signed envelope travels over TLS and the agent stores records encrypted), port assignments (`name → ip:port`), `ExtraArguments` and the restart policy. The agent **renders** the command line itself from the manifest: the panel **never sends a command line or a free executable path**. The RCON password of `logfile+rcon` games is generated by the agent and never leaves it.

`HelloAccepted` returns the server time (to detect clock skew), the desired state of every server, the console subscriptions browsers are watching (`ConsoleSubscriptions`, with the panel's last sequence of each) and the current panel keys. This drives **reconciliation** after every reconnect or panel restart (see doc 05).

Disk usage is not part of the periodic metrics: walking 60 GB of CS2 every 5 s would be absurd. It is computed on demand and cached (≥ 10 min).

*Query (Phase 11):* a running server whose manifest has a `query` is asked every 10 seconds (every 2 while it starts) by its supervisor, not by the metrics timer, so a game slow to answer never delays the batch; the last answer goes with the server's metrics while it is less than 30 seconds old. Its texts come from the game and from its players: the agent removes control characters, direction overrides and Minecraft colour codes and cuts them to 128 characters and 256 players (`QueryText`), and the panel does the same again before pushing them to browsers, which show them as text.

### Console: flow and volume

- The agent keeps a **ring buffer** per server (e.g. 2 MiB) with a monotonic `Sequence`, and writes a rotated log on disk through a batching writer (channel + periodic flush, never one write per callback).
- Console output is only sent to the panel when at least one browser is watching (`SubscribeConsoleCommand`, reference-counted by the panel). Thirty noisy servers do not saturate the link if nobody watches them.
- The agent coalesces output (≤ 50 ms or 16 KiB per message). If the link backs up, the oldest output is dropped and an `IsGapMarker` is emitted.
- Browser reconnect: it sends its last `Sequence`; the panel asks the agent for the backlog from there. No silent gaps.
- UTF-8 decoding is *stateful* in the agent (chunks can split a multi-byte character); in `pipes` mode the encoding is declared by the manifest.

**Implementation (Phase 5).**

- *Agent buffer* (`ConsoleBuffer`, one per server, across restarts of its game): about one million characters, oldest out first. Small pieces of output join the last entry while it is younger than 50 ms, shorter than 16 KiB and nobody has read it; once read, an entry never changes ("seal on read"), so a sequence always means the same text. Sequences start at the buffer's creation time in microseconds since 1970 (below 2^53, safe in JavaScript): a restarted agent continues above every sequence the previous run used, so the panel and browsers can tell new output from output they have. This relies on the node's clock not going back between two runs.
- *Sources:* pseudo console and pipe output as is (VT sequences included, xterm renders them); for `logfile+rcon` the log file, followed for the whole run with a last read after the exit (what the game writes while quitting is kept). Console input: written to the console (`pty` echoes it; for `pipes` the agent adds `> command`), or sent over an RCON session kept per process. For RCON the agent adds `> command` and the answer, unless the manifest says the game logs commands itself (`rcon.logsCommands`, CS2); such a game logs some answers (`status`) but not others (cvar queries such as `sv_tags`), so the agent shows an answer whose first line does not appear in the log within 2 seconds (Phase 11). A session found closed is replaced once; a late answer is never retried (the game may have run the command). Failures appear in the console as a dimmed `[Pulsar]` note. *Installs and updates (1.0.8):* the console shows them as other panels do. What SteamCMD prints goes there line by line as printed, with the Steam account's password, Steam Guard code, user name and Steam ID and the beta branch's password blanked out (the panel shows the account's name only to those who manage its settings); the agent adds a `[Pulsar]` note when the operation starts and how it ended (done, cancelled, failed with the reason), what each step it runs itself does (Minecraft's download, a file copied), a download's progress every 10 %, an addon installed again after an update, and SteamCMD's retries. A browser that watched the console before the node knew the server (the create dialog opens it at once) was refused then; the panel subscribes it again once the server is provisioned.
- *Relay:* one sender per subscription: up to 64 KiB of entries per message, at most one message per 50 ms, entries kept until sent while the link is down. A subscription that falls behind what the buffer still holds gets a gap entry (`IsGap`, the last missing sequence). Subscriptions end when the connection ends; the panel subscribes again in `HelloAccepted`.
- *History on disk:* `console-logs\{shortId}\console.log`, one line per console line prefixed with its UTC time, escape sequences removed, written in batches (at most once a second) by a background writer that drops output rather than slow the game; rotated at 10 MiB, four older files kept, deleted with the server.
- *Panel copy* (`ConsoleMirrors`): per watched server, the last 256 K characters, deduplicated by sequence. The first browser to watch subscribes the panel; later browsers and reconnects get what the copy holds after their last sequence, then the stream. Nobody watching for 30 s: the agent is unsubscribed; the copy goes after 10 minutes. After an agent reconnect or a panel restart the subscription starts again from the panel's last sequence (or from nothing: the agent then sends its whole buffer and browsers drop what they have), so neither loses output. Output from an agent about a server that is not one of its node's watched servers is dropped.
- *Metrics:* the agent samples each running server's Job every 5 s: CPU time of every process it ever held (as a share of the whole machine since the previous sample, like the node's CPU and Task Manager), working set of the processes alive in it (`conhost.exe` included), process count and uptime. The panel keeps the last sample per server in memory (`LiveMetrics`, older than 15 s counts as none) and pushes it to the pages watching that server.

### Large transfers

The panel cannot connect to the agent (no inbound port), so:

1. Browser → `POST /api/v1/servers/{id}/files/upload` (streaming, authorized).
2. The panel creates a single-use **ticket** (256 random bits, 60 s TTL) and sends `PrepareTransferCommand`.
3. The agent opens `GET /agent/v1/transfers/{ticket}` and the panel **pipes** the browser stream into that response (`System.IO.Pipelines`, with backpressure, never staged on the panel's disk).
4. Downloads (files, backups): symmetric, with a `PUT` from the agent.

Size limits are configurable; the agent writes to a temporary file inside the server directory and renames it when done (atomic).

Each transfer is a connection of the agent to the panel, and a node holds only so many (see *Client certificates*): the panel runs at most 8 transfers of a node at once by default (half of `Agents:MaxConnectionsPerNode`), and answers another one `files.transfers_busy` (409) before the node is told. A user gets 3 of them at most, the second and third only while 2 places stay free for users with none running. A transfer is a request that lasts as long as bytes move (Kestrel's least rate is 240 bytes a second), so it does not outlive what it was allowed by: it is aborted when its user's sessions end (sign-out, disabling, deletion, a new password, two-factor reset or other roles: `BrowserConnections.EndUser`, and any role change: `EndAll`), when the API key it was started with is revoked, and once it has lasted its size at 64 KiB/s, five minutes at least (a download from when the node sends its size). Both of its requests stop: the browser's breaks off, and the node never gets the rest of an upload, so nothing sent after that lands on it.

**Implementation (Phase 6).**

- *What travels where:* listings, new folders, renames and deletions are signed commands that answer in their ack (`CommandAck.Result`, an additive field: `FileListResult`, `FileEntryResult`). File content never goes through the hub: editor reads and saves, uploads and downloads are all transfers. A listing is cut where its message could outgrow the hub's limit (2,000 entries at most, `Truncated`). The agent reads a folder as it goes, holding only the entries it keeps (a folder of millions of files costs no more memory than one of 2,000), and reads at most 1,000,000 of them: a larger folder is listed from the first ones the file system returns, `Truncated` too. Deleting a folder also reads and deletes its entries a batch at a time.
- *Commands:* `server.files_list`, `server.files_create_directory`, `server.files_move` (never replaces, unless SFTP asks: below), `server.files_delete` (a folder with everything in it; links removed, never followed), `server.files_send` (the agent checks it can read the file, answers its size and version, then `PUT`s it) and `server.files_receive` (the agent checks the target and creates the temporary file, acks, `GET`s exactly the announced size and reports with `IAgentHub.TransferCompleted`). Changes are refused with `Busy` while an operation (provision, install, update, delete) runs on the server; reading is not.
- *Tickets* (`TransferTicket`): 256 random bits, at `/agent/v1/transfers/{ticket}` with the agent's session token. A ticket works once and only for the node it was issued to: one presented by another node is burnt; one nobody claims within 60 s expires. The panel's `FileTransfers` holds the browser's request until the agent's request arrives, then copies one into the other as data arrives: nothing is staged on the panel's disk or held in memory (moving an 841 MB map each way, the panel peaked at 235 MB of working set and the agent at 160 MB). A transfer whose other end sends or takes nothing for two minutes is abandoned by the agent, and by the panel too: an upload the agent claimed but stopped reading, or a download it claimed without sending a body within 60 s, fails (`files.transfer_failed`) instead of holding the browser's request. The editor's 1 MiB limit is checked again on the length the agent sends.
- *Writes* go to `.pulsar-upload-<random>.tmp` next to the target, with the space reserved up front (a full disk fails before the transfer), then replace the target in one rename. A short transfer, a target changed meanwhile or any failure removes the temporary file and leaves the target as it was. Versions (`FileVersion`: size and last write time) let the editor save only over what it opened (`files.changed`).

**SFTP additions (Phase 17).** The panel's SFTP server turns each SFTP request into the commands and transfers above, plus what an agent announcing `server.files_sftp` (`AgentCapabilities.SftpFiles`) also understands. Every addition is an optional field whose default is the old behaviour, or a new command; the panel sets none of them for an agent that does not announce the capability, and `ServerFiles`' SFTP methods then answer `files.sftp_unsupported` (409: the node's agent needs an update). The web file manager is unchanged. Paths are checked by the panel and again by the agent, as for every file command, and the agent still acts as the server's account on checked handles.

- *Paged listings:* `server.files_list` with `Paged` and `After` (the previous page's last name). Entries come by name alone, ignoring case and then exactly (`FileNameOrder`), so a page's last name says where the next starts; a page holds up to 2,000 entries (fewer when its message would outgrow the hub's limit), and `FileListResult.Next` names where the next page starts (null on the last). Names no path can address are counted in `Skipped` on the first page, and what SFTP hides (`SftpView`: the server's `.pulsar` folder, also by its short name, and names with format characters such as U+202E, which a client cannot show marked as the web does) is left out before the cap; listing a hidden folder is `files.not_found`. Each page reads the folder once, holding only the entries it keeps, and at most 100,000 of them (`ServerFileRules.MaxPageScan`; `Truncated` then: some entries are in no page): every page reads the folder again, so paging through a huge folder costs the node pages times that, and the panel's SFTP server also stops one listing after 100,000 entries. The panel checks every page again (`ServerFiles.ListPageAsync`): only names after `After` and up to `Next`, each once, nothing hidden; a `Next` that does not move past `After` ends the listing, marked truncated, so an agent cannot make the panel page forever.
- *`server.files_stat`* (`StatFileCommand`): one entry, answered as a `FileEntryResult`; a link is described, never followed, and a hidden path is not found. Allowed while an operation runs.
- *Downloads from an offset:* `server.files_send` with `Offset`. The agent sends the file from there (nothing at or past its end, as a read past the end of a file reads nothing; a negative offset is `files.invalid_offset`), and the ack still describes the whole file. The panel checks the length the agent sends is at most what is left from the offset. Each one is audited as a download, with its offset. A client that seeks back gets a new transfer.
- *Streamed uploads:* `server.files_receive` with `Streamed`. `Size` is then the most that may arrive (the panel's upload limit, `Files:MaxUploadBytes`), and the panel sends the content without a length (chunked) until the SFTP handle closes; the agent writes the temporary file as before, without reserving space, and puts it in place in one rename only when the content ends cleanly. A client that disconnects or content past the limit (`files.too_large`) makes the panel abort the agent's request, so the agent never takes a cut-off stream for a shorter file. On the panel the transfer counts against the node's and the user's transfer limits like any other and lasts at most the limit's size at 64 KiB/s (`FileTransfers.BeginStreamedUpload`), besides the two-minute idle rule.
- *Appends:* `server.files_receive` with `Append` (and `Streamed`), for resumed uploads. The content is added at the end of the file, created when missing, **in place** as it arrives, not through a temporary file: an interrupted append leaves what arrived, which is where the client resumes. `ExpectedVersion`, when given, is what the file must still be; directories and links are refused.
- *Renames that replace:* `server.files_move` with `Replace` (`posix-rename@openssh.com`, WinSCP's `.filepart` uploads). Only a file is replaced, and only by a file, in one step (a POSIX-semantics rename on NTFS); a directory or link at the destination, or a directory or link moved onto a file, is refused as before.
- *`server.files_set_modified`* (`SetFileModifiedCommand`): sets a file's or folder's last write time (clients keep a file's time after an upload); a link is refused, and a time the file system cannot hold is clamped (1601 to 9999). Answered with the entry's new `FileEntryResult`. Not audited: it changes no content, and the upload it follows is.

### Backups (Phase 7)

- *Operations:* `server.backup_create` and `server.backup_restore`. Their progress stages are `scanning`, `archiving` (percent of the bytes to read), `checking` (the SHA-256 pass) and `restoring` (percent of the bytes to write). A successful backup's `OperationCompleted` carries `Result` (additive, a `CommandResult`): `BackupResult(Size, FileCount, SkippedFiles, Sha256)`; the panel completes the backup's row with it.
- *Not exclusive:* while a backup runs the server can start, stop and restart, and its files can be edited (doc 05's matrix); another backup, an install, an update, a restore or a deletion gets `Busy`. A backup can be cancelled like an install (`CancelOperationCommand`): the partial archive is removed. A restore is exclusive, needs the server stopped (`server.running` otherwise) and cannot be cancelled from the panel: half a restore is worse than either side of it.
- *Plain commands:* `server.backup_delete` (`AlreadyInState` when the archive is already gone) and `server.backup_send`, which sends the archive like a file (`SendFileCommand`'s transfer ticket and `PUT`). An archive being read (a download, a restore) cannot be deleted (`backups.in_use`).
- *Storage:* `<backups root>\<shortId>\<backupId>.zip`, by default the agent's `backups` folder (SYSTEM and Administrators only: a game server can neither read nor change its backups), or the folder given at enrollment (`--backups-root`, restricted the same way; it must be empty or already the agent's). Written as `<backupId>.zip.partial` and renamed when complete; an agent that stopped halfway deletes the partial archives when it starts. Deleting a server deletes its backups.
- *Errors:* `backups.not_found` (the archive is not on the node), `backups.corrupt` (its SHA-256 changed, or an entry a restore may not write), `backups.in_use`; reading and writing server files fail with the file manager's codes (`files.*`).
- *Steam accounts (Phase 13):* `InstallServerCommand`, `UpdateServerCommand` and `RemoveAddonCommand` take an optional `Login`, a `SteamLogin(AccountId, UserName, Password, GuardCode?)` (additive; agents announce `steam.login`, and the panel refuses an account to agents that do not, `steam_account.unsupported`). The agent keeps none of it: it signs SteamCMD in with it and keeps only the login SteamCMD cached, per `AccountId` and tied to a hash of the name and password it came with, so a changed one drops it (doc 06). `SteamLogin.ToString` prints the password and the code as `***`. A game that needs an account and gets none fails with `steamcmd.account_required` on the agent too. Deleting an account in the panel makes the nodes forget the login SteamCMD cached for it (with it, the user name alone signs in): connected agents that announce `steam.forget_login` get a `ForgetSteamLoginCommand(AccountId)` right away (`Accepted`, or `AlreadyInState` when they had none), and `AgentHello.CachedSteamLogins` (additive) names the accounts whose logins the agent cached (256 at most), and the panel answers with a signed `ForgetSteamLoginCommand` for each one it no longer has, so an agent that was away drops them at its next `Hello` (every session renewal says `Hello` again). `HelloAccepted` is not signed: its `SteamAccountIds`, which agents used to act on (an empty list from whatever answered on the way would have deleted every cached login), is no longer sent, and agents ignore it.
- *Snapshots, saves and clean restores (Phase 15):* `BackupResult` gains `Capture` (additive; null from older agents): `BackupCapture(Mode, SnapshotError, Save)`, where `Mode` is `stopped` (the game was not running), `snapshot` or `live`, `SnapshotError` is a `snapshot.*` code for a live copy of a running game (`BackupSnapshotErrors`: `disabled`, `not_permitted`, `unsupported`, `unavailable`, `no_space`, `busy`, `failed`, and `game_started` for a stopped server that started while its files were read) and `Save` is `confirmed`, `waited` or `unconfirmed` when the game was asked to save. New progress stages: `saving`, `snapshotting` (backup), `cleaning` (restore). `RestoreBackupCommand` gains `Clean` (additive, default false): agents that honour it announce `backups.clean_restore`, and the panel sends `Clean = true` to no other, since an older agent ignores the property and would keep the files.
- *Remote copies (Phase 10):* the four backup commands take an optional `Remote`, a `RemoteBackupTarget(Endpoint, Region, Bucket, Key, AccessKeyId, SecretAccessKey, PathStyle)` the panel builds from the server's backup storage (additive; agents announce the `backups.remote` capability, and the panel sends none to agents that do not). After the archive is written the agent uploads it (stage `uploading`, multipart, the archive's SHA-256 as `pulsar-sha256` metadata) and reports `BackupResult.RemoteCopied` or `RemoteError`: a failed copy does not fail the backup. A restore of an archive the node no longer has downloads it first (stage `downloading`), checks it against the SHA-256 and keeps it; a download streams it from the storage and, when `RestoreBackupCommand.SizeBytes` (the archive's size, additive: a panel that sends none leaves the download unlimited) is given, stops with `backups.corrupt` as soon as the storage announces or sends more than that; a delete removes the copy too (within 20 s, before the ack). The agent keeps nothing of the target: the secret arrives in each command and is not printed (`RemoteBackupTarget.ToString` leaves it out). Failures are `backups.remote_failed` with what the storage answered.

### Addons (Phase 12)

- *Operations:* `server.addon_install` and `server.addon_remove`, exclusive and only on a stopped, installed server (the panel answers `server.must_be_stopped` otherwise); an install can be cancelled. The key names an addon of the manifest the agent already holds: the panel never sends a URL, a repository or a file list. Progress stages: `preparing` (asking GitHub for the release), `downloading` (percent), `installing` (unpacking).
- *Results:* a successful operation's `OperationCompleted` carries `AddonsResult(Addons)`, a list of `AddonRelease(Key, Release)` (no release: removed); an update that reinstalls `reinstallAfterUpdate` addons reports their releases the same way. The panel keeps them in `server_addons`.
- *Spec:* `ServerRuntimeSpec.Addons` (additive) lists the installed keys; before each start the agent applies their `lineEdits`.
- *Capabilities:* `server.addon_install` and `server.addon_remove`; the panel refuses addons for agents without them (`addon.unsupported`).
- *Errors:* `addon.no_release`, `addon.no_asset` (not exactly one asset matches), `addon.no_checksum` (GitHub publishes no SHA-256), `addon.checksum_mismatch`, `addon.untrusted_host`, `addon.download_failed`, `addon.unsupported_source`, `addon.bad_archive` (an entry outside the target, or more than Pulsar unpacks), `addon.file_missing` (at a start: a file an installed addon edits is missing; a missing anchor is `config.invalid`).

### Ports in use (1.0.7)

- *Command:* `node.ports_in_use` (`ListPortsInUseCommand`, no payload), answered in its ack with `PortsInUseResult(Ports, Truncated)`: each `PortInUse(Address, Port, Protocol)` once, the TCP ports listened on and the UDP ports bound on the agent's machine by any program (.NET's `IPGlobalProperties`), IPv4-mapped addresses as IPv4, the lowest ports first and at most 4096 (`Truncated` past that).
- *Panel:* `GET /api/v1/nodes/{id}/ports-in-use` (`node.view` or `node.manage` on the node: what else runs on the machine says more than its allocations, so `server.create` alone is not enough) asks the agent each time, at most 30 times a minute per node, whoever asks (`429 rate_limit.exceeded` past that); `known: false` when the node is not connected or its agent is older (not announcing the capability), which is not "nothing in use". Of the first 4096 entries, those that are not a port from 1 to 65535, `tcp` or `udp` and an IP address of at most 64 characters are dropped, and each address is written again by the panel (an IPv6 scope removed).
- *Use:* the create dialog and the Network tab, for whoever types port numbers, mark such a number busy (on a protocol the game's port uses, whatever address it is bound to; the server's own allocation excepted) and propose the next free one.

### Protocol versioning

- Major version in the path (`/agent/v1/…`) and in `ProtocolVersion`.
- Within a major version only **additive** changes: new optional fields, new commands announced through `Capabilities`. The panel never sends a command the agent does not announce.
- Panel N supports agents on protocol N and N-1 for at least one minor release, so nodes can be upgraded gradually.
- Incompatibility → the panel rejects the `Hello` with an explicit error ("Agent 1.0 is not compatible with panel 2.0; update the agent"), visible in the node UI.

### Limits and robustness

- Bounded `MaximumReceiveMessageSize` (e.g. 1 MiB) on both hubs.
- The agent reads at most 64 KiB of an answer to its HTTP requests (enrollment, sign-in, rotation; a transfer streams its file and reads its answer within the same 64 KiB), signs only a challenge nonce of 1 to 64 bytes and keeps only a session token of 1 to 1024 characters: anything else is not the panel's answer (see "Fallback": a longer answer fails as a broken connection does, a longer nonce or token counts as no panel answering there).
- What an agent says is bounded where it enters the panel (the hub, the answers to its commands), before browsers, the audit log, the panel's log and notifications see it: an error code must be lowercase letters, digits, dots and underscores, 64 at most, or it becomes `agent.invalid_error_code`; a progress stage is cut to 64 characters, and messages to 1024 (an acknowledgement's, a progress report's, an operation's result, a transfer's result, which becomes the detail of the browser's error, a server state change's detail, which notifications quote, and a backup's remote copy error); an addon's release is cut to 128 characters; a file listing keeps at most 2000 entries, and only those whose name is one segment of a path the panel accepts (`ServerFilePath`, which lets format characters through, so the panel can still open them; an entry with another name, an unknown kind or a negative size is left out and counted in `FileListResult.Skipped`, which the web shows apart from `Truncated`, the 2000-entry cap; the agent already leaves out and counts, before its own cap, the names `ServerFilePath` refuses (a trailing dot, a device name, a lone surrogate that JSON would rewrite as U+FFFD), so they cannot fill the cap, and the panel adds its own count to the agent's, which it clamps to 0 to 1,000,000); a file the agent answers with (an acknowledgement's, a transfer's) must have such a name and a version shaped as the agent makes it (two lowercase hexadecimal numbers joined by a dash, because the panel sends it back as the ETag), otherwise the panel treats the answer as none (a rejected command) or the transfer as failed (`files.failed`); a node's metrics list at most 16 drives with names of 64 characters; what a `Hello` (and an enrollment) says about the machine is cut to its column (host name, Windows description and CPU 255, build 64, servers root 1024, agent version 32); control, format and line-separator characters are removed, reading the text once and stopping when the limit is reached (doc 08, T32).
- Reconnect with exponential backoff + jitter (max 60 s); challenge re-authentication on every reconnect.
- SignalR keep-alive; a node without a connection for > 30 s shows as "disconnected" in the UI.
- If the panel goes down, **game servers keep running**; crash auto-restart and boot auto-start are local to the agent.

## Node registration and authentication

### Identity

- Every node has an **ECDSA P-256 key pair generated on the node itself**. The private key **never leaves the node**: it is created through CNG as a **non-exportable** machine key, using the *Microsoft Platform Crypto Provider* (TPM) when present, or the *Software Key Storage Provider* otherwise. A TPM that says "not now" (device not ready, TPM base services starting or busy) is asked again three times over about 3.5 seconds before the software provider is used, but only when the TPM Base Services (`Tbsi_GetDeviceInfo`) say a TPM may be there: the Platform Crypto Provider also answers "device not ready" where there is none (VMs, CI), and those fall back at once; whatever the reason for the fallback, the agent logs a warning with the error code and message. (Checked with a virtual TPM on Windows Server 2022, rotation included: `scripts/hyperv`.)
- The panel only knows the public key (`node_credentials`). There is no global API key; each node has its own revocable, rotatable credential.
- The panel has its own signing key; the agent **pins** it at enrollment (by fingerprint) and thereby authenticates the panel's answers independently of the TLS certificate (useful with proxies that terminate TLS or self-signed certificates). The enrollment token itself is sent in the request, so whatever terminates the TLS connection on the way can read it: the panel's signed answer names the fingerprint of the key it enrolled, and the agent refuses an answer for another key (a hop that took the token and enrolled its own), saves nothing and says which node to revoke. The node code pins the panel's certificate (when the panel is not behind a proxy or a public certificate), so no hop reads the token in the first place.

Comparison with mTLS:

| | **Application-level proof of possession (recommended)** | mTLS |
|---|---|---|
| Behind a reverse proxy that terminates TLS | Works | Breaks (or requires forwarding the certificate in a header, fragile) |
| Own CA, issuance, CRL | Not needed | Needed |
| Immediate revocation | Yes (database state + abort connection) | Needs CRL/OCSP or custom logic |
| Robustness against TLS MITM | Signed commands + pinned panel key | Strong at the transport level |

**Recommendation:** application-level proof of possession with mandatory TLS. The identity (node key pair) is the same one mTLS would use, so an optional mTLS mode can be added without re-enrolling nodes. *Phase 16 added it, with a certificate each node signs itself on its key (no CA): "Client certificates" below.*

### Node code (Phase 18)

With the token, `POST /api/v1/nodes` and `POST /api/v1/nodes/{id}/enrollment-tokens` return `nodeCode`: what `PulsarAgentSetup.exe` needs, in one string the administrator pastes on the machine with the panel's address (`Pulsar.Contracts.NodeCode`, which the panel writes and the agent's setup reads):

```
pulsar-node-1.<base64url, no padding, of UTF-8 JSON>
{"url":"https://panel.example.com:8443","token":"<enrollment token>","key":"sha256:<panel key fingerprint>","cert":"<64 lowercase hex digits>"}
```

- `url`: the origin the administrator's request reached the panel by, exactly as agents compare it (`scheme://host[:port]` in lower case, no trailing slash, no default port; the PowerShell command uses the same, from the browser). An origin agents could not use gives no code (`nodeCode: null`): plain HTTP other than `localhost` or a loopback address, or one not written as an agent writes it.
- `token`: the single-use token above (a reusable one, `pulsar_enroll_…`, also fits the format). `key`: the panel key the agent pins, as `--panel-key` takes it.
- `cert`: the lowercase hex SHA-256 of the DER of the TLS certificate Kestrel presented in that request's handshake (`SslStream.LocalCertificate`, for the host the browser asked for), so the node's agent can pin that certificate without copying `panel.cer` (see "Transport": nothing is added to the node's certificate stores). `null` when the panel cannot tell what certificate its clients see: plain HTTP, HTTP/3 (Kestrel does not expose QUIC's), or a request that came through a proxy (any `X-Forwarded-*`, `X-Original-*`, `Forwarded` or `Via` header), which may serve a certificate of its own. The setup then needs a certificate the machine already trusts. A proxy that re-encrypts to Kestrel without saying so gives Kestrel's hash, which does not match what the node is served: the setup refuses.
- `cert` is `null` too when that handshake served the public IP certificate (Let's Encrypt, doc 08, T40): publicly trusted and replaced every few days, it is checked as any site's is, never pinned.
- Reading it is strict (`NodeCode.TryParse`): at most 2048 characters, exactly the prefix, base64url without padding or whitespace in its one canonical spelling, a JSON object (no BOM, comments or trailing commas, nothing nested) with exactly these four members once each (`cert` may be null), each well formed: `url` in printable ASCII and at most 512 characters, the token 32 random bytes in base64url (with or without `pulsar_enroll_`), the key `sha256:` and 32 bytes in base64url, `cert` 64 lowercase hex digits. Anything else is not a code; callers trim what a person pasted. A later format takes another prefix.
- The code carries the token: it is a secret for as long as the token works. Like the token it is shown once, never stored (the panel keeps the token's hash only) and never audited or logged (`EnrollmentInstructions` and `NodeCode` print `***` in its place).
- `agentSetupSha256` is the lowercase hex SHA-256 of the `PulsarAgentSetup.exe` the panel serves at `GET /downloads/PulsarAgentSetup.exe` (`Downloads:Path`, by default the `downloads` folder next to the panel's executable; doc 08, T37), or `null` when it serves none; `agentSetupAvailable` says whether it serves one. **Add node** then links to it and shows the hash, for whoever downloads it to compare. The download is limited per client address (`Downloads:ConcurrentPerAddress`, 4 at once; `Downloads:PerAddressPerHour`, 60).

### Bulk enrollment (Phase 14)

To enroll many machines with one command (the agent MSI deployed through Intune or a group policy, or a script), an administrator with `node.credentials.manage` held globally creates a **reusable enrollment token** (`/api/v1/enrollment-tokens`): a name, a number of uses (1 to 1000), an expiry (1 hour to 90 days) and whether the nodes it creates wait for approval (on by default: `requireApproval` left out of the request is `true`). The value (`pulsar_enroll_` and 32 random bytes) is shown once; only its SHA-256 is stored, with its first characters to recognize it. At most 50 usable tokens exist at a time, and a token can be revoked whenever. Tokens are never deleted (the nodes they created name them); the list shows every usable one and the 20 newest of the others (revoked, expired or used up).

The agent enrolls with it exactly as with a single-use token (the same endpoint, proof and signed answer). The panel looks the hash up among single-use tokens first, then among reusable ones, and then:

- counts the use atomically (`UPDATE … SET uses = uses + 1 WHERE uses < max_uses AND revoked_at IS NULL AND expires_at > now`), so machines racing for the last use cannot all enroll;
- creates a **new node** named after the machine (with `-2`, `-3`… when the name is taken; a save that loses a race to the same name, a unique violation of the node's name, retries with a suffix). A use never re-enrolls an existing node: a leaked token cannot take one over. The host name the agent reports (here and at every `Hello`) loses control and format characters (zero-width spaces, direction overrides) and line and paragraph separators, so a node cannot pass for another, and is cut without splitting a character. A request whose key is registered already (a replayed one) is refused without using the token;
- audits `node.created` and `node.enrolled` with the token's name, and answers with `awaitingApproval` when the token requires approval, which `PulsarAgent enroll` reports. A refused use (expired, revoked or used-up token, a replayed key) is audited `node.enrollment_failed` with the token's name and id.

Enrollments are limited per client address (`RateLimiting:Auth:EnrollPermitLimit`, 10 a minute by default); the panel's 429 says when to come back (`Retry-After`). Machines enrolling together behind one NAT address share that limit, so `PulsarAgent enroll` waits as told, plus a random share of up to 10 s, and tries again for up to 10 minutes; it never retries a refused token. A larger rollout from one site raises the limit for its duration (docs/guides/install.md).

A node waiting for approval (`pending_approval`) is enrolled but may not authenticate: its agent retries with its usual backoff and connects within a minute of the approval. Disabling and enabling such a node does not skip the approval. Approving takes `node.manage` (`POST /nodes/{id}/approve`, or `POST /nodes/approve` with up to 200 nodes, held globally), audited `node.approved`; deleting the node turns the machine away. The node list shows, for each node, the reusable token that created it and its active key's fingerprint, so a machine can be checked before it is approved. Approving (or enabling) a node starts the "node offline" notification's grace period again: its agent was turned away until then.

### Authentication on every connection

```
Agent                                         Panel
  │── POST /auth/challenge {nodeId, credentialId[, nonce][, pinnedPanelKeys]} ─►│ 32-byte nonce, 60 s TTL, single use (in memory)
  │◄─ {challengeId, nonce, panelOrigin} ────────────│
  │── POST /auth/token {challengeId,                │
  │     signature = Sign("pulsar-agent-auth-v1" ‖ nodeId ‖ credentialId ‖ nonce ‖ panelOrigin ‖ pinnedPanelKeys)} ─►│
  │                                                 │ verifies signature with the registered key,
  │                                                 │ credential active, node not revoked/disabled,
  │                                                 │ consumes the nonce; updates last_used_at
  │◄─ {accessToken (opaque), sessionId, expiresAt=+15 min, grant} ─│ the session (node, credential) stays in the panel
  │── WSS /agent/v1/hub  (Authorization: Bearer …) ─►│ OnConnected: re-checks credential/node in the database;
  │                                                 │ registers the connection (closes a previous one for the same node)
  │── Hello(AgentHello) ───────────────────────────►│ reconciliation
  │◄─ HelloAccepted ────────────────────────────────│
```

- Including `panelOrigin` in the signed data prevents replaying a response against another panel.
- The answer carries the session as a `grant`: `SessionGrant(nodeId, credentialId, sessionId, expiresAt, nonce, issuedAt)` signed with a panel key the node pins (`pulsar-session-grant-v1`: the first of the panel's keys, active first, among the ids the challenge request names in `pinnedPanelKeys`, at most 8 fingerprints, or the active key when it names none; never the pins a `Hello` reported, which whoever holds a session token can write), where `nonce` is the one the agent sent with its challenge request, kept with the challenge until the token request. The panel's challenge nonce would not do: a proxy could forge a challenge carrying an old one and play back the grant it got then, but it cannot make the agent send an old nonce of its own (32 random bytes per sign-in). The panel signs it only once it recorded the sign-in (`last_used_at`, committed) and created the session, so a grant that verifies, for this node, key, session and nonce, proves the panel itself saw this sign-in: whatever sits between them (a TLS-terminating proxy) can answer a sign-in itself, but cannot make such a grant. **Agents require it:** a sign-in whose answer has no grant that verifies (missing, signed by a key the agent does not pin, for another node, credential, session or nonce, or without `issuedAt`) is no sign-in at all; the agent uses no such session, and treats the answer as one where no panel answers (the next attempt, the fallback address). Otherwise whatever answers in the panel's place could hand the agent a session id and a time of its choosing (Hello's answer is not signed either) and play back a command recorded in an earlier session, which would pass every check. The session id the agent's command verification expects is the grant's, and the panel's clock offset comes from `issuedAt` (the panel's time when it signed), against the agent's clock when the answer arrived: off by at most the token request's time, since the grant answers this sign-in's fresh nonce, and the agent refuses an answer that took longer than the commands' clock tolerance (30 s). Panels and agents of this release always ship together, so the panel always sends it; it leaves it out only for a request without a nonce (an older agent) or a node that pins none of its keys (one that missed a whole panel key rotation, which cannot connect any more and must be enrolled again). The signature covers the challenge request's `pinnedPanelKeys` too, as sent (`ProtocolCrypto.KeyIds`: each id's UTF-8 with its 4-byte length, in order; no list is no bytes): the panel records the keys a node pins at enrollment (what it answered) and then only from a sign-in, with the node's row locked, from the list its node key signed (audited `node.panel_keys_pinned` when it changes); never from a `Hello` or an answer to `UpdatePanelKeysCommand`, which whoever holds a session token can send. A sign-in whose signature does not cover the list it named is refused (`invalid_signature`). The panel and the agents of this release ship together (agents already require the grant), so the signed data changed without a compatibility path: an agent of an earlier build cannot sign in until it is updated. `grant` is a field added within v1 (see "Protocol versioning"), a few hundred bytes within the agent's 64 KiB answer limit.
- **Implementation note (Phase 2):** the session is an opaque random token (stored as SHA-256, in memory) rather than a JWT. The panel is a single instance in v1 and keeps per-session state anyway (command sequence, immediate revocation), so a JWT would add signing-key management without removing that state. A panel restart ends every session; agents re-authenticate on reconnect.
- The session token only works for the agent hub and transfers, lasts 15 minutes, and the connection closes when it expires (the agent re-authenticates transparently).
- One active connection per node.
- Once the session exists the panel reads the credential and the node once more: a disable, deletion or revocation that committed while the sign-in ran (and so ended the node's sessions before this one existed) ends it, and the sign-in is refused.
- A sign-in records the key's use and the node's last contact with the node's row locked first, as a revocation, a rotation and a re-enrollment lock it before they write the node's keys: every writer takes the node's row before a key's, so none of them deadlocks with another.
- The hub hears a connection only after its `Hello` and while its session lasts: a connection whose session ended (a revocation, a rotation) is ignored until it closes.
- Every refused sign-in, and a rotation asked without an active session, key and node, gives the agent the same answer (`agent.authentication_rejected`); the panel log has the detail, and the audit log an entry `node.authentication_failed` with a reason (`credential_or_node_inactive`, `inactive_after_challenge`, `inactive_while_signing_in`, `invalid_signature`, `client_certificate_mismatch`, `challenge_origin_mismatch`, `challenge_nonce_too_long`, `challenge_pinned_keys_invalid`, `pending_credential_expired`, `current_credential_signed_in_after_challenge`, `rotation_without_active_session`, and `session_certificate_mismatch` for a session token presented without the client certificate it was issued with) when the request names an existing node. A rotation whose new key is refused answers `agent.rotation_rejected` and is audited as `node.credential_rotation_started` with outcome failure (`invalid_current_key_proof`: the current key did not sign the new one for this session; `invalid_proof`: malformed or the new key's proof does not verify; `key_already_registered`). An agent turned away keeps trying, so a node gets one entry per reason and client address every 15 minutes, the next one saying how many were left out (`notRecordedBefore`): another address gets its own entry (a copied token or key tried from elsewhere is not hidden behind the node's own agent being refused), up to 8 addresses per node and reason, past which the others share one entry. Requests that name no existing node are only logged, and each address is held to the rate limit of these endpoints. Refused enrollments that name no node (`unknown_token`, a malformed request) are audited up to 20 a minute for the whole panel, the next entry saying how many were left out; those of a real token always are. Being sent to the agents' address (`agent.certificate_required`) is not a failure and is not audited.

### Client certificates (Phase 16)

An optional check at the TLS level, on the same node key, with no CA and no new enrollment. The session token is a bearer token: whoever copies it (from a proxy that decrypts the traffic, a memory dump, a log) can use it until it expires. On the agents' endpoint a session is bound to the key of the TLS connection that opened it instead.

- *Agents' endpoint:* the Kestrel endpoint `Agents` (`Kestrel:Endpoints:Agents`, the installer's `-AgentsPort`), HTTPS only, on a fixed port. It asks every client for a certificate in the TLS handshake (a client that presents none is refused before any HTTP) and serves only `/agent/v1/*` (everything else is 404 there), so browsers, which use the main endpoint, never see a certificate request. Agents put the endpoint's port on the host they reach the panel by, unless the operator set another address (`Agents:PublicUrl`: a port forwarded under another number, another name). The panel never builds the address from a request's `Host` header: a proxy in front of the panel could set it, and the panel would sign a host of the proxy's choosing. Agents must reach the endpoint directly: a reverse proxy that terminates TLS in front of it cannot pass the client certificate on (a TCP pass-through can, but unless it keeps the client's address every agent then comes from the proxy's and shares its connection budgets, below).
- *Certificate:* the agent makes a self-signed certificate on its node key (`CN=Pulsar node`, client authentication, valid from a day back to ten years ahead) and presents it on every request and on the hub's WebSocket. The key stays where it is (CNG, in the TPM or the software provider): the certificate names its container, and SChannel signs the handshake with it. The panel takes any certificate in the handshake and checks its key, not a chain: through the agents' endpoint a challenge or a token needs a certificate on the credential's key, and an enrollment one on the key being enrolled (both keys re-encoded before they are compared); otherwise `agent.authentication_rejected` (`agent.enrollment_rejected`). Nothing else decides anything: dates, names, issuer and extensions are not checked. The TLS layer still builds the certificate's chain before Kestrel accepts it, and the endpoint makes it build one from what the handshake carried and the machine's stores only (`X509ChainPolicy`: certificate downloads disabled, which on Windows also turns off the automatic root update, and no revocation check; Kestrel's own revocation check off): the addresses a certificate names (its issuer's certificate, OCSP, revocation lists), chosen by whoever connects, are never fetched (doc 08, T31). The result of that chain is ignored. (The machine's trust costs nothing more there; a custom root trust with no roots, used before, built a chain engine for every handshake: about 5 ms of CPU against 0.2 ms.) The endpoint holds at most `Agents:MaxConnections` connections at once (1000 by default, about four per node: each agent keeps one for its hub and opens one or two more for a while to sign in or move a file). A connection is *not signed in* until a request on it presents a valid agent session with the key of the connection's certificate (the hub's WebSocket request, a transfer, a rotation: the agent authentication handler marks the connection, a connection feature its requests see); a challenge, a token or an enrollment does not sign a connection in, since anyone can send one. Connections not signed in have budgets of their own within that cap: `Agents:MaxPendingConnections` (a quarter of `MaxConnections` by default), of which addresses no agent signed in from within a day take half at most (the addresses agents signed in from are kept in memory for a day: each node's latest four, and past max(4096, `MaxConnections`) of them the node holding the most loses its oldest, so one node key can neither open the reserved half to many addresses nor push the others' out); `Agents:MaxPendingConnectionsPerAddress` (20 by default) from one address, counted by IPv4 address (mapped into IPv6 or not), by IPv6 /64, and all of the loopback (127.0.0.0/8, ::1) as one; `Agents:MaxPendingConnectionsPerNetwork` (three times that by default) from one IPv4 /24 or IPv6 /48, for addresses no agent signed in from only (an agent's neighbours never take its address's places). One connection more than a budget allows is closed on arrival, before its TLS handshake. The endpoint never serves HTTP/3, whatever its configuration says (QUIC would not pass its connection middleware): an HTTP/3 setting is dropped and the rest of the operator's protocols kept, HTTP/1.1 and HTTP/2 when nothing is left. A handshake has 5 seconds (Kestrel's default is 10). A connection not signed in 30 seconds after it arrived is asked to close as Kestrel closes an idle keep-alive connection (after the request in progress), and aborted 5 seconds later if it is still open and still not signed in. A signed-in connection belongs to one node (a session of another node on it is refused) and lasts as long as the latest session it presented: when that ends it is asked to close in the same way, and aborted 5 seconds later unless a request of a session is still in progress (a transfer is never cut); requests without a session do not keep it. A node holds at most `Agents:MaxConnectionsPerNode` signed-in connections (16 by default; a request with its session on another connection is refused with 401, and the once-a-minute warning names the node), of which connections signed in by a transfer (a request routed to a transfer endpoint, whatever the case of its path) take all but min(4, half): the rest stays for its hub, the hub it replaces and its rotation. Its other requests are not limited further: a holder of the node's key can take all of the node's connections with any authenticated request. The panel starts at most half of a node's connections' worth of transfers on it at once (8 by default; `FileTransferLimits`), three of them for one user on that node, the second and third only while two places stay free for users with none running, and refuses others before the node is told (`files.transfers_busy`, 409), so that one user's slow uploads cannot shut the other users' transfers, or the agent's hub, out. When a node's sessions are cut off (revocation, disabling, deletion, re-enrollment) its connections whose session ended are closed at once, and so are a superseded key's. The panel refuses to start with a budget below 1 or out of order (per address ≤ per network ≤ pending ≤ `MaxConnections`; 2 ≤ per node ≤ `MaxConnections`, the hub and a transfer). The agent signs in on a connection it closes once it has its token, a second or two, and its hub and transfers present the session in their first request, so a node needs a place for moments only; nodes behind one NAT address sign in about ten at a time and retry within seconds. Refusals and timeouts are logged at most once a minute, with how many there were of each. Kestrel's own `MaxConcurrentConnections` would count the browsers' endpoint too. The rate limits of the sign-in, enrollment and login endpoints count clients the same way (IPv6 by /64, the loopback as one). What a flood can still do: many networks together can fill the strangers' half of the budget and refuse sign-ins from addresses no agent signed in from within a day for as long as they keep it up; connected agents keep their hub until their session ends (15 minutes at most) and then sign in like the others, at the main endpoint while certificates are not required (see *Fallback*), where the session is not bound to the key. Whatever shares an agent's address (a game server on its node, a neighbour behind its NAT, every agent behind a TCP pass-through proxy or hairpin NAT) shares its budgets and can starve it; docs/guides/install.md has the mitigations (a firewall rule for the game servers' accounts, budgets for a proxy).
- *Binding:* a token issued through the agents' endpoint records the fingerprint of that key, and every request of the session (the hub, transfers, a rotation) must come through the agents' endpoint with the same key: the token alone is worth nothing. A request that presents it without that key (or a session of the main endpoint on the agents' endpoint, or one without a certificate once they are required) is refused, logged as a warning and audited (`node.authentication_failed`, `session_certificate_mismatch`). A session signed in on the main endpoint carries no key and is refused on the agents' endpoint. Revocation stays immediate, as before. A rotation works the same way: the session of the old key registers the new one, and the new key signs in with a certificate of its own.
- *Moving agents:* agents that have a certificate (one whose key store cannot make one does not) announce `node.use_agents_address`. When one connects without a certificate and the panel has an agents' endpoint, the panel sends it `UseAgentsAddressCommand(Port, Url)` after `Hello` (a signed command, not awaited): the port, and the operator's address only when one is configured. The agent puts the port on the host of the address its session uses, signs in there first (7 s at most) and only then saves it as its address, the address it used until then as its fallback (`fallbackPanel`), and opens its next session there. An address it cannot sign in at is refused with `agent.address_unreachable` and changes nothing; the panel tells it again at its next session (every 15 minutes). A port out of range, or an address that is not an https origin, is `command.invalid_agents_address`.
- *Fallback:* the agent signs in at its address and goes to its fallback when no panel answers there: connection or TLS refused, no answer in time, a 404 or 5xx from whatever listens there, a redirect (the agent follows none: it would carry the request's body elsewhere), a 401 or 403 without the protocol's `AgentError` body, a success whose body is not the protocol's (a page of another service the port was given to), or a hub whose WebSocket does not open after the sign-in. A refusal from the panel (a revoked key, certificates required) is no reason to try the fallback: the panel's 401 answers carry an `AgentError` (`agent.authentication_rejected`, its generic message) so the agent tells them apart; agents that do not read it still take any 401 as a refusal. A closed agents' port therefore never cuts a node off: it keeps connecting to the main endpoint (and is told the agents' address at each session) until the port answers again.
- *Requiring certificates:* a switch on the Nodes page (`settings.manage`; `GET/PUT /api/v1/agent-transport`, audited `agent_transport.changed`), off by default and in effect only while the panel has an agents' endpoint (without one it cannot be turned on: `agent_transport.no_agents_endpoint`). Turning it on ends every session signed in without a certificate and closes its connection. From then on a challenge on the main endpoint is refused with 403 `agent.certificate_required` and an `AgentsAddress(NodeId, Port, Url, Nonce)` signed with a panel key (`pulsar-agents-address-v1`): for that node, and with the random `Nonce` (up to 64 bytes) the agent sent in its challenge request, so a refusal recorded once cannot be played back to it later. An agent with a certificate checks the signature against its pinned keys, the node id and its nonce, signs in at the port on the host it was refused at (or the operator's address), and only then keeps that address, the old one as fallback. A token asked for with a challenge answered just before the switch is refused the same way, without an address (the next challenge carries it). Agents too old to move cannot connect until they are updated; before the switch is turned on, the page lists the nodes that still connect without a certificate and whether their agent can move (from each node's last `Hello`: `connectedWithCertificate`, `agentCanUseCertificate`). Enrolling stays possible on both endpoints: an agent enrolled on the main one moves at its first sign-in.
- *Panel side:* the panel sets the endpoint up through Kestrel's configuration loader (`Endpoint("Agents", …)`: `RequireCertificate`, any certificate accepted in the handshake) and a connection middleware marks its connections. Whether certificates are required is kept in memory (one panel instance) and read from the database before the first sign-in needs it. A change whose outcome is unknown (its save failed, and so did reading the switch again) counts as on until the next sign-in reads it: the sessions without a certificate end, as they do when it is turned on.

### Rotation

**Node key** — automatically once the key is 90 days old (checked at every connection), or when an administrator asks from the node page (`RotateCredentialCommand`, permission `node.credentials.manage`):

1. The agent creates a new key in the same scope and provider preference (TPM first) and calls `POST /agent/v1/credentials/rotate` within its current session, with `proof = Sign_new("pulsar-rotate-credential-v1" ‖ nodeId ‖ currentCredentialId ‖ sessionId ‖ newPublicKey)` and `currentKeyProof = Sign_current("pulsar-authorize-rotation-v1" ‖ nodeId ‖ currentCredentialId ‖ sessionId ‖ newPublicKey)`. The session token is a bearer token: whoever copies it (with the ids a proxy that decrypts the traffic sees) could otherwise register a key of their own, sign in with it and supersede the node's key for good. The current key's signature says this new key, for this node and session; it cannot be played back for another key or session, and a key once registered is never registered again (`key_already_registered`). The panel checks it against the current credential's public key, then the new key's proof. *A protocol change before the first release:* agents older than it send no `currentKeyProof` and cannot rotate (`agent.rotation_rejected`, `invalid_current_key_proof`); they keep their key.
2. The panel registers a `pending` credential (an earlier pending one is superseded), with the node's row locked as a revocation locks it, so a revocation of the current key and the registration take turns; it answers with `CredentialRotation(nodeId, credentialId, keyFingerprint)` signed by a pinned panel key (`pulsar-rotation-result-v1`). The agent verifies the signature, the node and that the fingerprint is the new key's (so a signed answer to another rotation, replayed or mixed up, is refused), then saves the new key as `pendingRotation` in its configuration before using it. `keyFingerprint` is an optional field added within v1 (see "Protocol versioning"): an answer from an older panel has none and is still accepted, signed for this node; a credential registered for another key would then fail at its first sign-in, and the agent keeps its current key. The key of an earlier rotation that never completed is deleted only now, once this signed answer says the panel registered the new one (which superseded the earlier pending credential); a rotation that fails keeps it as `pendingRotation`.
3. The agent authenticates with the pending credential (challenge and token accept `pending` credentials registered within the last 24 hours; an older one is refused, `pending_credential_expired`, and superseded). That first authentication makes the panel activate it and supersede the previous one in one transaction (with the node's row locked, and refused if the pending credential was revoked meanwhile, or if the current credential signed in after the challenge this sign-in answers was issued: `current_credential_signed_in_after_challenge`, see below), end the sessions of the old key and close the connections they opened, the hub's and those on the agents' endpoint (whoever else holds the old key keeps none of the node's share of it), while the new key's stay; the agent then connects with the new key. The agent then switches its configuration to the new key and deletes the old one: the sign-in came with the panel's `grant` for the pending credential, as every sign-in the agent uses does, so the panel activated it. An answer without the grant (whatever sits between them answered the sign-in itself, so the panel may never have activated the pending credential, which would then expire after its day and leave the node without a key the panel accepts) is not a sign-in: nothing changes, and the agent signs in with its current key for that attempt, as when nothing answers (below).

At any interruption one of the two keys works: before step 3 the current credential is still active; after it, `pendingRotation` is still in the configuration, so the next start authenticates with it first. If the panel refuses a pending key, or the key fails to sign (a TPM busy for a moment), the agent signs in with the current key, and deletes the pending one only when that works, which means with the panel's `grant` for that sign-in: a current key the panel itself still accepts, at a sign-in it recorded, proves it did not activate the pending one (a later rotation superseded it, it was revoked or expired). An answer to the current key without a grant that verifies (a TLS-terminating proxy that answers it itself, so that the panel never records it, or plays back an earlier answer) is no sign-in either: the attempt fails, both keys stay, and the agent tries again after its backoff, the pending key first. The refusal may come after the panel activated it (a proxy that passes the sign-in on and forges the refusal, a node disabled right after, an answer lost before a later attempt): then the current key is refused too, and the agent keeps both and tries again after its backoff, the pending key first. An answer that is not the panel's (a bare 401 without the protocol's error, or a success without the panel's grant) signs in with the current key for that attempt, and the pending key is deleted after three such answers in a row while the current key signs in. The panel holds the other end: a sign-in with a pending key whose challenge was issued before the current key's last sign-in is refused (`current_credential_signed_in_after_challenge`, decided with the node's row locked, where the current key's sign-in records its time). The agent signs in with its current key only once the pending one was refused or not answered, and deletes the pending key once that sign-in works (with the panel's grant, as every one); so a proxy that held the pending key's request, forged the refusal and passes the request on later (within the challenge's minute) would otherwise activate a key the agent no longer has, and lock the node out for good. Either the current key's sign-in commits first and the late request is refused, or the late request activates the pending key first and the current key's sign-in is then refused, so the agent keeps the pending key and signs in with it next. A proxy that also answers the current key's sign-in itself (a forged success, which the panel never records, so the late request is not refused) gets no grant from the panel for it: the agent uses no session and keeps both keys, and the pending key signs in once the proxy passes the requests on. A failed rotation, an abandoned pending key included, is retried after an hour, when the key is due by age or the panel asked for it. A rotation the panel asked for (`RotateCredentialCommand`) stays asked for until one completes: one that fails to register is tried again an hour later in the same session, and one whose pending key is given up starts again after that hour (the pending rotation remembers it was asked for, `pendingRotation.requested`, also across a restart); asking again meanwhile answers `AlreadyInState` (a request that has not registered yet lives in the agent's memory: a restart drops it, and the key's age still triggers one at 90 days).

The panel's own side of the fence does not depend on the agent: the time a sign-in records for its key is never earlier than its own challenge nor than the key's previous use, and challenges are issued in strictly increasing time (a microsecond apart at least, even when the panel's clock steps back), so a pending key's challenge issued before the current key's sign-in is refused afterwards. That holds within one panel process, which is all there is (a single instance, R6 in doc 08): challenges live in its memory, so a restart drops every held challenge, and a request held across it is refused as an unknown challenge.

**Panel key** — from the Nodes page (permission `settings.manage`): rotating creates a new active key and turns the previous one into `retiring`; the panel accepts both and signs with the active key.

- Every `Hello` carries `pinnedPanelKeys`. The panel signs that connection's commands with the active key if the agent pins it, otherwise with the newest retiring key it pins; it does not record them (a difference from the node's record is logged): the node's record comes from its sign-ins (see "Authentication on every connection").
- When the pins differ from the panel's keys, the panel sends `UpdatePanelKeysCommand` (to connected agents right after the rotation, to the others when they connect), signed with a key the agent already trusts. The agent requires every key id to be its fingerprint and the list to include the key that signed it, so an update can never lock it out. Its answer changes the keys the panel signs that connection's commands with, not the node's record, which follows at the agent's next sign-in (a session lasts 15 minutes, so within about a quarter of an hour of connecting).
- Retiring the old key (only one key can be retiring at a time) sends the shortened list to connected agents. A node that never connected during the rotation pins only a retired key: the panel can no longer sign anything it accepts, the UI flags it as "old panel key", and it has to be enrolled again. The Nodes page shows how many nodes trust each key before retiring and names the enrolled, not disabled, nodes whose recorded keys include no other key of the panel's (or are unknown): while there is one, retiring is refused (409 `panel_key.nodes_outdated`) unless forced (`POST /api/v1/panel-keys/{keyId}/retire?force=true`, which the page sends only after a confirmation naming them; audited with the names).

### Revocation and expiry

- Revoke (UI, permission `node.credentials.manage`): credential → `revoked`, the node's active connection is aborted immediately, any later challenge fails. Audited. Revoking the active credential also revokes a `pending` one: a rotation registered it from a session of the revoked key, so whoever stole that key may have (the audit entry lists it, `pendingRevoked`).
- Disabling a node: same effect without deleting the credential. A disable or a deletion is applied again when the agent wrote the node's row meanwhile (`Hello`, last seen), so it is never lost.
- Enrollment tokens expire (30 min by default). Session tokens: 15 min. Node credentials: automatic rotation every 90 days; an active credential does not expire. A pending one (a rotation's new key) expires 24 hours after it was registered unless the agent signed in with it: it is refused and superseded at its next sign-in.
- Re-enrolling a node (e.g. Windows reinstall) = a new enrollment token for the same `Node`; the previous credential is revoked, and so is a pending one from an unfinished rotation. The node's row is locked meanwhile, as a rotation locks it: a key the old one registers at the same moment is either revoked with them or refused.

## Agent implementation (Phase 2)

How `Pulsar.Agent.Core` (portable protocol logic), `Pulsar.Agent.Windows` (CNG, inventory, ACLs, service control) and the `PulsarAgent` executable put the design above into practice.

### Command line

```
PulsarAgent enroll --panel <url> --token <token> --panel-key <fingerprint> [--servers-root <dir>] [--no-service] [--dev] [--data-dir <dir>] [--log-file <file>]
PulsarAgent status [--check] [--data-dir <dir>]
PulsarAgent run [--data-dir <dir>]
PulsarAgent service install|uninstall|start|stop [--stop-servers] [--data-dir <dir>]
PulsarAgent unenroll [--data-dir <dir>] [--log-file <file>]
PulsarAgent host --server <id> --pipe <name> [--data-dir <dir>]   (started by the agent, not listed by help)
```

- The service runs the executable it was installed from as SYSTEM, so `enroll` and `service install` refuse when anyone other than SYSTEM, Administrators or TrustedInstaller could modify it or its folder, or rename a folder above it (a download folder, or a folder created directly under `C:\`, fails; `C:\Program Files\Pulsar\Agent` passes). The check runs before enrolling, so a refusal does not consume the token. `service start` checks again, and so does the agent itself when it runs as the service (started by the service control manager, or as SYSTEM): it logs the reason and exits.
- `enroll` must run elevated. It pins the panel key, creates the node key, enrolls, writes `config\agent.json`, and installs and starts the `PulsarAgent` service (LocalSystem, automatic start; the service control manager restarts it after 5 s, 15 s, then every 60 s, also when it stops itself with an error). Re-running it on an enrolled node stops the service first (one still stopping after 30 s stops the command: nothing is enrolled, and it says to run it again or start the service) and deletes the old key, and the pending one of an unfinished rotation, once the new enrollment is saved (a key that cannot be deleted is reported, to delete by hand, and the enrollment stands); if anything fails after the service was stopped, it is started again before the command ends. A previous configuration that cannot be read (corrupt JSON) is replaced with a warning, as `unenroll` does: the key it names stays in the key store.
- `--data-dir` is taken as a full path without a trailing separator (a quote at its end, which a quoted folder ending in a backslash leaves, is dropped), and the service's command line quotes it so the service reads back the same folder `status` and `unenroll` look at.
- `status` shows the enrollment and the node key fingerprint (the one the panel shows for the credential); `--check` also authenticates against the panel.
- `--dev` is for development only: the key goes to the current user's store, the state directory also grants the current user, and no service is installed. The service runs as SYSTEM and could not open such a key. A development enrollment never runs as the service either: `service install` and `service start` refuse it, and the agent refuses to run it as the service, where its servers (started as the current user) would run as SYSTEM. Nor does it replace a production enrollment: `enroll --dev` without `--data-dir` targets the default state directory, and it is refused, before anything is written or sent, when that directory holds a production configuration (or one the current user cannot read).
- `unenroll` removes the service, the node key (and the pending one of an unfinished rotation; a key that cannot be deleted is reported and fails the command with exit code 1, keeping the configuration that names it, so that running `unenroll` again deletes it; everything removed before stays removed and each step can be repeated) and the configuration, and what the game servers leave besides their folders: their Windows accounts (`pulsar_<shortId>`, with their logon right and profile; named by the server records and by the folders in the servers root), the firewall rules the agent made for them (the `Pulsar <shortId> …` rules of the `Pulsar` group, whether managing the firewall is on now or not), and the agent's `state` folder, which holds the server records (secret variables, RCON passwords) and the cached Steam logins. It prints what it removed and what it keeps: the servers' folders, the backups and the logs (agent and consoles), for the administrator to delete once they are no longer needed. What cannot be removed (an account, rules without elevation) is reported with what to do by hand. The node must also be deleted, or re-enrolled, in the panel. Since Phase 14 it stops the node's game servers first (they would otherwise keep running in their host processes); hosts the service was not running to stop are ended. It waits up to 60 s for the service to stop its games gracefully; a service still stopping after that is removed anyway (Windows deletes it once it stops), the games left are ended, and the rest (key, configuration) is removed, with a message saying so. With its games ended, the service gets 30 s more to stop; one still stopping then could yet write a server record or log on as a server account, so the server accounts and the `state` folder stay, and the message says to delete them by hand once the service is gone (the firewall rules still go). A configuration that cannot be read (corrupt JSON) does not stop it, since no retry would fix that: the service, the games and the configuration go, and the message says the node key, named only there, stays in the key store. Without a configuration (deleted by hand), the service is still removed when its command line runs it with that state directory (a development agent never runs as the service).
- `service stop` leaves the game servers running in their hosts (Phase 14, doc 06 "Server hosts"); `--stop-servers` stops them with the service, and they start again with it; when the service is not running, it ends the game servers the service left running instead. Both wait up to 60 s for the service.
- `enroll --log-file` and `unenroll --log-file` also write what they print to a file: the agent MSI runs them as custom actions, which have no console. A log file that cannot be opened is reported, and the command goes on without it. An unexpected error is written there too (the runtime would print it past the log) and fails the command (exit code 1).
- `--servers-root` and `--backups-root` are made full paths. A quoted folder ending in a backslash (`"D:\PulsarServers\"`) reaches the program with a quote at its end, since Windows reads `\"` as an escaped quote: that quote is dropped.
- `host` is the process a game server runs under (doc 06, "Server hosts"); its log is `logs\hosts\host-<server>-<date>.log`.
- The value after an option is always taken as its value: enrollment tokens are base64url and can start with `-`.
- The process list shows command lines: `--token -` reads the token from standard input, and without `--token` it is taken from the `PULSAR_ENROLLMENT_TOKEN` environment variable.

### Panel address

The panel URL must be an origin (`https://panel.example.com[:port]`), without path, query or credentials. HTTPS is required; plain HTTP is accepted only for a loopback panel, because the session token would otherwise travel in clear. The agent compares the origin the panel binds into enrollment results and challenges with the one it was configured with, and refuses to continue on a mismatch: behind a reverse proxy, the proxy must forward the original host and scheme.

The agent checks the panel's TLS certificate against the machine's trusted roots with a chain built only from the certificates the panel sends in the handshake: certificate downloads are disabled (on Windows that also turns off the automatic root update) and revocation is not checked, as before (`PanelTransport.PanelChainPolicy`, on every request and on the hub's WebSocket, which the agent opens through the same handler). The agent runs as SYSTEM, and whoever answers at the panel's address (a forged DNS answer, an intercepted route) chooses the addresses a certificate names: without this the agent would fetch them (its issuer's certificate over HTTP or LDAP) before refusing the certificate (doc 08, T31). So the panel (or the reverse proxy in front of it) must send its full chain, intermediates included, and the root must already be in the node's `LocalMachine\Root` store: a missing intermediate is no longer fetched, and the root of a public authority is not installed on demand on a fresh Windows (Windows installs those when something first validates a site with them; with the panel's self-signed certificate, `-TrustCertificate` puts it there). A panel that does not send its intermediates, or whose root the node lacks, fails the agent's TLS handshake (`PartialChain` or `UntrustedRoot` in the agent's log).

*Pinned certificate (Phase 18).* An agent enrolled from a node code (`PulsarAgent enroll … --panel-certificate <sha256>`, which `Install-Pulsar.ps1` passes when the machine does not already trust the certificate the code names and the panel presents) keeps that SHA-256 as `panelCertificate` in `config\agent.json` and accepts the panel's certificate only when the SHA-256 of its DER is that one (`PanelTransport.WithPinnedCertificate`, on enrollment, sign-in, rotation, transfers, the hub's WebSocket and the agents' address, which serves the same certificate): of its chain's errors only the missing trusted root is forgiven (`UntrustedRoot`, `PartialChain`: a self-signed certificate has no trusted root), so an expired or not yet valid certificate is refused, its name must still match the host, and any other certificate is refused, even one the machine trusts. Nothing is added to the machine's certificate stores, so the certificate vouches for nothing else on the node, whatever names it lists. Without a pin the machine's trusted roots decide, as above. The pin does not outlive the certificate: when the pinned certificate expires, the node is cut off until it is pinned again, so renew the panel's certificate before then. Re-issuing the panel's certificate (a new self-signed one, a renewal, a CA's in its place) cuts pinned nodes off until each is pinned again: enroll it again with a new code from **Add node** (or `PulsarAgent enroll … --panel-certificate <the new certificate's SHA-256>`), or, as an administrator of the node, change `panelCertificate` in `config\agent.json` (or remove it, once the machine trusts the new certificate's root) and restart the `PulsarAgent` service. `PulsarAgent status` shows the pin.

### Node key

ECDSA P-256 created through CNG with export policy *none*, in the TPM (Microsoft Platform Crypto Provider) when it can create the key, otherwise in the software key storage provider; the result is reported to the panel (`tpm`/`software`) and shown in the UI. Production keys are machine keys whose DACL grants only SYSTEM and Administrators. The state directory (`%ProgramData%\Pulsar\Agent` by default) gets a protected DACL with the same two principals and Administrators as owner. What the agent's own folders in it already hold (`config`, `logs`, `state`, `steamcmd`, `console-logs`, `backups`: a folder someone created before the agent) is reset to inherit that DACL, owned by Administrators; anything else in it (a development agent's `servers`) keeps its own rules; a junction or symbolic link at its top or in the agent's folders is refused (other reparse points, such as deduplicated files or OneDrive placeholders, are ordinary files, as in the file manager). A `--backups-root` gets the same DACL, but one that already holds something is refused unless it is already restricted to those accounts (an earlier enrollment): restricting it would change who can open the files there, and the agent cannot tell its backups from planted ones; and enrollment refuses a state directory (or backups folder) below a folder that an account other than SYSTEM, Administrators or TrustedInstaller owns or could rename or replace, before anything is written. The servers root (`--servers-root`, or the default) is secured at enrollment too: the same ancestor check (a root under `C:\Users\Public` is refused: someone could rename it and put a folder of theirs in its place, where the agent lends Steam logins), refused when it is a junction or link or holds someone else's files, and given the same DACL; what it holds keeps its rules (each server directory has its own). A development agent skips the ancestor checks, as for its state directory.

### Connection loop

1. Challenge/response → session token; the agent checks the challenge's `panelOrigin` before signing. It presents its node key as TLS client certificate (asked for on the agents' endpoint only), and tries its fallback address when its address does not answer (Phase 16, "Client certificates").
2. Hub over WebSockets only (no negotiation), `Authorization: Bearer` header, then `Hello` with the capabilities, inventory and agent version. The panel clock offset is measured at sign-in, from the grant (see "Authentication on every connection"), never from `HelloAccepted.ServerTime`, which is not signed; a difference above one minute is logged as a warning. The panel may send its first commands as soon as `Hello` is answered (an `UpdatePanelKeysCommand` to an agent that missed a rotation): the offset is known by then, so a node whose clock is off is not refused them as `command.expired`. Handling them never delays `Hello`'s answer: the SignalR client runs handlers that return a result without holding back the messages behind them. Opening the hub, `Hello` and the deliveries that waited for a connection (results, latest states) have 30 s together: a panel or proxy that keeps the connection alive but never answers is given up on, and that counts as a failed connection (and, at the agents' address, as one where no panel answers).
3. Node metrics right after `Hello` and every 15 s. A sample that fails (a Windows call that failed this time) is logged as a warning and skipped; only a failed send ends the loop (the connection is going away).
4. **Session hand-over:** one minute before the session expires (or at half its lifetime if it is shorter), the agent authenticates again and opens a second connection; its `Hello` makes the panel close the old one. Commands always arrive on the current connection, and the node never shows as offline because its session ended. A session is renewed 5 s after it opened at the earliest, and one renewed within a minute of its `Hello` (its token issued about to expire, a clock far off) counts as a failure, so the next one waits the backoff while it goes on: never a loop of sign-ins.
5. A lost connection is retried with exponential backoff (1 s, 2 s, 4 s… up to 60 s), randomized to 50–100 % of the value so many agents do not reconnect in lockstep after a panel restart. A rejected credential (revoked, node disabled or deleted) waits the maximum between attempts. Connecting is not enough to start the backoff over: a session closed within a minute of its `Hello` counts as one more failure (two machines with one node identity, a cloned VM, close each other's session at every `Hello`), and one that lasted starts it over.

The SignalR client's automatic reconnect is not used: every connection needs a fresh challenge and a new `Hello`, which the loop already does.

### Command verification

One verifier per session, in this order (the first failure answers the command):

| Check | Ack status | Error code |
|---|---|---|
| `KeyId` is a pinned panel key | `InvalidSignature` | `command.unknown_key` |
| Signature over the payload, for the `pulsar-command-v1` purpose | `InvalidSignature` | `command.invalid_signature` |
| Envelope readable | `Rejected` | `command.malformed` |
| `NodeId` and `SessionId` are this node and session | `Rejected` | `command.wrong_recipient` |
| Sequence new and inside the 1024-wide window | `Rejected` | `command.replayed` |
| Inside `IssuedAt`–`ExpiresAt` on the panel's clock, ±30 s | `Rejected` | `command.expired` |
| Supported `ProtocolVersion` | `Rejected` | `command.unsupported_version` |
| Command type handled by this agent | `UnsupportedCommand` | `command.unsupported` |

The verifier reads the pinned panel keys on every command, so an `UpdatePanelKeysCommand` applies to the next command. That command is also refused (`command.invalid_panel_keys`) when a key id is not its fingerprint, a key is not P-256, or the list leaves out the key that signed it.

Routing checks run on the envelope without its command, so an unknown command type is reported as unsupported rather than malformed. A sequence number is consumed as soon as the command is authentic and addressed to this session, even if a later check refuses it.

## Agent implementation (Phase 3): servers

- **Commands:** `server.provision`, `server.install` and `server.delete` are operations: the envelope carries the operation id, the ack only says accepted, and the result follows as `OperationCompleted`, kept in `state\outbox` and delivered until the hub call succeeds. The result is in the outbox before the operation counts as ended, so an agent that stops at that moment still reports it at its next connection; one that cannot be written there (a full disk) is logged, still delivered from memory, reported in flight by the Hello, and written again every few seconds. One operation runs per server; another one gets `Busy`. `server.start`, `server.stop`, `server.restart` and `server.kill` answer `Accepted` or `AlreadyInState` from the server's state machine (doc 05).
- **Events:** `ServerStateChanged` (sequence per server, increasing while the agent runs) is sent without waiting for an answer; the panel checks that the server belongs to the reporting node and drops older changes. `OperationProgress` is advisory. `OperationCompleted` is idempotent on the panel.
- **Hello** adds `Servers` (each server's state) and `OperationsInFlight` (running operations, plus finished ones whose result is still in the outbox) for reconciliation.
- **Capabilities** list the server commands, plus `server.test_game` when the agent has Pulsar's test game server.
- **Servers root:** the folder chosen at enrollment, otherwise `%SystemDrive%\PulsarServers` (`<data-dir>\servers` for a development agent). It is reported in the inventory.
