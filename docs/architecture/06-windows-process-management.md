# 06 — Windows process management: Job Objects, ConPTY and isolation

> Status: **implemented in Phase 3** (see "Implementation (Phase 3)" at the end for what differs from the proposal) · Decisions: ADR-0005 (accepted), ADR-0006, ADR-0007.
> Everything marked **[spike]** was validated with a prototype in Phase 0 before building on it.

## Why not `Process.Start()`

`System.Diagnostics.Process` cannot:

1. Create the process **inside** a Job before it runs any code (assigning it afterwards lets children created in between escape).
2. Launch as another user from a token (`CreateProcessAsUser`).
3. Attach a pseudo console (ConPTY).
4. Restrict which handles the child inherits (with `UseShellExecute=false` and redirection, the child may inherit inheritable handles of the agent).

So `Pulsar.Agent.Windows` uses Win32 directly, with P/Invoke generated by **CsWin32** (`Microsoft.Windows.CsWin32`, Microsoft's official source generator: correct signatures, `SafeHandle`s, no hand-written `DllImport`).

## Abstraction

```csharp
// Pulsar.Agent.Core
public interface IGameProcessManager
{
    Task<IGameProcess> StartAsync(ProcessLaunchSpec spec, CancellationToken ct);
}

public sealed record ProcessLaunchSpec(
    Guid ServerId,
    string ServerRoot,                     // authorized root directory
    string ExecutableRelativePath,
    IReadOnlyList<string> Arguments,       // argv already rendered by Pulsar.Manifests
    string WorkingDirectoryRelativePath,
    IReadOnlyDictionary<string, string> Environment,
    ConsoleMode ConsoleMode,               // Pty | Pipes
    ConsoleEncoding Encoding,
    ProcessIdentity Identity,              // dedicated account of the server
    ProcessLimits? Limits);                // reserved (memory/CPU) post-v1

public interface IGameProcess : IAsyncDisposable
{
    int MainProcessId { get; }
    DateTime StartedAtUtc { get; }
    Task<ProcessExit> Exited { get; }                       // exit of the main process
    ChannelReader<ConsoleChunk> Output { get; }
    ValueTask WriteInputAsync(string text, CancellationToken ct);
    ValueTask SendInterruptAsync(CancellationToken ct);     // Ctrl+C (Pty only)
    void TerminateTree(uint exitCode);                      // TerminateJobObject
    ProcessTreeUsage SampleUsage();                         // accumulated CPU, memory, process count
}
```

`WindowsGameProcessManager` implements this. A future `LinuxGameProcessManager` (cgroups/pidfd/pty) would implement the same interface without touching `Agent.Core`.

## Start sequence (Windows)

```
 1. Resolve and validate paths:
      exe = Path.GetFullPath(Combine(ServerRoot, ExecutableRelativePath))
      open a handle to the exe, GetFinalPathNameByHandle → must be under ServerRoot
      no path component may be a reparse point (junction/symlink)
 2. Job:
      CreateJobObject(unnamed)
      SetInformationJobObject(JobObjectExtendedLimitInformation):
         JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE
         JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION   (avoids WER dialogs that hang the server)
         (no BREAKAWAY_OK or SILENT_BREAKAWAY_OK: no child can leave the Job)
      SetInformationJobObject(JobObjectBasicUIRestrictions): EXITWINDOWS, GLOBALATOMS,
         HANDLES, READCLIPBOARD, WRITECLIPBOARD, SYSTEMPARAMETERS, DESKTOP, DISPLAYSETTINGS
      SetInformationJobObject(JobObjectAssociateCompletionPortInformation) → agent's shared IOCP
 3. Identity:
      LogonUser(server account, LOGON32_LOGON_BATCH) → token
      LoadUserProfile(token)              (required: without it the child gets SYSTEM's environment, spike 0002)
      CreateEnvironmentBlock(token) + manifest overrides + TEMP/TMP inside the server directory
      CreateRestrictedToken(token, DISABLE_MAX_PRIVILEGE) → child token (only SeChangeNotifyPrivilege;
         removes SeShutdownPrivilege, which Users hold on client editions)
 4. Console:
      Pty:   CreatePipe ×2 → CreatePseudoConsole(COORD{220, 50}, inRead, outWrite)
      Pipes: CreatePipe ×3 (stdin/stdout/stderr), only the child ends inheritable
 5. STARTUPINFOEX + attribute list:
      PROC_THREAD_ATTRIBUTE_JOB_LIST       → the process is born inside the Job (Windows 10+)
      PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE  (Pty)  or
      PROC_THREAD_ATTRIBUTE_HANDLE_LIST    (Pipes) → inherits ONLY those handles
      lpDesktop = the server's own window station/desktop with a DACL for SYSTEM, Administrators and the server SID
         (works with srcds, which creates a console window: see "Implementation (Phase 3)")
 6. CreateProcessAsUser(child token, lpApplicationName = absolute exe, lpCommandLine = quoted argv,
      flags: EXTENDED_STARTUPINFO_PRESENT | CREATE_UNICODE_ENVIRONMENT | CREATE_SUSPENDED
             (+ CREATE_NO_WINDOW in Pipes))
 7. Check IsProcessInJob; ResumeThread; close the thread handle and the child pipe ends.
 8. Register a wait on the main process handle (no thread blocked per server).
 9. Output reader tasks → stateful UTF-8 decoder → ring buffer + log + subscribers.
```

`CREATE_SUSPENDED` plus `JOB_LIST` is deliberately redundant: if `JOB_LIST` failed on some build, `AssignProcessToJobObject` runs before `ResumeThread`, and in no case does the process execute code outside the Job.

## Console: ConPTY vs pipes

| | **ConPTY** (`CreatePseudoConsole`, Windows 10 1809+) | **Pipes** (stdout/stderr/stdin) |
|---|---|---|
| Processes writing through the Windows console API (not stdout) | Works: conhost translates it into VT sequences | Nothing or garbled output is captured |
| ANSI colors in xterm.js | Native (VT) | Only if the process emits ANSI |
| Input | VT; Ctrl+C = byte `0x03` → `CTRL_C_EVENT` | stdin; Ctrl+C is unreliable from a service without a console |
| Output format | Rendered screen (cursor moves, redraws, wrapping at the width) | Clean line stream |
| Per-line timestamps | Approximate (per chunk) | Exact |

**Decision (validated by [spike 0001](../spikes/0001-console-capture.md)):** the manifest chooses `console.mode` among `pty`, `pipes` and `logfile+rcon`. SteamCMD runs under `pty` (block-buffered on pipes). `srcds.exe` (CS:S, GMod) needs `logfile+rcon`: on pipes it crashes because it requires a console for input, and given a ConPTY it allocates its own console and writes nothing to ours, so output is read from `-condebug`'s log file and commands/stop go through RCON. `cs2.exe` behaves the same way (spike 0001, F7).

A ConPTY child inherits the caller's standard handles when the caller has them; the agent service has none, and in development the agent clears its standard handles (or passes explicit ones) before creating ConPTY children.

Known gotchas to cover with tests:

- `ClosePseudoConsole` can block on older builds if nobody drains the output pipe: the reader stays alive until after the close.
- The pseudo console width affects wrapping; a wide fixed width (≈220) is used and it is never resized per client (several browsers watch the same console).
- Reader tasks never write to disk on every callback: they feed a channel with a batching writer.

## Graceful stop

Windows has no SIGTERM. Pulsar runs the manifest steps in order:

1. `consoleCommand` (e.g. `quit`, `stop`) written to the input, or `rconCommand` sent over RCON (`logfile+rcon` mode: `quit` over RCON stopped CS:S with exit code 0 in about 1 s).
2. `ctrlC` (Pty only).
3. Wait up to `timeoutSeconds` for the main process.
4. `TerminateJobObject` → kills **the whole tree** atomically.

When the main process exits and the Job still has processes (crash handlers, helpers), they get a 5 s grace period and then the Job is terminated. No orphans remain.

## Exit detection and events

- **Primary signal**: a wait on the main process handle (reliable exit code), registered with the thread pool (no thread blocked per server).
- **Secondary signal**: the Job's IOCP (`JOB_OBJECT_MSG_ACTIVE_PROCESS_ZERO`, `JOB_OBJECT_MSG_ABNORMAL_EXIT_PROCESS`, `JOB_OBJECT_MSG_NEW_PROCESS`). Microsoft documents that delivery of these messages is **not guaranteed**, so they are never the only source of truth; they serve diagnostics and counting. *Not used in Phase 3: the processes still alive in a Job are counted with `JobObjectBasicAccountingInformation` when the main process exits.*
- One dedicated thread reads the IOCP of every Job (completion key = server). No polling.

## Metrics (every 5 s, one timer for the whole node)

*Phase 5 (with the live console); Phase 3 reports states only.*

| Metric | Source |
|---|---|
| CPU % | `QueryInformationJobObject(JobObjectBasicAccountingInformation)`: Δ(TotalUserTime + TotalKernelTime) / (Δt × logical cores) |
| Process count | `ActiveProcesses` from the same query |
| Memory | `JobObjectBasicProcessIdList` → `GetProcessMemoryInfo` per process: working set, and commit charge (`PagefileUsage`, what a memory limit counts; Phase 12). |
| Main PID, uptime | From the supervisor state |
| Disk | On demand, cached (never in the 5 s cycle) |

Cost: a few syscalls per server every 5 s. No performance counters (slow and fragile).

## Isolation: one Windows account per server (ADR-0005, accepted)

**The agent runs as LocalSystem; no game server runs as SYSTEM.** A malicious SourceMod plugin or GMod Lua running as SYSTEM would compromise the whole machine.

| Option | Isolation between servers | Complexity |
|---|---|---|
| A. Everything as the agent's user | None; catastrophic if the agent is SYSTEM | Minimal |
| B. One shared low-privilege account for all | Protects the OS, not one server from another | Low |
| **C. One local account per server** | Each server only reaches its own directory | Medium |
| D. AppContainer | Strong | High; breaks networking and paths of many games |

**Decision: C**, implemented in Phase 3 together with process management (before the file manager, which relies on impersonation). Details:

- Account `pulsar_<shortId>` (≤ 20 characters) created with `NetUserAdd`, `UF_DONT_EXPIRE_PASSWD | UF_PASSWD_CANT_CHANGE`. **Its password is never stored:** right before every logon the agent sets a new random 64-character one (`NetUserSetInfo` level 1003; satisfies complexity policies) and uses it once. There is no secret at rest to steal, lose or get out of sync (an earlier draft kept it with DPAPI). Each logon of a server account therefore appears as a password reset in the security log when account management auditing is on.
- The token **always contains `BUILTIN\Users`** (through `Authenticated Users`; removing group membership has no effect, spike 0002), so isolation relies on directory ACLs and never on the account being outside Users. The child runs with a restricted token without privileges (start sequence, step 3).
- Residual risk: locations writable by Users (`C:\ProgramData`, `C:\Users\Public`) are readable by every server. `TEMP`/`TMP` point into the server directory and manifests keep game data there; system ACLs are not modified.
- LSA rights (`LsaAddAccountRights`): `SeBatchLogonRight`; **denied** `SeDenyInteractiveLogonRight`, `SeDenyRemoteInteractiveLogonRight`, `SeDenyNetworkLogonRight` (nobody can use it for RDP or SMB).
- ACLs: `<ServersRoot>` with inheritance disabled (SYSTEM and Administrators only). Each `<ServersRoot>\<shortId>`: SYSTEM and Administrators full control, `pulsar_<shortId>` Modify. A server cannot list or read another one. (An earlier draft also gave a shared SteamCMD account Modify on every server directory; see "SteamCMD" for why it was dropped.)
- **Escaping the Job.** A server's account can start processes outside its Job through Windows services: a scheduled task (it has the batch logon right), WMI, COM servers. They would keep running after the server stops, and even after its account is deleted. The agent kills every process running as the server's account (matched by the SID of its token) before each start, after the server's processes end, before installs and updates, and before deletion. A stray process can still live while its server runs, under no Job limits; such sweeps are logged as warnings.
- Not evaluated: S4U logon (no stored password). `LogonUser` + password is kept because it is better documented and validated by spike 0002.
- Known limitation: a **domain controller** has no local accounts; the agent refuses to install on a DC with a clear message.
- Window station / desktop: a process launched with another token from a service can fail to initialize user32 (`0xC0000142`) if its SID cannot access the window station/desktop. Spike 0002 did not reproduce it with a console process. Each server gets its own window station and desktop with a proper DACL; a real `srcds.exe` (which creates a console window) runs with it as its account from SYSTEM (Phase 3). Whether it would also run on the service's default desktop was not tested: the private station is kept because it also keeps one server's windows, atoms and clipboard away from the others.
- A "current user" mode exists only for development with the agent running in a console, with explicit warnings.

### SteamCMD

- **Each server has its own SteamCMD** (`<server>\.pulsar\steamcmd`), run **as the server's account**, in a Job, like the game. The first design had one installation per node under a shared `pulsar_steamcmd` account with Modify on every server directory; that account would have let a server plant a junction in its own folder and have SteamCMD write into another server's. With a copy per server, SteamCMD can only write where its server can write, a server tampering with its copy of an anonymous SteamCMD only affects itself (a copy that signs in with a Steam account is rebuilt first, below), and installs of different servers run in parallel (`SteamCmdOptions.MaxConcurrentRuns`, 2 by default, bounds bandwidth and disk load; a waiting install reports the stage `queued`). Each copy updates itself on its first run (about 70 MB) and keeps its own `appcache`.
- Arguments: `+@ShutdownOnFailedCommand 1 +@NoPromptForPassword 1 +force_install_dir <dir>` **before** `+login anonymous` (or a Steam account, below), `+app_update <appId> [-beta … [-betapassword …]] [validate]`, `+quit`. Built as argv, never concatenated for a shell.
- The bootstrapper is downloaded once from Valve's official URL over HTTPS into the agent's state directory (`steamcmd\steamcmd.exe`, SYSTEM and Administrators only) and accepted only with a valid Authenticode signature (`WinVerifyTrust`, without revocation checks so an offline node keeps working) **whose signer's organization is Valve's**: `O=Valve` in spike 0001, `O=Valve Corp.` since 2026, matched exactly. Servers get a copy of it. A run that only updated SteamCMD itself exits with code 7 and is simply run again.
- Runs under ConPTY (live output). Progress through a regex over ` Update state (0x61) downloading, progress: 9.44 (238319757 / 2524405728)` lines (`0x81` verifying, `0x3` reconfiguring), tolerant to format changes. Some messages are localized to the OS language, so parsing relies only on language-neutral lines (`Update state`, `Success!`, `ERROR!`) and exit codes.
- Retries with backoff for transient failures (3 attempts, 10 s then 30 s) — spike 0001 hit `ERROR! Failed to install app (Missing configuration)` (exit code 8) on the first attempt and the retry succeeded; a full disk (`Disk write failure`, `state is 0x202`) or an unavailable app (`No subscription`, `Invalid platform`) is not retried. An install stuck in `state is 0x6` (update required, files present: SteamCMD lacks the manifests of the build the files are from, after a copy from another install or an interrupted update) fails the same way at every identical run, so once per install the agent removes `steamapps/appmanifest_<app>.acf` (through the server's file access, never through a link) and runs SteamCMD again with `validate`, which checks every file and downloads what differs (Phase 11). A run that prints nothing for 10 minutes is killed and retried. Cancellation (`CancelOperationCommand`) terminates its Job; the operation completes as cancelled.
- Progress reaches the panel throttled (a new stage, a point of progress, or every 2 seconds); the panel keeps the latest in memory and writes it to the database only on stage changes or every 15 seconds.
- *Steam accounts (Phase 13):* most dedicated servers download anonymously; a manifest step with `login: "account"` needs an account that owns the game, and any server can be given one. The panel keeps the accounts (password encrypted with Data Protection) and sends a `SteamLogin` (account id, name, password, and a Steam Guard code when one was given) inside each install, update or addon removal that runs SteamCMD; the agent stores none of it. What the agent keeps is the login SteamCMD caches after a successful sign-in (`config/config.vdf` in its folder, the token that spares the password and the Steam Guard code next time), encrypted with DPAPI in `state\steam-logins\<account>.bin`, together with a SHA-256 of the account's name and password: once the panel changes either, the old login is dropped instead of used. It is **lent** to the server's SteamCMD for one run: written into the copy's `config` folder right before it starts (through the server's file access, as everything there), read back and deleted right after it ends; should the agent stop in between, it is deleted when the agent starts again and before the game's next start. The game is stopped during installs and updates, the file manager refuses `.pulsar/steamcmd/config` at any time, and backups never include `.pulsar`. That folder is refused by where the opened handle is, not by the name asked for: on Windows every entry the file manager opens is checked after opening, so an 8.3 short name (`PULSAR~1`, which a server's account cannot expand when it may not list the folders above its own) or a junction the server's account made inside the server pointing at it is refused too; the agent's command checks also treat a first segment shaped like a short name as `.pulsar`. *The copy itself (Phase 13 review):* the server's account controls `.pulsar\steamcmd`, so the game, a mod or the server's owner could replace `steamcmd.exe` or plant a DLL next to it and catch the password and the cached login. Before a run with an account the agent therefore deletes the whole folder (through the file manager, as the server's account, never through a link) and copies the verified bootstrapper again, which then updates itself from Valve (exit code 7, about 70 MB at every install or update with an account); anonymous runs keep reusing their copy. The file manager also refuses every change under `.pulsar` (uploads, new folders, renames and deletions; reading it stays allowed, `config` excepted). With a cached login the command line is `+login <name>` alone; without one (or when Steam refuses it) `+login <name> <password> [<code>]`, visible to the node's administrators and to the server's account while SteamCMD runs (the game is not running then). A cached login is kept after every run that may have signed in (one that succeeded, or failed later on); a run with one that fails before reaching the app (any failure but an error about the app, its state or the disk, or Steam's rate limit: an expired login does not always say so) drops it and tries once more with the password. A retry inside an operation signs in with what the previous attempt cached, so a Steam Guard code is used only once. Runs of one account wait for each other (they would race on its cached login). Steam Guard: SteamCMD would wait at its `Steam Guard code:` prompt (it has no line end), so the agent stops the run as soon as it shows and fails it with `steamcmd.guard_required`; the server's page asks for the code (mailed, or shown by the Steam mobile app) and runs the operation again with it. Other sign-in failures are not retried: `steamcmd.login_failed` (wrong password, result code 5), `steamcmd.rate_limited` (84), and a refused code is `guard_required` again (63, 65, 85, 88). Each line SteamCMD prints is read as printed (a one-letter password would otherwise break `Success!`), and the password and the code are blanked out of it before it is kept, logged or reported. The panel refuses passwords SteamCMD's command line would not pass whole: spaces, double quotes, control characters, and a leading `+` or `-` (a command or an option). When Steam stops an update for a code, the box asking for it also offers to verify every file again, since the failed operation does not record whether the update did.

### Windows Firewall

Optional, decided by the machine's administrator in the agent's configuration (`Pulsar:ManageFirewall`, off by default; the agent announces it to the panel with the `node.firewall` capability). Before every start the agent replaces the server's inbound rules (`Pulsar <shortId> <port name> <udp|tcp>`, grouping `Pulsar`) with one per bound port and **declared** protocol, limited to the server's executable and, when the allocation is not every interface, to its address, through the firewall's COM API (`HNetCfg.FwPolicy2`), never `netsh`. Game ports declare UDP only, so the TCP side where RCON listens is never opened (spike 0001, F7: CS2 has no RCON brute-force protection). Rules of ports the server no longer has are removed at the next start; all are removed when the server is deleted. The firewall is never disabled and no generic rules are created.

## Agent restarts and `KILL_ON_JOB_CLOSE` (ADR-0006)

| | **KILL_ON_JOB_CLOSE (v1)** | Servers survive the agent |
|---|---|---|
| Orphans | Impossible: if the agent dies, the OS closes the Job handle and kills the tree | Possible |
| Console after an agent restart | N/A (everything restarts cleanly) | Lost: the ConPTY/pipes belonged to the dead agent; the game keeps writing into a broken pipe |
| Updating the agent | Stops the servers (to be scheduled) | No downtime |
| Complexity | Low | High: needs a *shim* process per server owning the Job and console, with IPC to the agent |

KILL_ON_JOB_CLOSE was chosen for v1 for reliability: an orderly service stop (`OnStop`) stopped the servers gracefully before exiting, and they started again with the agent. `IGameProcess` was designed so a per-server *shim* (`containerd-shim` pattern) could replace it without changing the rest of the agent; Phase 14 built it, keeping KILL_ON_JOB_CLOSE (below).

## Server hosts (Phase 14)

Each game server runs under a **host process** of its own: `PulsarAgent host --server <id> --pipe <name>`, the agent's own program in a hidden mode, started by the agent as its own account (SYSTEM for the service, the developer for a development agent). The host starts the game with the same `WindowsGameProcessManager` as before, so the start sequence, isolation and limits above are unchanged; it owns the game's Job (still `KILL_ON_JOB_CLOSE`), its pseudo console or pipes and its exit. The agent drives it over a named pipe (`GameHostManager`, `HostedGameProcess` and `GameHostService` in `Pulsar.Agent.Core/Processes`).

- **Lifetime.** The agent starts a host for every start of a game (never for SteamCMD: installs and updates stay in the agent and are interrupted by a restart, as before). A host lives as long as its game: when the agent is done with an exited game it releases the host, which kills what is left of the tree, closes the game's console, sends the last of its output (a pseudo console shows its final screen as it closes) and only then answers and ends; the agent keeps the console open until that answer. A host that does not answer a release within 10 s is killed (a warning is logged). If a host dies, its Job closes and the game dies with it: no game ever runs without its host, and none runs without a Job.
- **Out of the agent's way.** Hosts are created detached (no console: a development agent's Ctrl+C is not theirs), in a new process group, inheriting no handle, and out of any Job the agent is in (`CREATE_BREAKAWAY_FROM_JOB`; when that Job forbids it, a warning is logged and hosts end with it, as games did before). Their security descriptor gives SYSTEM and the account that started them full access, Administrators only the rights to end them and wait for them (an `unenroll` ends them when the agent is not running), and nobody else any. They run from a **copy of the agent's program** made per version in the state directory (`host-programs\<fingerprint>`, SYSTEM and Administrators only), so updating the agent can replace its installed files while games run in hosts of the previous version. The copy is made when the agent first needs it; when it cannot be made (a full disk, say) the error is logged and starts fail with `host.start_failed` until it can, while the hosts already running are still found, watched and ended. When the agent starts, a copy no recorded host runs from is deleted, unless its program is still running (a copy whose executable cannot be opened for writing is left alone, so a host the agent did not recognize never loses half its program).
- **The pipe.** `pulsar-host-<server>-<64 random bits>`: created by the host with `FILE_FLAG_FIRST_PIPE_INSTANCE` and a DACL for its own account only, so another account can neither open it nor create it first. (Not .NET's `PipeOptions.CurrentUserOnly` on the host's end: it grants the token's default owner, which for SYSTEM is the Administrators group.) The pipe's owner is the account's default owner; the agent opens the pipe only when it has that owner (`PipeOptions.CurrentUserOnly` on its end) and checks that the serving process is the host it started (process id and start time, so a reused id is not mistaken for it). One connection at a time; the next agent connects when the previous one is gone. Frames are a 32-bit length and JSON (`GameHostProtocol`): requests (hello, start, input, Ctrl+C, terminate, limits, usage, release) and events (output with its offsets, output lost, output ended, exited). A frame the host cannot read ends that connection, never the host; a request that fails in the host is answered as failed (`host.request_failed`).
- **Protocol versions.** The first request is a hello with the agent's protocol version; a host of another version refuses it. An agent update that changed the protocol must not end every game on the node, so such a host is left running with its game and its record (for an agent that speaks its protocol), and a warning is logged. The server is never started beside it, and the agent reports it offline (it has no game it can drive), so the panel offers Start: a start, a stop or a kill of the server (or its deletion) ends that host, and its game with it, and a start then starts the server as usual. Ending it is a kill (the game's console and Ctrl+C belong to that host), so the server's console says so ("ended the game (killed, without saving)"). A restart is refused (`server.host_incompatible`, explained in the panel) until then.
- **Output.** The host drains the game's output whether or not anyone reads (a game whose output is not read blocks) into a ring of about a million characters, addressed by character offsets since the game started. The agent asks for output from an offset; output the ring no longer holds is reported as lost, and the console says so ("N characters of output were lost while the agent was away").
- **Taking a game over.** For every game in a host the agent keeps a record (`state\hosts\<server>.json`): the host's pipe, process id and start time, whether the game was ready, and how far the console was read, its offset in the host and, for `logfile+rcon` games, its position in the game's log file (the last byte of a whole character: never inside one). It is written as soon as the host is started, before its game (an account's first logon takes seconds, and an agent that dies meanwhile must find the host and whatever game it started), then when the game starts, at every state change, every second while the console moves, and exactly when the agent stops; it is deleted when a game cannot start (its host is ended). When the agent starts, before its first Hello, it connects to every recorded host, all at once, each getting up to 30 s to accept the connection and 30 s more to answer: the server is running again without a start, reported by the Hello's snapshot, and its console continues from the recorded position, so after an orderly stop nothing is missing or repeated and after a crash of the agent at most a second of output is shown again (the console log on disk, written in batches about every second, can miss up to that much from right before the crash). A game that was still starting has its readiness checked again (a log line it already printed is not seen again: it then counts as running when the readiness times out). A game that was being stopped is still stopping: its exit ends the stop (not a crash), the stop's timeout runs again, and a restart starts it again afterwards. A game that exited while no agent was connected (its host keeps the exit code, and kills leftover children after the usual grace) is handled as if it had just exited: the crash policy applies. A host that is gone (the machine restarted) means the game is gone, as after an agent crash before (auto-start servers start); so is a host that never got a game (the agent died before starting it), which is released. A host that is alive but does not answer in time, or is not the process serving its pipe, is killed with its game, so it never runs beside a new start; a host whose server the node no longer has is killed too. A host whose server is still the node's but could not be loaded (its record names something this agent cannot run, or could not be read and was set aside) is left running with its record, and a warning is logged.
- **When the agent stops.** A service stop, a restart or an update leaves the games running (the agent lets go of each host). Windows shutting down stops them gracefully first, as before (the service lifetime tells a shutdown from a stop; they would die with the machine otherwise), and they start again with the agent. `PulsarAgent unenroll` and `PulsarAgent service stop --stop-servers` ask a running service for the same (a `state\stop-servers` file the agent reads when it stops, and deletes); when the service is not running, nobody would read that file, so they end the hosts it left instead (their games end with them), and neither writes it. A file older than the agent's run was left by an earlier one and is deleted when the agent starts, so it never stops the games at a later, plain stop. A server already stopping finishes its stop.
- **Account logons.** Setting a server account's password and logging on with it is one step under a lock (see "Isolation"); hosts log server accounts on too, so the lock is shared by the agent and its hosts: a file per account in the state directory (`state\logon-locks\<account>.lock`, SYSTEM and Administrators only, which the hosts find through `--data-dir`), held open without sharing while the password is set and the account logs on, waited for up to 30 s. A server's account can neither name nor reach it. (A named kernel object would not do: any account can create a mutex in the global namespace, which needs no privilege, and hold it, or deny SYSTEM access to it, blocking every logon of another server's account.) The handle closes with its process, so a process that dies holding the lock does not keep it. A development agent logs no account on.
- **Cost.** A host is a .NET process: about 12 MB of private memory (40 MB working set, most of it shared with the agent's program files).
- `Pulsar:ServerHosts` set to `false` runs games inside the agent as before Phase 14 (they then stop with it). The hosts an earlier run left are ended when the agent starts (with a warning), since a game it starts would run beside theirs. The agent announces hosts with the `server.hosts` capability.

## Resource limits (Phase 12)

The Job already exists per server, so limits are configuration of it. A server has an optional CPU cap (a share of the whole node, 1–100 %, the unit its usage is shown in) and an optional memory cap (MiB), set with `server.limits.edit` (node or global roles only) and sent in the server's spec (`ServerRuntimeSpec.Limits`; agents announce `server.limits`, and the panel refuses limits for an agent that does not).

- CPU: `JobObjectCpuRateControlInformation` with `ENABLE | HARD_CAP`, the rate in cycles per 10,000. Every job gets one, the whole machine when there is no cap: Windows refuses to turn rate control off on a job that never had it, and this way a cap can be added, changed and removed while the server runs. Programs that size their threads by the processors they may use see the cap in force when they start (.NET counts `Environment.ProcessorCount` from it; found by the tests, whose CPU burner first used it).
- Memory: `JOB_OBJECT_LIMIT_JOB_MEMORY` counts the memory the whole tree commits; a process asking for more is refused it, and most games then crash. The job's completion port reports `JOB_OBJECT_MSG_JOB_MEMORY_LIMIT`; a crash after it is reported as `MemoryLimit` (the crash policy applies as for any crash) and notified as "ran out of memory". .NET programs stay under a job's memory limit by themselves (their garbage collector reads it), so the test game allocates native memory, as engines do. The usage shows committed memory next to the cap (the working set otherwise).
- Changes reach a running server at once (`ApplyServerSpecCommand` → `IGameProcess.ApplyLimits`); SteamCMD runs are never capped.
- Not done: network rate (`JobObjectNetRateControlInformation`) and I/O priority.

## Backup snapshots (Phase 15)

A backup of a running game reads its files from a Volume Shadow Copy snapshot (`WindowsVolumeSnapshots`, the VSS requester API through CsWin32: `IVssBackupComponents`, no library):

- The volume is the one the server directory is on after any junction to it: `GetFinalPathNameByHandle(VOLUME_NAME_GUID)` gives `\\?\Volume{guid}\` and the directory's path on it. A path without a volume name (a network share) has no snapshot.
- `InitializeForBackup`, `SetContext(VSS_CTX_FILE_SHARE_BACKUP)` (non-persistent, auto-release, **without writers**: games are not VSS writers, their own save comes through the console first), `SetBackupState` as a copy backup (other backup programs' history is left alone), `StartSnapshotSet`, `AddToSnapshotSet`, `DoSnapshotSet`, then `GetSnapshotProperties` for the device (`\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopyN`). Without writers there is no backup components document, so neither `GatherWriterMetadata` nor `PrepareForBackup` is called: `PrepareForBackup` answers `VSS_E_BAD_STATE` then (found in Windows Sandbox), and Microsoft's `vshadow` skips both too. The backup reads `<device>\<path on the volume>`. Windows holds the volume's writes for a moment while it takes the snapshot.
- The snapshot is deleted when the backup has read it (`DeleteSnapshots`, then the requester is released); an auto-release snapshot also goes when its requester's process ends, so an agent that crashes leaves none behind. One snapshot set is created at a time; another program's set in progress is waited for (up to 2 minutes, then `snapshot.busy`). The blocking calls run on a thread of their own.
- The snapshot is read through the file manager as the server's account, like the live directory (doc 08, "Backups and restore"): the reads open the root read-only (a snapshot is a read-only volume), accept the `\\?\` form, and compare final paths by device name (`VOLUME_NAME_NT`) when the volume has no drive letter. Junctions and symbolic links in the snapshot are listed, never followed, and a hard link keeps its target's ACL, so the server's account still reads nothing it could not read live.
- Failures fall back to a live copy with a reason: `E_ACCESSDENIED` (a development agent without administrator rights) → `snapshot.not_permitted`; `VSS_E_VOLUME_NOT_SUPPORTED(_BY_PROVIDER)` → `snapshot.unsupported`; `VSS_E_INSUFFICIENT_STORAGE`, `VSS_E_MAXIMUM_NUMBER_OF_SNAPSHOTS_REACHED`, `VSS_E_MAXIMUM_DIFFAREA_ASSOCIATIONS_REACHED` → `snapshot.no_space`; the service disabled or not answering → `snapshot.unavailable`; a Windows without `vssapi.dll` → `snapshot.unsupported`; anything else → `snapshot.failed` (the agent logs Windows' answer). Deleting the snapshot is best effort: a failure is logged, never fails a backup whose archive is complete. `Pulsar:BackupSnapshots=false` turns snapshots off (`snapshot.disabled`).
- Client Windows supports the requester API (only `vssadmin create shadow` is limited to Server editions). Checked in Windows Sandbox with the agent service as SYSTEM: a file the test game held open with no sharing was in the backup, the snapshot was gone afterwards.

## Tests

`Pulsar.TestGameServer` is a test executable driven by arguments: it prints output, reads stdin, spawns children and grandchildren, ignores `quit`, crashes with a given code, writes through the console API, tries to create a junction. `Pulsar.Agent.Windows.Tests` (Windows runners only) verifies:

- killing the Job leaves no process alive (grandchildren included);
- killing the test agent process kills its servers (KILL_ON_JOB_CLOSE);
- the child does not inherit unlisted handles;
- crash detection and exit codes;
- stop via command, Ctrl+C and timeout;
- the process runs as the expected account and cannot read another server's directory.

## Implementation (Phase 3)

- **Code.** `Pulsar.Agent.Core/Processes` (`IGameProcessManager`, `IGameProcess`, `IServerProvisioner`), `Pulsar.Agent.Windows/Processes` (`WindowsGameProcessManager`, `WindowsGameProcess`, `JobObject`, `ServerPaths`, `WindowsCommandLine`) and `Pulsar.Agent.Windows/Servers` (`WindowsServerAccounts`, `WindowsServerProvisioner`, `ServerWindowStation`).
- **Start sequence** as above: paths resolved under the server directory with no junction or link in them and the final path of the executable checked; Job (kill on close, die on unhandled exception, no breakaway, the UI restrictions listed) given through the job list attribute to a process created suspended (assigned before resuming if the attribute did not apply); pseudo console with null standard handles, or pipes with a handle list; `TEMP`/`TMP` in `<server>\.pulsar\temp`, created through `IServerFiles` (a `.pulsar` junction is refused, never followed); reserved variables refused.
- **Account launches** log on with a fresh password (see "Isolation"), load the profile, take the environment from `CreateEnvironmentBlock`, start the game with the `DISABLE_MAX_PRIVILEGE` token and give it **its own window station and desktop**, open to SYSTEM, Administrators and the server's account (`Pulsar-<serverId>\Default`). The profile stays loaded while the process runs; provisioning logs the account on once, so the profile already exists at the first start (creating it took seconds on Windows Server 2025). A development agent (`--dev`) starts servers as the current user, without accounts or window stations.
- **Ctrl+C.** "Ignore Ctrl+C" is inherited by child processes. A parent started in a new process group (a test host, some service wrappers) passes it on, and then Ctrl+C never reaches a server; the agent clears it for itself (`SetConsoleCtrlHandler(NULL, FALSE)`) before starting servers.
- **Server directories.** `<ServersRoot>` (default `%SystemDrive%\PulsarServers`) is protected (SYSTEM and Administrators, Administrators as owner). Each `<ServersRoot>\<shortId>` adds Modify for the server's account and limits `OWNER RIGHTS` to Modify, so a server owns the files it creates but cannot change who may read them.
- **The agent writes into folders a server controls** (install steps, deletion) only through checks: install steps refuse paths through junctions or links and replace files instead of writing into them (an existing name could be a hard link to a system file); deletion removes links without following them. .NET's recursive delete would also not follow a junction, but it removes one through `DeleteVolumeMountPoint`, which needs elevation, so the agent walks the tree itself. Installs need the server offline, so none of its processes can swap a folder in between.
- **Agent restarts (ADR-0006).** Killing the agent kills its servers with their Jobs (checked by hand with a development agent: no process left). An orderly stop (service stop, update, reboot) stops the servers gracefully within 20 s and starts them again with the agent; after a crash of the agent, only auto-start servers start. *Since Phase 14 games run in host processes and survive the agent ("Server hosts"); this is the behavior with `Pulsar:ServerHosts` set to `false`.*
- **Verified:** `Pulsar.Agent.Windows.Tests` (pseudo console and pipes, argv round trip, Ctrl+C, exit codes, trees killed, no inherited handles, path checks, environment; accounts, rights, ACLs, profile and restricted token, and a server unable to read another one, as SYSTEM in CI), the production install check in Windows Sandbox and CI (the test game server as its own account in session 0 from the SYSTEM service), and the real-game check below.
- **Agent file access (Phase 4).** Writing configuration files, reading the game's log, copying SteamCMD: the agent opens files through `IServerFiles`, which never follows a final link (`FILE_FLAG_OPEN_REPARSE_POINT`) and checks the path the opened handle really has (`GetFinalPathNameByHandle`) against the server directory. Folders are opened and created level by level, each through the handle of the checked one above it (`NtCreateFile` with a root directory), and a written file is created through the last checked folder's handle the same way: a folder swapped for a junction after its check is not followed, and a file that still ends up outside (the checked folder itself moved away) is deleted through its own handle. However a server swaps junctions, the handle the agent uses is inside its directory. Writes delete the old file and create a new one, so a hard link never redirects them. A server directory reached through an administrator's junction is followed (only what lies below it is the server's).
- **Deleting a server directory** (deprovisioning, as SYSTEM) walks it by handle as the file manager deletes: every entry is opened relative to the handle of the folder it was listed in, by the very name listed (`NtCreateFile` with a root directory), without following a link, and deleted through that handle. No path is looked up again, so a folder swapped for a junction while the agent deletes never takes it outside, and names a Windows path would change (`name.`, `name `, which a server's account can create with `\\?\` paths) are deleted as they are instead of failing forever. The walk keeps its own stack: depth is not limited.
- **File manager (Phase 6).** `WindowsServerFileManager` opens every entry without following a final link and checks the path its handle really has against the server directory (a server directory reached through an administrator's junction is followed; only what lies below it is the server's). It works on those handles: listings come from the directory handle (`FileFullDirectoryInfo`), renames name the checked destination folder by its handle (`FILE_RENAME_INFORMATION` with a root directory, through `NtSetInformationFile`: the Win32 call refuses a root directory; POSIX semantics since Phase 11, so a file another program is reading, as a virus scanner does right after a write, is still replaced, and a read-only one too, with the classic rename on file systems without them), deletions mark the handle (POSIX semantics, read-only files included) and never enter a link. Junctions and symbolic links (name-surrogate reparse tags) are listed as links and never followed; other reparse points (deduplicated or compressed files, cloud placeholders) are ordinary files. Opening, creating, renaming and deleting run **as the server's account** (`ServerImpersonation`: a batch logon with a fresh password, its privileges removed as for the game, kept for a minute after its last use; the password and the logon are one step under a lock shared with process launches); reading and writing content happen on the opened handles, outside the impersonation. So Windows itself refuses what the account may not do: as server A, a hard link planted in A's folder to server B's file is listed but cannot be read or deleted (verified as SYSTEM in CI). Paths longer than `MAX_PATH` work (`\\?\` paths). A development agent acts as its own user.
- **Real game (`scripts/sandbox/real-game`, `RealGameTests`).** A Counter-Strike: Source dedicated server, copied into a new server folder, started by `WindowsGameProcessManager` as its account from SYSTEM in Windows Sandbox (pseudo console, restricted token, private window station, Job with UI restrictions): it wrote its own `console.log` (`-condebug`) and reached `Server is hibernating` in about 2 s with two processes in its Job (srcds and the console host it creates), was still running 10 s later, and nothing was left after its tree was terminated. As in spike 0001, nothing reached the pseudo console: Source servers need `logfile+rcon` (Phase 4). GMod is checked the same way when its manifest is written.
- **Real game through the panel (Phase 4).** The production install check (Windows Sandbox and the CI job, Windows Server 2025) creates a Counter-Strike: Source server through the API with the agent as a SYSTEM service: SteamCMD downloads it from Valve as the server's account with live progress, srcds becomes ready over RCON with the configured map and slots, `server.cfg` and the firewall rule (UDP only, bound to `srcds.exe`) are in place, `quit` over RCON stops it and the deletion leaves nothing. On Windows Server 2025, srcds ends with exit code `0xC0000409` (a fast fail on its way out) after `quit`, where it ended with 0 on Windows 11: the stop is still the requested one (no timeout, no kill), so exit codes after a requested stop are reported, not judged. CS2 went through the same panel flow on a developer machine with a development agent (create, install progress and cancel, install, start with the configured mode, map and slots, settings applied at the next start, stop over RCON, delete).
