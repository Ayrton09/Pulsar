# 06 — Windows process management: Job Objects, ConPTY and isolation

> Status: **implemented in Phase 3** (see "Implementation (Phase 3)" at the end for what differs from the proposal) · Decisions: ADR-0005 (accepted), ADR-0006, ADR-0007.
> Everything marked **[spike]** was validated with a prototype in Phase 0 before building on it.

## Why not `Process.Start()`

`System.Diagnostics.Process` cannot:

1. Create the process **inside** a Job before it runs any code (assigning it afterwards lets children created in between escape).
2. Launch as another user from a token (`CreateProcessAsUser`).
3. Attach a pseudo console (ConPTY).
4. Restrict which handles the child inherits (with `UseShellExecute=false` and redirection, the child may inherit inheritable handles of the agent).

So `Pulsar.Agent.Windows` uses Win32 directly, with P/Invoke generated by **CsWin32** (`Microsoft.Windows.CsWin32`, Microsoft's official source generator: correct signatures, `SafeHandle`s, no hand-written `DllImport`).

## Abstraction

```csharp
// Pulsar.Agent.Core
public interface IGameProcessManager
{
    Task<IGameProcess> StartAsync(ProcessLaunchSpec spec, CancellationToken ct);
}

public sealed record ProcessLaunchSpec(
    Guid ServerId,
    string ServerRoot,                     // authorized root directory
    string ExecutableRelativePath,
    IReadOnlyList<string> Arguments,       // argv already rendered by Pulsar.Manifests
    string WorkingDirectoryRelativePath,
    IReadOnlyDictionary<string, string> Environment,
    ConsoleMode ConsoleMode,               // Pty | Pipes
    ConsoleEncoding Encoding,
    ProcessIdentity Identity,              // dedicated account of the server
    ProcessLimits? Limits);                // reserved (memory/CPU) post-v1

public interface IGameProcess : IAsyncDisposable
{
    int MainProcessId { get; }
    DateTime StartedAtUtc { get; }
    Task<ProcessExit> Exited { get; }                       // exit of the main process
    ChannelReader<ConsoleChunk> Output { get; }
    ValueTask WriteInputAsync(string text, CancellationToken ct);
    ValueTask SendInterruptAsync(CancellationToken ct);     // Ctrl+C (Pty only)
    void TerminateTree(uint exitCode);                      // TerminateJobObject
    ProcessTreeUsage SampleUsage();                         // accumulated CPU, memory, process count
}
```

`WindowsGameProcessManager` implements this. A future `LinuxGameProcessManager` (cgroups/pidfd/pty) would implement the same interface without touching `Agent.Core`.

## Start sequence (Windows)

```
 1. Resolve and validate paths:
      exe = Path.GetFullPath(Combine(ServerRoot, ExecutableRelativePath))
      open a handle to the exe, GetFinalPathNameByHandle → must be under ServerRoot
      no path component may be a reparse point (junction/symlink)
 2. Job:
      CreateJobObject(unnamed)
      SetInformationJobObject(JobObjectExtendedLimitInformation):
         JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE
         JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION   (avoids WER dialogs that hang the server)
         (no BREAKAWAY_OK or SILENT_BREAKAWAY_OK: no child can leave the Job)
      SetInformationJobObject(JobObjectBasicUIRestrictions): EXITWINDOWS, GLOBALATOMS,
         HANDLES, READCLIPBOARD, WRITECLIPBOARD, SYSTEMPARAMETERS, DESKTOP, DISPLAYSETTINGS
      SetInformationJobObject(JobObjectAssociateCompletionPortInformation) → agent's shared IOCP
 3. Identity:
      LogonUser(server account, LOGON32_LOGON_BATCH) → token
      LoadUserProfile(token)              (required: without it the child gets SYSTEM's environment, spike 0002)
      CreateEnvironmentBlock(token) + manifest overrides + TEMP/TMP inside the server directory
      CreateRestrictedToken(token, DISABLE_MAX_PRIVILEGE) → child token (only SeChangeNotifyPrivilege;
         removes SeShutdownPrivilege, which Users hold on client editions)
 4. Console:
      Pty:   CreatePipe ×2 → CreatePseudoConsole(COORD{220, 50}, inRead, outWrite)
      Pipes: CreatePipe ×3 (stdin/stdout/stderr), only the child ends inheritable
 5. STARTUPINFOEX + attribute list:
      PROC_THREAD_ATTRIBUTE_JOB_LIST       → the process is born inside the Job (Windows 10+)
      PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE  (Pty)  or
      PROC_THREAD_ATTRIBUTE_HANDLE_LIST    (Pipes) → inherits ONLY those handles
      lpDesktop = the server's own window station/desktop with a DACL for SYSTEM, Administrators and the server SID
         (works with srcds, which creates a console window: see "Implementation (Phase 3)")
 6. CreateProcessAsUser(child token, lpApplicationName = absolute exe, lpCommandLine = quoted argv,
      flags: EXTENDED_STARTUPINFO_PRESENT | CREATE_UNICODE_ENVIRONMENT | CREATE_SUSPENDED
             (+ CREATE_NO_WINDOW in Pipes))
 7. Check IsProcessInJob; ResumeThread; close the thread handle and the child pipe ends.
 8. Register a wait on the main process handle (no thread blocked per server).
 9. Output reader tasks → stateful UTF-8 decoder → ring buffer + log + subscribers.
```

`CREATE_SUSPENDED` plus `JOB_LIST` is deliberately redundant: if `JOB_LIST` failed on some build, `AssignProcessToJobObject` runs before `ResumeThread`, and in no case does the process execute code outside the Job.

## Console: ConPTY vs pipes

| | **ConPTY** (`CreatePseudoConsole`, Windows 10 1809+) | **Pipes** (stdout/stderr/stdin) |
|---|---|---|
| Processes writing through the Windows console API (not stdout) | Works: conhost translates it into VT sequences | Nothing or garbled output is captured |
| ANSI colors in xterm.js | Native (VT) | Only if the process emits ANSI |
| Input | VT; Ctrl+C = byte `0x03` → `CTRL_C_EVENT` | stdin; Ctrl+C is unreliable from a service without a console |
| Output format | Rendered screen (cursor moves, redraws, wrapping at the width) | Clean line stream |
| Per-line timestamps | Approximate (per chunk) | Exact |

**Decision (validated by [spike 0001](../spikes/0001-console-capture.md)):** the manifest chooses `console.mode` among `pty`, `pipes` and `logfile+rcon`. SteamCMD runs under `pty` (block-buffered on pipes). `srcds.exe` (CS:S, GMod) needs `logfile+rcon`: on pipes it crashes because it requires a console for input, and given a ConPTY it allocates its own console and writes nothing to ours, so output is read from `-condebug`'s log file and commands/stop go through RCON. `cs2.exe` behaves the same way (spike 0001, F7).

A ConPTY child inherits the caller's standard handles when the caller has them; the agent service has none, and in development the agent clears its standard handles (or passes explicit ones) before creating ConPTY children.

Known gotchas to cover with tests:

- `ClosePseudoConsole` can block on older builds if nobody drains the output pipe: the reader stays alive until after the close.
- The pseudo console width affects wrapping; a wide fixed width (≈220) is used and it is never resized per client (several browsers watch the same console).
- Reader tasks never write to disk on every callback: they feed a channel with a batching writer.

## Graceful stop

Windows has no SIGTERM. Pulsar runs the manifest steps in order:

1. `consoleCommand` (e.g. `quit`, `stop`) written to the input, or `rconCommand` sent over RCON (`logfile+rcon` mode: `quit` over RCON stopped CS:S with exit code 0 in about 1 s).
2. `ctrlC` (Pty only).
3. Wait up to `timeoutSeconds` for the main process.
4. `TerminateJobObject` → kills **the whole tree** atomically.

When the main process exits and the Job still has processes (crash handlers, helpers), they get a 5 s grace period and then the Job is terminated. No orphans remain.

## Exit detection and events

- **Primary signal**: a wait on the main process handle (reliable exit code), registered with the thread pool (no thread blocked per server).
- **Secondary signal**: the Job's IOCP (`JOB_OBJECT_MSG_ACTIVE_PROCESS_ZERO`, `JOB_OBJECT_MSG_ABNORMAL_EXIT_PROCESS`, `JOB_OBJECT_MSG_NEW_PROCESS`). Microsoft documents that delivery of these messages is **not guaranteed**, so they are never the only source of truth; they serve diagnostics and counting. *Not used in Phase 3: the processes still alive in a Job are counted with `JobObjectBasicAccountingInformation` when the main process exits.*
- One dedicated thread reads the IOCP of every Job (completion key = server). No polling.

## Metrics (every 5 s, one timer for the whole node)

*Phase 5 (with the live console); Phase 3 reports states only.*

| Metric | Source |
|---|---|
| CPU % | `QueryInformationJobObject(JobObjectBasicAccountingInformation)`: Δ(TotalUserTime + TotalKernelTime) / (Δt × logical cores) |
| Process count | `ActiveProcesses` from the same query |
| Memory | `JobObjectBasicProcessIdList` → `GetProcessMemoryInfo` per process (private bytes / working set). Handles opened with `PROCESS_QUERY_LIMITED_INFORMATION` are reused. |
| Main PID, uptime | From the supervisor state |
| Disk | On demand, cached (never in the 5 s cycle) |

Cost: a few syscalls per server every 5 s. No performance counters (slow and fragile).

## Isolation: one Windows account per server (ADR-0005, accepted)

**The agent runs as LocalSystem; no game server runs as SYSTEM.** A malicious SourceMod plugin or GMod Lua running as SYSTEM would compromise the whole machine.

| Option | Isolation between servers | Complexity |
|---|---|---|
| A. Everything as the agent's user | None; catastrophic if the agent is SYSTEM | Minimal |
| B. One shared low-privilege account for all | Protects the OS, not one server from another | Low |
| **C. One local account per server** | Each server only reaches its own directory | Medium |
| D. AppContainer | Strong | High; breaks networking and paths of many games |

**Decision: C**, implemented in Phase 3 together with process management (before the file manager, which relies on impersonation). Details:

- Account `pulsar_<shortId>` (≤ 20 characters) created with `NetUserAdd`, `UF_DONT_EXPIRE_PASSWD | UF_PASSWD_CANT_CHANGE`. **Its password is never stored:** right before every logon the agent sets a new random 64-character one (`NetUserSetInfo` level 1003; satisfies complexity policies) and uses it once. There is no secret at rest to steal, lose or get out of sync (an earlier draft kept it with DPAPI). Each logon of a server account therefore appears as a password reset in the security log when account management auditing is on.
- The token **always contains `BUILTIN\Users`** (through `Authenticated Users`; removing group membership has no effect, spike 0002), so isolation relies on directory ACLs and never on the account being outside Users. The child runs with a restricted token without privileges (start sequence, step 3).
- Residual risk: locations writable by Users (`C:\ProgramData`, `C:\Users\Public`) are readable by every server. `TEMP`/`TMP` point into the server directory and manifests keep game data there; system ACLs are not modified.
- LSA rights (`LsaAddAccountRights`): `SeBatchLogonRight`; **denied** `SeDenyInteractiveLogonRight`, `SeDenyRemoteInteractiveLogonRight`, `SeDenyNetworkLogonRight` (nobody can use it for RDP or SMB).
- ACLs: `<ServersRoot>` with inheritance disabled (SYSTEM and Administrators only). Each `<ServersRoot>\<shortId>`: SYSTEM and Administrators full control, `pulsar_<shortId>` Modify. A server cannot list or read another one. (An earlier draft also gave a shared SteamCMD account Modify on every server directory; see "SteamCMD" for why it was dropped.)
- **Escaping the Job.** A server's account can start processes outside its Job through Windows services: a scheduled task (it has the batch logon right), WMI, COM servers. They would keep running after the server stops, and even after its account is deleted. The agent kills every process running as the server's account (matched by the SID of its token) before each start, after the server's processes end, before installs and updates, and before deletion. A stray process can still live while its server runs, under no Job limits; such sweeps are logged as warnings.
- Not evaluated: S4U logon (no stored password). `LogonUser` + password is kept because it is better documented and validated by spike 0002.
- Known limitation: a **domain controller** has no local accounts; the agent refuses to install on a DC with a clear message.
- Window station / desktop: a process launched with another token from a service can fail to initialize user32 (`0xC0000142`) if its SID cannot access the window station/desktop. Spike 0002 did not reproduce it with a console process. Each server gets its own window station and desktop with a proper DACL; a real `srcds.exe` (which creates a console window) runs with it as its account from SYSTEM (Phase 3). Whether it would also run on the service's default desktop was not tested: the private station is kept because it also keeps one server's windows, atoms and clipboard away from the others.
- A "current user" mode exists only for development with the agent running in a console, with explicit warnings.

### SteamCMD

- **Each server has its own SteamCMD** (`<server>\.pulsar\steamcmd`), run **as the server's account**, in a Job, like the game. The first design had one installation per node under a shared `pulsar_steamcmd` account with Modify on every server directory; that account would have let a server plant a junction in its own folder and have SteamCMD write into another server's. With a copy per server, SteamCMD can only write where its server can write, a server tampering with its copy only affects itself, and installs of different servers run in parallel (`SteamCmdOptions.MaxConcurrentRuns`, 2 by default, bounds bandwidth and disk load; a waiting install reports the stage `queued`). Each copy updates itself on its first run (about 70 MB) and keeps its own `appcache`.
- Arguments: `+@ShutdownOnFailedCommand 1 +@NoPromptForPassword 1 +force_install_dir <dir>` **before** `+login anonymous`, `+app_update <appId> [-beta … [-betapassword …]] [validate]`, `+quit`. Built as argv, never concatenated for a shell.
- The bootstrapper is downloaded once from Valve's official URL over HTTPS into the agent's state directory (`steamcmd\steamcmd.exe`, SYSTEM and Administrators only) and accepted only with a valid Authenticode signature (`WinVerifyTrust`, without revocation checks so an offline node keeps working) **whose signer's organization is Valve's**: `O=Valve` in spike 0001, `O=Valve Corp.` since 2026, matched exactly. Servers get a copy of it. A run that only updated SteamCMD itself exits with code 7 and is simply run again.
- Runs under ConPTY (live output). Progress through a regex over ` Update state (0x61) downloading, progress: 9.44 (238319757 / 2524405728)` lines (`0x81` verifying, `0x3` reconfiguring), tolerant to format changes. Some messages are localized to the OS language, so parsing relies only on language-neutral lines (`Update state`, `Success!`, `ERROR!`) and exit codes.
- Retries with backoff for transient failures (3 attempts, 10 s then 30 s) — spike 0001 hit `ERROR! Failed to install app (Missing configuration)` (exit code 8) on the first attempt and the retry succeeded; a full disk (`Disk write failure`, `state is 0x202`) or an unavailable app (`No subscription`, `Invalid platform`) is not retried. A run that prints nothing for 10 minutes is killed and retried. Cancellation (`CancelOperationCommand`) terminates its Job; the operation completes as cancelled.
- Progress reaches the panel throttled (a new stage, a point of progress, or every 2 seconds); the panel keeps the latest in memory and writes it to the database only on stage changes or every 15 seconds.
- v1: `anonymous` only (CS2, CS:S and GMod allow it). Steam account login and Steam Guard: post-v1, with node-level encrypted credentials.

### Windows Firewall

Optional, decided by the machine's administrator in the agent's configuration (`Pulsar:ManageFirewall`, off by default; the agent announces it to the panel with the `node.firewall` capability). Before every start the agent replaces the server's inbound rules (`Pulsar <shortId> <port name> <udp|tcp>`, grouping `Pulsar`) with one per bound port and **declared** protocol, limited to the server's executable and, when the allocation is not every interface, to its address, through the firewall's COM API (`HNetCfg.FwPolicy2`), never `netsh`. Game ports declare UDP only, so the TCP side where RCON listens is never opened (spike 0001, F7: CS2 has no RCON brute-force protection). Rules of ports the server no longer has are removed at the next start; all are removed when the server is deleted. The firewall is never disabled and no generic rules are created.

## Agent restarts and `KILL_ON_JOB_CLOSE` (ADR-0006)

| | **KILL_ON_JOB_CLOSE (recommended for v1)** | Servers survive the agent |
|---|---|---|
| Orphans | Impossible: if the agent dies, the OS closes the Job handle and kills the tree | Possible |
| Console after an agent restart | N/A (everything restarts cleanly) | Lost: the ConPTY/pipes belonged to the dead agent; the game keeps writing into a broken pipe |
| Updating the agent | Stops the servers (to be scheduled) | No downtime |
| Complexity | Low | High: needs a *shim* process per server owning the Job and console, with IPC to the agent |

KILL_ON_JOB_CLOSE is recommended for v1 for reliability. `IGameProcess` allows a future implementation backed by a per-server *shim* (`containerd-shim` pattern) without changing the rest of the agent. An orderly service stop (`OnStop`) stops the servers gracefully (manifest steps) before exiting, within the time the SCM allows.

## Future limits (prepared, not implemented in v1)

The Job already exists per server, so adding limits is configuration, not redesign: `JOB_OBJECT_LIMIT_JOB_MEMORY`, `JobObjectCpuRateControlInformation` (hard cap or weights), `JobObjectNetRateControlInformation`, I/O priority.

## Tests

`Pulsar.TestGameServer` is a test executable driven by arguments: it prints output, reads stdin, spawns children and grandchildren, ignores `quit`, crashes with a given code, writes through the console API, tries to create a junction. `Pulsar.Agent.Windows.Tests` (Windows runners only) verifies:

- killing the Job leaves no process alive (grandchildren included);
- killing the test agent process kills its servers (KILL_ON_JOB_CLOSE);
- the child does not inherit unlisted handles;
- crash detection and exit codes;
- stop via command, Ctrl+C and timeout;
- the process runs as the expected account and cannot read another server's directory.

## Implementation (Phase 3)

- **Code.** `Pulsar.Agent.Core/Processes` (`IGameProcessManager`, `IGameProcess`, `IServerProvisioner`), `Pulsar.Agent.Windows/Processes` (`WindowsGameProcessManager`, `WindowsGameProcess`, `JobObject`, `ServerPaths`, `WindowsCommandLine`) and `Pulsar.Agent.Windows/Servers` (`WindowsServerAccounts`, `WindowsServerProvisioner`, `ServerWindowStation`).
- **Start sequence** as above: paths resolved under the server directory with no junction or link in them and the final path of the executable checked; Job (kill on close, die on unhandled exception, no breakaway, the UI restrictions listed) given through the job list attribute to a process created suspended (assigned before resuming if the attribute did not apply); pseudo console with null standard handles, or pipes with a handle list; `TEMP`/`TMP` in `<server>\.pulsar\temp`; reserved variables refused.
- **Account launches** log on with a fresh password (see "Isolation"), load the profile, take the environment from `CreateEnvironmentBlock`, start the game with the `DISABLE_MAX_PRIVILEGE` token and give it **its own window station and desktop**, open to SYSTEM, Administrators and the server's account (`Pulsar-<serverId>\Default`). The profile stays loaded while the process runs; provisioning logs the account on once, so the profile already exists at the first start (creating it took seconds on Windows Server 2025). A development agent (`--dev`) starts servers as the current user, without accounts or window stations.
- **Ctrl+C.** "Ignore Ctrl+C" is inherited by child processes. A parent started in a new process group (a test host, some service wrappers) passes it on, and then Ctrl+C never reaches a server; the agent clears it for itself (`SetConsoleCtrlHandler(NULL, FALSE)`) before starting servers.
- **Server directories.** `<ServersRoot>` (default `%SystemDrive%\PulsarServers`) is protected (SYSTEM and Administrators, Administrators as owner). Each `<ServersRoot>\<shortId>` adds Modify for the server's account and limits `OWNER RIGHTS` to Modify, so a server owns the files it creates but cannot change who may read them.
- **The agent writes into folders a server controls** (install steps, deletion) only through checks: install steps refuse paths through junctions or links and replace files instead of writing into them (an existing name could be a hard link to a system file); deletion removes links without following them. .NET's recursive delete would also not follow a junction, but it removes one through `DeleteVolumeMountPoint`, which needs elevation, so the agent walks the tree itself. Installs need the server offline, so none of its processes can swap a folder in between.
- **Agent restarts (ADR-0006).** Killing the agent kills its servers with their Jobs (checked by hand with a development agent: no process left). An orderly stop (service stop, update, reboot) stops the servers gracefully within 20 s and starts them again with the agent; after a crash of the agent, only auto-start servers start.
- **Verified:** `Pulsar.Agent.Windows.Tests` (pseudo console and pipes, argv round trip, Ctrl+C, exit codes, trees killed, no inherited handles, path checks, environment; accounts, rights, ACLs, profile and restricted token, and a server unable to read another one, as SYSTEM in CI), the production install check in Windows Sandbox and CI (the test game server as its own account in session 0 from the SYSTEM service), and the real-game check below.
- **Agent file access (Phase 4).** Writing configuration files, reading the game's log, copying SteamCMD: the agent opens files through `IServerFiles`, which never follows a final link (`FILE_FLAG_OPEN_REPARSE_POINT`) and checks the path the opened handle really has (`GetFinalPathNameByHandle`) against the server directory, level by level when creating folders. However a server swaps junctions, the handle the agent uses is inside its directory. Writes delete the old file and create a new one (`CREATE_NEW`), so a hard link never redirects them.
- **Real game (`scripts/sandbox/real-game`, `RealGameTests`).** A Counter-Strike: Source dedicated server, copied into a new server folder, started by `WindowsGameProcessManager` as its account from SYSTEM in Windows Sandbox (pseudo console, restricted token, private window station, Job with UI restrictions): it wrote its own `console.log` (`-condebug`) and reached `Server is hibernating` in about 2 s with two processes in its Job (srcds and the console host it creates), was still running 10 s later, and nothing was left after its tree was terminated. As in spike 0001, nothing reached the pseudo console: Source servers need `logfile+rcon` (Phase 4). GMod is checked the same way when its manifest is written.
