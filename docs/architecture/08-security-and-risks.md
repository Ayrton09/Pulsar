# 08 — Security model and main risks

> Status: **proposal under review**.

## Trust boundaries

```
[Internet / players] ──UDP/TCP──► game servers (per-server account, Job)
[Browser] ──HTTPS + cookie──► Panel ──► PostgreSQL
                                 ▲
[Agent (SYSTEM)] ──outbound WSS, PoP + signed commands──┘
[Plugins / mods / uploaded files] = UNTRUSTED code inside the game server
```

Explicit assumptions:

1. **The panel is the control plane.** Whoever controls the panel with administrator permissions controls the nodes *within the supported operations*. Pulsar limits what the panel can ask for, but cannot protect a node from a fully compromised panel.
2. **A game server runs untrusted code** (SourceMod/CounterStrikeSharp plugins, GMod Lua, uploaded DLLs). Anyone who can upload files and start a server can execute code **as that server's account**. This is inherent to game hosting; the goal is that this code cannot leave its box (account + ACL + Job).
3. The node's local administrator is fully trusted.

## Controls per layer

### Users and web

- ASP.NET Core Identity: password hashing (Identity's default PBKDF2), lockout (5 failures, 15 minutes), security stamp, TOTP 2FA (enforceable per role in settings). Recovery codes.
- Browser sessions: a cookie that lasts as long as the browser and slides for 12 hours while it is used, but never lasts more than 7 days from its sign-in however much it is used (`SessionLifetime`), so a copied one (a shared PC, malware) does not live on by being used. *Remember me (1.0.9):* a user who ticks "Remember me on this device" at sign-in (the choice goes with the second factor too: `rememberMe` in both requests) gets a persistent cookie that slides for 30 days and has no maximum age: it lasts until they sign out, as long as it is used at least every 30 days (it renews once half of that has passed). Residual, the user's choice: such a cookie, copied or left on a shared PC, works for as long as it keeps being used; it still ends with the user's security stamp (signing out anywhere, a password changed, the user disabled), checked at least every minute. Signing out renews the security stamp: every session of the user ends, a cookie copied before included (sessions are not told apart, so the user's other browsers sign in again). It counts only once the new stamp is stored: a change of the user saved meanwhile (a failed sign-in counted, an administrator's edit) makes its save fail on the user's concurrency stamp, so the user is read again and the stamp renewed on it, up to three times; if it still is not stored, nothing is signed out, this browser included, and the answer is `409 auth.sign_out_failed` (`SecurityStamps`). Disabling a user is refused the same way (`409 user.disable_failed`, the user stays enabled) rather than leave their sessions working.
- *Implemented in Phase 9:* two-factor authentication with any authenticator app (RFC 6238: HMAC-SHA1, 30-second steps, six digits, one step of drift either way). A code works once: the last accepted step is kept, so a code seen over someone's shoulder cannot be reused within its window. The authenticator key is encrypted with Data Protection and the ten recovery codes (about 47 random bits each) are kept as SHA-256 hashes; a recovery code works once. Wrong codes, of the app or recovery ones, count towards the lockout like wrong passwords, and a user disabled since the password step gets no session from either. A role can require it (the Administrator role too): until such a user sets it up, every endpoint but the session, logout and the setup itself answers `403 auth.two_factor_required`, and so does the live channel. Setting it up (a new authenticator key, which also ends the user's other sessions) needs the password, and turning it on needs a code from the app and the password (a stolen session alone cannot reset the key and end the owner's sessions, nor turn it on, lock the owner out and keep the recovery codes); turning it on renews the security stamp (other sessions end); turning it off needs the password and is refused while a role requires it; an administrator who may manage the user can turn it off for them (a lost phone), which ends their sessions. All of it is audited.
- Confirming the current password (changing it, setting up, turning on or off two-factor authentication, new recovery codes) counts wrong guesses towards the lockout, so a stolen session cannot be used to guess the password. Locked-out and disabled accounts take as long to answer as wrong passwords (Identity answers them before hashing; the panel hashes anyway). An account's credential checks run one at a time (`SignInLocks`: the password or code check, the failed-count update and the audit entry of the sign-in, its second step, SFTP's password, code and key checks, and a password or code confirmation), so parallel guesses each count and the fifth locks the account, and each attempt keeps its audit entry, saved apart from the user row; the user row's concurrency stamp would otherwise let only one of parallel updates through. The lock lives in the panel's process (the panel is one process; several panels on one database would need a lock in the database); it is keyed by the normalized user name, names of no user included, so parallel attempts wait the same whether the user exists or not. An update of the user refused because something else (an administrator's edit) saved it meanwhile is applied again on the row as it is now (Identity's own update within the browser's sign-in is not retried: that attempt alone goes uncounted). Residual risk: anyone can lock an account for 15 minutes with five wrong passwords (the rate limit slows it down; locking out the only administrator is possible).
- Protected initial setup: when no users exist, `/setup` requires a **single-use token printed in the panel log/console** at startup (prevents someone else on the network from creating the first admin before you). Automated installations can provide it instead with `InitialSetup:Token` (at least 32 characters; then it is never printed).
- **HTTPS by default.** Cookies are `__Host-` prefixed, `HttpOnly; Secure; SameSite=Strict`; HSTS and HTTP→HTTPS redirection are on, and API calls (and downloads, T37) over plain HTTP get `400 transport.https_required`. TLS can terminate at Kestrel or at a reverse proxy: `X-Forwarded-For/Proto` are read only from the proxies `Security:TrustedProxies` names (a proxy on the panel's own machine too, as `127.0.0.1`): any other client, a process on that machine included (a game server's account), is the address of its connection, which rate limits and the audit log use. Plain HTTP is only possible with the explicit opt-in `Security:AllowInsecureHttp=true` (development, trusted networks): cookies lose `Secure` and the prefix, the panel logs a warning at startup and the UI shows a permanent banner.
- Antiforgery token (readable `__Host-pulsar-xsrf` cookie, `X-XSRF-TOKEN` header) on every state-changing API call.
- Headers on every response, errors included (set when the response starts, after the exception handler has replaced it): strict CSP (`default-src 'self'`, no inline scripts; inline `<style>` elements only, because the dialogs' scroll lock injects one at runtime — style attributes stay blocked, images from the panel and, while the game artwork is on, Steam's store CDN and Minecraft's site only (T41; with it off, or until the panel has read the setting, neither), `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, a restrictive `Permissions-Policy` and `Cross-Origin-Opener-Policy: same-origin`. HTML pages also carry `Cache-Control: no-cache` (revalidated by ETag), so a page opened by navigating to it carries the current CSP; one the browser restores from its history (Back) keeps the policy it had, like a page left open. The end-to-end suite fails on any CSP violation.
- Users change their own profile and password (`/account`); a password change ends the user's other sessions.
- *The panel's certificate (LAN):* `GET /api/v1/panel/certificate` (its SHA-256, names and addresses, expiry, whether it is self-signed and a web server's own) and `/download` (`application/pkix-cert`, `pulsar-panel.cer` as an attachment, `no-store`, `nosniff`) give any signed-in user, without a permission, the certificate Kestrel presented on that very connection, which every TLS client receives anyway, so the browsers of a home network can trust the installer's self-signed one once (the Account page's **Panel certificate**, docs/guides/install.md "Trusting the panel's certificate"); none (`404 panel.certificate_unavailable`) over plain HTTP, HTTP/3 or a request a forwarding proxy marked, the detection node codes use (T36; `PanelCertificateKestrelTests`). Over a connection the browser does not trust yet, the page could be another machine's, so it says to compare the downloaded file's or the browser's SHA-256 with the one the installer showed on the panel's PC, never the page's alone, and gives install steps only for a self-signed certificate that cannot issue others and is for server authentication alone.
- Built-in rate limiting (`Microsoft.AspNetCore.RateLimiting`) on login and its second step, setup, password confirmations, enrollment and the agent challenge; the anonymous routes that read the database (the session check and readiness) take at most 300 requests a minute from one address (`RateLimiting:Auth:AnonymousPermitLimit`), so that a flood does not take the database's connections from sign-ins. A failed password check, in the browser and over SFTP, takes at least 0.4 s once it is the account's turn (`RateLimiting:Auth:FailedPasswordCheckTime`), whatever failed: an unknown name, a locked or disabled account and a wrong password cost different database work, which the answer's time would otherwise tell. Routes that cost more than a database read take at most 60 requests a minute from one user (`RateLimiting:Auth:LookupPermitLimit`, by address without one): Workshop lookups, each of which asks Steam with the panel's address (and key), the mod catalog's searches, versions, update checks, installs and updates (1.0.9), each of which asks Modrinth with the panel's address (300 a minute; the whole panel also keeps under 240 a minute of Modrinth's and 120 of CurseForge's, the administrator's key being everyone's, past which the catalogs answer busy for the rest of the minute; several users together can still spend that, residual), and the template preview and import, which check up to 256 KiB of manifest.
- *Public IP certificate:* for a panel on a static public IP, a Let's Encrypt certificate for that address (off by default; `settings.manage`, audited; docs/guides/install.md, "Access from the internet with your public IP"), so browsers on the internet reach it without a warning. The panel's own ACME client (RFC 8555, no package) talks only to the directory's host over HTTPS, follows no redirects and reads every answer strictly; port 80 answers only Let's Encrypt's http-01 check, and only while the feature is on; the certificate is served on the browsers' endpoints, per connection, only to connections from the internet; nodes never pin it (T40).
- Request bodies are limited to 2 MiB (Kestrel's default is 30 MB): the endpoints that take files (uploads, the agent's transfers) raise it for themselves.
- Resource authorization on **every** endpoint (enforced by a test) and hub method; IDs of other users' resources → 404 (in the browser hub: `null`).
- The browser hub (`/hubs/panel`) requires a signed-in user, WebSockets only, and refuses an `Origin` other than the panel's own host (cross-site WebSocket hijacking; SameSite cookies are per site, not per origin). Permissions are checked when a page starts watching. A WebSocket outlives the cookie checks of ordinary requests, so (*Phase 9*) the panel closes a user's live connections when they sign out (which ends all of their sessions, other browsers' too), are disabled or deleted, their password or two-factor setup changes or their roles change, and closes every connection when a role changes; connections reopen on their own and are checked again, and a connection only opens for a session whose security stamp is still current (checked at once, not at the cookie's next one-minute check). A tab whose live channel cannot reconnect reloads its session, so a session that ended (expired, signed out elsewhere) takes it to the sign-in page. A file transfer is a request that lasts as long as bytes move (Kestrel's least rate is 240 bytes a second), so it does not outlive what allowed it either: the panel ends a user's running transfers with their live connections (sign-out, disabling, deletion, a new password or two-factor setup, other roles, and every user's when a role changes), a transfer started with an API key when that key is revoked, and any transfer once it has lasted its size at 64 KiB/s (five minutes at least); both of its requests stop, so the node never gets the rest of an upload (`TransferRevocationTests`, `FileTransfersTests`).
- RBAC anti-escalation (doc 02).
- Names people give what others see listed and shown as they are (servers, backups, schedules, API keys) refuse control characters, format characters (zero-width spaces, direction overrides and isolates, tag characters) and line and paragraph separators, so one cannot be made to read like another; the zero-width joiner and non-joiner and the left-to-right and right-to-left marks stay allowed (emoji sequences, Persian, Hebrew and Arabic names). Node and role names refuse those too (T2). Checked when a name is given or changed; names saved before stay as they are.
- *Phase 11:* roles given on one node or one server. The gate resolves the server or node of the route and checks the permission there, answering `404` for what the user cannot see; lists are filtered. Live notices follow the same rule: watchers with global roles share the `servers` and `nodes` groups, others join groups per node and per server they see, and the panel sends each server's and node's notices and usage to those groups only, so nobody learns the ids of servers they cannot see. Changing a user's assignments closes their live connections, which reopen with what they may see now.

### Panel ↔ Agent

- Mandatory TLS: the agent rejects `http://` panel addresses other than loopback ones (a panel on the same machine; that traffic never leaves it).
- Per-node identity with a non-exportable key (TPM when available), proof of possession through a challenge, an opaque 15-minute session token (the panel keeps only its hash), immediate revocation, rotation.
- *Phase 16:* optionally, the node key as TLS client certificate on a separate agents' port, with the session bound to it, so a copied session token is useless without the key; a switch then turns agents without one away from the main endpoint (docs/architecture/03, "Client certificates"). The agents' port takes any client certificate before a single byte of HTTP, so the TLS layer builds its chain only from what the handshake carried and the machine's stores: nothing is fetched and no revocation is checked; it holds a bounded number of connections at once: those not signed in per address, per network and for 30 seconds, those signed in per node and for their session (T31). The agent builds the panel's certificate chain the same way (T31).
- A rotation registers a new key only with the current key's signature over it, for that session: a copied session token cannot replace the node's key (T30). A key registered and not signed in with within 24 hours expires. The agent uses a session only when the sign-in's answer carries the panel's signed grant for that credential, session and the nonce it sent, so whatever answers a sign-in on the way can neither make it switch or delete a key the panel still needs nor hand it a session in which recorded commands would run again (T4, T30, T34).
- What an agent says is bounded where it enters the panel: the answers it reads (64 KiB), the nonce it signs and the token it keeps on its side; error codes, stages, drives, messages, details and what it says about its machine on the panel's (T32).
- Commands signed by the panel, pinned panel key, anti-replay (a session the panel granted + sequence + expiry judged on the panel's clock as that grant says it), strong validation before execution.
- There is no shell command. The executable always comes from the manifest and the server directory.
- *Phase 18:* **Add node** also shows a node code for `PulsarAgentSetup.exe` (doc 03, "Node code"): the token, the pinned panel key's fingerprint, the origin the administrator reached the panel by and the SHA-256 of the TLS certificate the panel served that request, so a node's agent pins the panel's certificate (it accepts that one and no other; no certificate store of the node is changed) without anyone copying `panel.cer`. It is as secret as the token (T36). The setup itself is downloadable from the panel without signing in, and the dialog shows its SHA-256 (T37).
- *Public IP certificate:* the agents' endpoint always serves the panel's own certificate, and so does the main endpoint to every connection from a local address and to every client that names a host (SNI), so agents on the local network or reaching the panel by a name see no change. An agent's pin is never widened: an agent pinned to the panel's own certificate that reaches the main endpoint by the public IP from the internet gets the Let's Encrypt certificate and refuses it (it fails closed, offline, rather than accept any certificate the web PKI vouches for). A node code made over the Let's Encrypt certificate names none (`cert: null`): such a node checks it as any site's, against its trusted roots, and Let's Encrypt replaces it every few days, so a pin would break at every renewal (T40).

### Node

- Agent without listening ports.
- Per-server accounts without interactive/RDP/network logon; the game runs with a restricted token without privileges (no `SeShutdownPrivilege`). The token still contains `BUILTIN\Users`, so isolation comes from ACLs, not group membership. Residual risk: files a server writes into Users-writable system locations (`C:\ProgramData`, `C:\Users\Public`) are readable by the other servers.
- ACLs: each server only sees its directory; agent directories (`%ProgramData%\Pulsar\Agent`) are SYSTEM/Administrators only.
- Jobs with UI restrictions and no breakaway.
- Explicit inherited handles (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`).
- RCON (Source servers in `logfile+rcon` mode) is a credential exposed on the game's TCP port: the agent generates and keeps a long random password per server (T18).
- SteamCMD runs as the server's own account, from the server's own copy (doc 06): it can write only where its server can.
- Processes a server's account starts outside its Job (scheduled tasks, WMI) are killed at every start, stop, install and deletion (T20).
- **The pseudo console's host.** A game in `pty` mode (and SteamCMD, which always is) gets its console from `conhost.exe`, which `CreatePseudoConsole` starts with the caller's token: the server's host (doc 06, "Server hosts") for a game, the agent for SteamCMD, SYSTEM for the service either way. conhost reads and parses everything the game writes (VT sequences), so a flaw in it that the game's output could exploit would run code as SYSTEM. To make that worth less, each host removes from its own token, for good and before anything starts, every privilege it never uses (`HostPrivileges`: TCB, creating tokens, debugging, drivers, ownership, security log, relabel, volumes, firmware, shutdown, time…). **Residual:** the host keeps what starting its game takes (assigning the game's token and quotas, and backup and restore, which loading and unloading its profile need, and with which a file can be read or written whatever its ACL), and it is still SYSTEM by its groups; SteamCMD's conhost runs with the agent's full token. A helper running as the server's account that would create the pseudo console itself (as OpenSSH's does) removes this, and is left for later.
- Left as they are, on purpose (audit WL2, CL6):
  - `Pulsar:TestGameDirectory` (the test game's files, doc 04) is honoured in every build, Release included: CI's agent-install job runs a Release production service with it, and for the service only administrators can set it (the settings file in the agent's install folder, which `ServiceBinarySecurity` checks only administrators can modify, or the machine's environment), so it gives nobody more than they already have.
  - A SteamCMD beta password (`-betapassword`) goes on SteamCMD's command line, where processes of the same account can read it: SteamCMD runs as the server's own account (doc 06), which could read a script file holding it just the same (as could administrators), so a file would protect nothing more.

### File manager (critical)

The agent's file manager runs in a SYSTEM process operating on directories **writable by untrusted code**. Defense in depth:

1. **Lexical validation** of the received relative path: reject roots, drive letters (`C:`), UNC (`\\server`), device paths (`\\?\`, `\\.\`), `..`, `:` (alternate data streams), reserved names (`CON`, `NUL`, `AUX`, `PRN`, `COM1-9`, `LPT1-9`, also with an extension), trailing dots/spaces, control characters, excessive lengths.
2. **Normalization** with `Path.GetFullPath(Path.Join(root, rel))` and a prefix check including the trailing separator (`C:\srv\a\` must not accept `C:\srv\ab`) using an ordinal case-insensitive comparison.
3. **Reparse points**: game code can create a *junction* (no privileges required) pointing at `C:\`. Every operation first opens a handle and checks with `GetFinalPathNameByHandle` that the real target is still inside the root (and not in the Steam login lent to SteamCMD, `.pulsar\steamcmd\config`, whatever name or junction led there), then operates **on that handle** (no TOCTOU between check and use). Enumeration does not follow reparse points; they are shown as non-navigable links. The agent's own reads and deletions inside server directories (`IServerFiles`: install steps, SteamCMD's copy, the lent Steam login) open the path level by level through handles, each folder checked before the next is opened, never with one `CreateFile` on the whole path (a junction on the way is refused itself, and nothing below it is opened with the agent's rights); the ACL rules the agent sets on its own folders go through a handle opened without following a link as well, so a link that replaced a folder after it was checked never receives them.
4. **Impersonation**: file operations run impersonating the server account (`WindowsIdentity.RunImpersonated` with the account token). Even if layers 1–3 failed, the OS enforces that account's ACLs: it cannot read outside its directory. This also neutralizes hard links to foreign files (the ACL lives on the file, not on the link). The logon token of an account is kept for a minute after its last use, so browsing a folder does not log it on at every click; a timer closes the ones that went idle (not only the next call), and deleting the account drops its token at once (one in use is closed when its operation ends). A server without an account of its own (a development agent's, which acts as itself) gets nothing done on any other agent: there the agent's account is SYSTEM, so the file manager refuses it (`files.access_denied`), as the process manager refuses to start it.
5. Limits: inline read/edit size (1 MiB), configurable upload size, and a free-space floor rather than per-server quotas (see "Disk space" below).
6. Atomic writes (temp file + rename) and auditing of deletions/renames/uploads. Once the rename has put the file in place, nothing that fails afterwards makes the upload delete it. **Known race:** an edit that carries the version it was based on checks it and then renames over the file as two steps (NTFS has no compare-and-swap rename, and moving the target aside to check it by handle would let the game recreate or keep writing to the moved file); a write by the game that lands in the few microseconds between them is overwritten, the same loss as one just after the rename. The check catches what changed while the editor was open, not a write racing the commit, so files a running game rewrites (its configuration, say) are best edited with the server stopped.

Path traversal tests: an extensive table of malicious inputs (more than 50 Windows-specific cases) + integration tests with real junctions, symlinks and hard links.

*Implemented in Phase 6.* Layer 1 is `ServerFilePath` (Pulsar.Contracts), checked by the panel and again by the agent: forward slashes only, no roots, drives, UNC or device paths, no `..`/`.`/empty segments, no `:`, no reserved device names (with or without an extension, `COM0-9`, `LPT0-9` and their superscript forms included), no trailing dots or spaces, no leading spaces, no control characters, wildcards or broken UTF-16, segments up to 255 characters, paths up to 1,024 (`ServerFilePathTests`: 79 refused inputs and 47 plain ones). Names may contain any printable Unicode, format characters included (zero-width joiners, direction marks, soft hyphens): they are legitimate in many scripts, and refusing them would make such files impossible to rename or delete and leave them out of backups. Instead the web file manager shows invisible formatting characters visibly, so a name such as `invoice` + U+202E + `fdp.exe` cannot read as `invoiceexe.pdf`. Layers 2–4 are described in doc 06 ("File manager"); the inline limit is 1 MiB, uploads are limited by `Files:MaxUploadBytes` (1 GiB by default), writes are atomic and changes and downloads are audited. `WindowsServerFileManagerTests` plant real junctions (at the top and deeper in a path, to the outside and inside), symbolic links to files and folders, and hard links to a file outside, and check that nothing outside is ever read, written, renamed or deleted; as SYSTEM in CI, the same checks run as a server's account, where another server's file stays unreadable even through a hard link. A shared contract (`ServerFileManagerContract`) runs the same behavior tests on the Windows implementation and on the portable one the in-process tests use.

**What the node says about files is checked when it reaches the panel** (`AgentInput`, doc 03, "Limits and robustness"; a compromised node is not trusted with it). A listing keeps at most 2,000 entries, and only the ones whose name is one segment `ServerFilePath` accepts (format characters pass, as above), whose kind is known and whose size is not negative. The rest are not rewritten, which would leave a name the user cannot open: they are left out and *counted* (`skipped` in the listing, shown by the web as "N entries with names Pulsar cannot open are not shown", apart from "only the first N entries are shown", which is the 2,000 cap, `truncated`). A game can create names Windows allows through extended paths but the panel cannot address (`trailing.`, `nul.txt`, a lone surrogate, which JSON would turn into U+FFFD, a name the panel would accept and open as another file). The agent applies the same rule (`ServerFileRules.Listing`, both file managers) *before* its 2,000-entry cap and counts those names in the listing's `Skipped`, so thousands of them cannot push the real files out of the listing and a broken name never travels; the panel adds the count of what it still refuses itself to the agent's (clamped to 0 to 1,000,000: it is only a number to show). So a game can hide a file from the file manager this way, but the count tells the user something is there, and backups report such names (`Refused`) instead of dropping them. A file the node answers with (an editor or download opening, a transfer's result) must have such a name and a version of the shape the agent makes (`FileVersion`: two lowercase hexadecimal numbers joined by a dash); the panel sends the version back as the `ETag` and reads it again from `If-Match`, so a quote, a control character or a non-ASCII character could not break the header or inject another one. Otherwise the panel treats the answer as none (a rejected command) or the transfer as failed. A download is named by the path the user asked for, never by the node's answer, and the browser's `Content-Disposition` name has each control, format and separator character replaced by `_` (a download dialog cannot show a direction override, so `update` + U+202E + `fdp.exe` would read as another file). The agent reads a file's last-write time without failing on one beyond year 9999 (any account can set it on its own files, and `DateTime` cannot hold it): it reads as the latest time there is, so listings, backups, restores, overwrites and deletes keep working (`AFileWhoseTimeIsBeyondYear9999…` in the contract).

*Zips (1.0.11; doc 03, "Archives").* Zipping and unzipping are the file manager too: the agent reads and writes through the same handles, as the server's account, so a zip can hold only what the account can read and an unzip can write only where it can, never through a link and never in `.pulsar`. A zip is untrusted input (a game, a plugin or a player may have made it): its end record is read first, so one claiming more than 200,000 entries or a list of entries over 48 MiB is refused before .NET loads that list into the agent's memory, and every entry is checked before anything is written (a relative path below the destination, `\` read as `/`, no `..`, drives, streams, device names or `.pulsar`, each path once by any case, not a file and a folder at once, at most 200,000 entries, what they declare fitting on the drive with 1 GiB to spare), and an existing file is replaced only when asked. Against zip bombs, an entry is written only up to the size it declares and its CRC-32 is checked before the file is put in place (.NET's reader checks neither the CRC nor reads past the declared size, so a bomb would otherwise be cut silently, and a damaged entry written as if whole); a zip being made is bounded by what was selected and appears complete or not at all.

*Phase 17 (SFTP) adds to the agent protocol* (doc 03, "SFTP additions"), behind its own capability so an older agent never gets a field it would ignore: paged listings, stat, downloads from an offset, streamed and appended uploads, renames that replace and setting a modification time. Each goes through the same path rules on both sides, the same handle checks as the server's account, and the same `Busy` and `.pulsar` refusals as the other changes. Pages are checked again by the panel (only names after the cursor and up to the next one, each once; a cursor that does not move ends the listing), so a node cannot make the panel page forever or slip another folder's names in. A rename replaces only a file, by a file, never a directory or link. A streamed upload is bounded by the upload limit and by the time that limit takes at 64 KiB/s, and only its clean end commits it (the panel aborts the agent's request on any failure), so a dropped connection never leaves a cut-off file in place of the original. An append is the exception by design: it writes in place, so an interrupted one leaves what arrived (that is what a resumed upload continues from), and it never truncates or replaces what was there.

*Phase 17: the panel's SFTP server* (docs/guides/sftp.md, T35) is a second door to the same file manager, not a new trust: it runs in the panel, signs users in with the browser's rules (or with an SSH key they added, T43), checks the permissions at every request with the web's evaluator and turns each request into a `ServerFiles` call, so the agent still checks every path and acts as the server's account, and the panel still audits. It never touches a node's disk itself.

### Backups and restore

- Creation: does not follow reparse points (otherwise a junction to `C:\Users` would exfiltrate data into the archive); reads impersonating the server account.
- Restore: every archive entry goes through the same validator (anti zip-slip), no reparse points are created, writes are impersonated, only while the server is `Offline`.
- Backup downloads require `server.backups.view` and go through a transfer ticket.

*Implemented in Phase 7.* Creation walks the server directory through the file manager (links are listed, never entered) and reads every file through it, so on Windows the server's own account opens them: a hard link to another server's file is left out (counted as skipped), an entry no path can name (a trailing dot or a device name created through `\\?\` paths) is left out the same way, and the agent logs its name (control characters shown as `?`), a junction to `C:\Users` adds nothing. The archives are written by the agent into its own directory (SYSTEM and Administrators only), out of every server's reach; each one's SHA-256 is kept by the panel. A restore first checks that SHA-256, then checks every entry before writing anything: each name must be a plain `ServerFilePath` (no `..`, roots, drives, `\`, `:` streams, device names…), outside Pulsar's own `.pulsar` folder and not repeated (ignoring case; a folder with per-directory case sensitivity can hold `Readme.txt` and `readme.txt`, so a backup keeps the first in ordinal order and counts the other as skipped, logging it, instead of making an archive no restore would accept); any other archive is refused whole (`backups.corrupt`). A first segment shaped like an 8.3 short name (`PULSAR~1`) is written only as a folder of that very name, one the server has or the restore creates: when the name leads to another folder (`.pulsar`, on volumes that keep short names), the file manager refuses to create it and those entries are left out, the restore failing with `files.exists` once the rest is written. Entries are written through the file manager as the server's account, one temporary file and one rename each, never through a link (a junction planted where a folder of the backup goes stops the restore), and only with the server stopped. *Remote copies (Phase 10):* the node uploads the archive itself (the panel never sees backup bytes) and, when it fetches one back, checks the SHA-256 the panel recorded before using it, so a copy changed in the bucket is refused. The panel sends the archive's size with the restore (`RestoreBackupCommand.SizeBytes`) and the download stops, with `backups.corrupt`, as soon as the storage sends more than that (or announces more), so a bucket serving a huge object cannot fill the node's disk before the hash is checked; an older panel sends no size and the download has no limit. The storage's keys travel inside the signed command over the agent's TLS connection and are dropped after use; anyone with administrator rights on a node can still see them while a backup runs, so the guide recommends keys scoped to the one bucket. The agent reaches the storage over HTTPS; plain HTTP is accepted only to a loopback, private or link-local address (127/8, 10/8, 172.16/12, 192.168/16, 169.254/16, ::1, fc00::/7, fe80::/10: storage on the node or on the owner's LAN, the way AMP users keep a NAS at home), so backup bytes and signed requests never cross the internet in clear. The same rule holds on both sides: the panel refuses an `http://` endpoint whose host is a public IP literal (`backup_storage.endpoint_needs_https`) and accepts a host name, which it cannot resolve as the node would; the node resolves the name once per client, refuses it if any address is public (`RemoteFailed`, saying which), and connects only to the addresses it checked, so a later DNS answer cannot redirect it. `BackupStorageTests` and `RemoteBackupStoreTests` cover both. `BackupStoreTests` (ten hostile entry names and more), `WindowsServerFileManagerTests` (junctions to the outside, as the developer and as a server's account in CI) and `ServerBackupTests` (the panel and the agent core end to end) cover it. *Snapshots, saves and clean restores (Phase 15):* a running game's files are read from a volume snapshot through the same file manager, still as the server's account, so a snapshot gives the account nothing it could not read live (a hard link keeps its target's ACL; links are listed, never followed; final paths are compared by device name); the snapshot is non-persistent, never exposed as a drive or share, and deleted when the backup has read it (Windows deletes it with the agent's process otherwise). The save commands are console commands from the template's `backup.save`, which only `template.manage` can import; the import preview does not list them (its capability summary has no console commands) and, for a new version of a template, only names `backup` among the sections that changed, so whoever imports a template must read that section. They go through the console's own checks; the record of a paused save lives in the agent's state directory (SYSTEM and Administrators only). A clean restore deletes, as the server's account, only files below the server directory that the backup rules it was made with select (recorded in the backup; the template's current ones for an older backup), after the archive's hash and entries were checked; links, Pulsar's own files and everything outside the rules stay. The panel refuses it for a backup that left files out and for agents that do not announce it.

### Disk space

A node's drive is shared by all its servers and their backups, and a full one stops every game on it. There are no per-server quotas (NTFS quotas are per user and volume, and a game cannot be told to stay within one); instead the panel keeps a floor and bounds what it adds itself:

- **Floor.** The panel refuses a backup (`server.backups.create`, scheduled ones too) when the drive of the node's backups folder has less than 5 % or 2 GB free, and an upload (browser or SFTP) that would leave the servers' drive under that floor (`node.disk_low`, HTTP 507). It goes by the free space the agent reported last (every 15 s), so a few uploads at once can still go past it by their size. The browser's editor saves (1 MiB at most) are not held back: fixing a configuration on a nearly full drive must stay possible, and deletions always are.
- **Retention.** A new server keeps its last 7 backups (locked ones besides); an owner can raise the limit or keep them all.
- **Frequency.** Scheduled backups are at least 15 minutes apart (`schedules.backup_too_often`), checked when the task is saved over the occurrences of the next 32 days (schedules repeat within a month, but for a few dates of the year).
- **Residual.** A game, a plugin or a mod writing to its own folder is not stopped by any of this, nor are installs, updates and restores (their size is the game's): the node notification for a drive nearly full tells the owner. Servers created before this rule keep the backup limit they had (none, unless set).

### Game databases

*Phase 13.* Database hosts are panel settings (`settings.manage`): their account may create databases and users, so it is a secret of the panel's, checked by connecting before a host is saved. An edit that leaves the password empty keeps the saved one only while the address, port and user name stay the same: it is never sent to another server (a settings manager pointing a host at their own machine must type the password). A server's databases are named `s{short id}_{suffix}`: the suffix is the owner's, 1 to 20 lowercase letters, digits and underscores, checked by the domain and again by the MySQL client before it is quoted into the statement (DDL takes no parameters); passwords are 24 random letters and digits. Each database gets a user of the same name with `ALL PRIVILEGES` on it alone: `_` is a wildcard in a grant's database name, so the grant escapes it (`s…\_main`), or the user of `s…_main` could create `s…1main`, a database Pulsar does not track and that no limit counts. Creating one never adopts a database that already exists, and removes what it made when any later step fails, a request given up included; the server's limit is checked with its row locked, and the row goes again whatever stopped the creation. A server's deletion drops its databases with its row locked, and a creation checks under that lock, once the host made the database, that its row is still there: a database the host was still creating when the deletion completed is dropped again, never left untracked nor handed to the deleted server's owner. A database's password rotations (and its deletion) take turns, its row locked from the host's change to the save, so the host and the panel always keep the same password. Deleting a server drops its databases on their hosts when its node confirms the deletion, before the row goes; a host that cannot be reached does not hold the deletion up (it is tried once per host, not once per database: each attempt may wait 15 s for a connection), and the audit log names the database left behind with a reason code (`database_host.password_unreadable`, `database.host_unreachable`: `audit.view` holders are not told what the host said, which names the panel's account there and the host's address; the panel's log has it). Reading a password is audited (`server.database_password_viewed`, never the password), and the answers that carry one (create, rotate, read) are sent with `Cache-Control: no-store`. What a host says when it refuses (its account's name, the panel's address) reaches settings managers only, when they save or test a host; a server's managers get `database.host_unreachable` and the panel's log has the detail. Connections use no pooling and 15-second timeouts, and TLS when the server offers it (`SslMode=Preferred`), which falls back to plain text, the panel account's password included, when it does not, and does not check the certificate. A host may require TLS (`SslMode=Required`: never plain text, but the certificate is still not checked, as home and LAN servers use self-signed ones); a new host requires it by default unless its address is localhost or a loopback, private or link-local address (the rule backup storages follow for plain HTTP); an edit that does not say keeps the choice, except that a host moved from the local network to a public address starts requiring TLS; hosts that existed before the setting (migration `DatabaseHostRequireTls`) keep the plain-text fallback until a settings manager changes it. A database server reached over the internet should require TLS, or sit behind a VPN or tunnel.

### Scheduled tasks

*Implemented in Phase 8.* Tasks run in the panel as the schedule: each action goes through the same service a user's request does, so its rules and audit apply, recorded with actor type `schedule`, the task's name and the run's id as correlation id. A task does later what its author set up, without them, so setting one up (creating, changing, running it now) needs the permission to do its action besides `server.schedules.edit` (`server.restart`, `server.backups.create`, `server.install` for updates, `server.console.write` for commands…), and changing one also needs the permission for the action it had: scheduling cannot be used to do what the user could not. Runs do not check their author again (a task belongs to its server, and whoever can edit schedules can disable it): taking a user's rights away does not stop the tasks they made. Scheduled commands are kept in clear and shown to whoever can see the server's schedules, so commands starting with one of the game's sensitive prefixes (`rcon_password`…) are refused. Due tasks are taken with `FOR UPDATE SKIP LOCKED`, so two panels never run one twice (`ServerScheduleTests` runs three passes at once).

### Game updates

*Implemented in 1.0.9.* A check runs the server's own SteamCMD copy as the server's account (anonymously, never with a Steam account), beside the game or not, and reads files of the server's folder: all of it is the server account's, so a check decides only what that server shows and, when it installs updates by itself, when it updates (a plugin of the game could make every check find a new build: automatic updates of a server start at most once an hour, and that account can stop its own game anyway). An install never runs beside a check (a lock on the copy), a check asked by hand is not sent again within a minute or while one is on its way (each one signs in to Steam, and a node runs two at a time), and an agent reports a check that could not read the server's files without their paths. The panel takes an answer only to a question it stored before asking, keeps short printable text of it, and notifies a server's updates at most once an hour, so a node cannot flood the channels or speak for a server it was not asked about. Installing updates by itself stops and starts the server and warns its players through the console: setting it needs the permissions it uses (`server.install`, `server.stop`, `server.start`, `server.console.write` to warn), and runs are audited as the system. As with scheduled tasks, its author's rights are checked when it is set, not at each update: taking them away does not turn it off (whoever can update the server can). Cancelling an automatic update (`server.install`) cancels the update it started and starts the server again if it was running, so it never leaves the server stopped. A warning's text is the server's settings', limited to letters, digits, spaces and a few marks before it reaches the game's broadcast command, so it can never end that command or start another (doc 04, "Commands").

*Template updates (1.0.10).* A newer template version comes from the panel's own templates (bundled, or imported with `template.manage`), never from a node. Servers are moved by themselves only to versions a Pulsar update brought (bundled, not pre-releases): an imported version is shown and notified, and each server's managers move to it by hand after reviewing it, so whoever imports one cannot get it run on every server that follows its templates (T9). Before anyone is warned or stopped, the move's own checks run on a copy nothing saves (the node reads the version, a Steam account if it needs one, the values and ports it would have); a move they refuse is not tried by itself again, and is notified. Moving to it by itself is the manual upgrade done as the game updates, with the same rights checked when it is set and the same hourly limit. Only the template updates' sequences can carry the move's step (scheduled tasks are refused, `schedules.steps_invalid`). A pass that meets a server whose stored template no longer passes the panel's checks skips that server, and the game updates' pass runs apart from the sequence runner, so neither stops the other. Residual: a move whose install fails after the switch (a download that does not verify, the node refusing) leaves the server on the new version, not installed, until someone installs it again from its page; the failure is notified.

### Player actions

*Implemented in 1.0.11.* Kick, ban, whitelist and admins are the game's own commands from its template (doc 04, "Players"), sent through its console with `server.players.manage`, audited as `server.player_action` (the action and the player) instead of a console command. A player's name is never cleaned into another: anything but letters, digits, `_ - .` (and single spaces where the template allows them), or a name starting with `-`, is refused, so a name typed in the panel or listed by the game's query cannot end the command, start another, pass an option, or select everyone (Minecraft's `@a`); the card offers no buttons for a listed name the panel would send changed (spaces around it). Spaces are the template's to allow (`spaces`), only where the command's arguments do not end at one: a template that allows them without quoting the name could get extra arguments from a player's chosen name (a reason, a duration), never another command. Making a player the game's admin, or taking it away, also needs `server.console.write`: an admin runs the game's commands in game, which is as much as the console. The lists (banned, whitelist, admins) are read from files of the server's folder, which its game (and so its players and plugins) writes: at most 256 KiB, parsed as JSON with a depth limit, only short names without control characters kept, at most 1,000, shown as text, invisible characters as their code (as the file manager's names); a list the panel cannot read says so without failing the others. Reading them is not audited, as opening a file in the editor is not.

### Notifications

*Implemented in Phase 10.* The panel posts only to Discord's own webhook addresses (`https://discord.com/api/webhooks/{id}/{token}` and its `discordapp.com`, `ptb.` and `canary.` hosts, default port, no user info), checked when saved and again before every post, and its client follows no redirects: a channel cannot be used to make the panel call a machine inside its network. Messages allow no mentions (`allowed_mentions` empty), so a server name cannot ping `@everyone`. The webhook client logs no URLs (the token is in the path). Email goes through the SMTP server an administrator sets (`settings.manage`); STARTTLS is required when chosen and certificates are checked; signing in needs STARTTLS or TLS (no encryption only for a server on the panel's own machine), and the saved password is kept only while the server and the user name stay the same (it is never sent to another server); addresses are plain addresses (no display names or lists, so nothing can add headers). Messages are written in the same transaction as the event that raised them (an outbox) and sent by the panel with retries; what they carry (server, node and task names, exit codes, an error message) goes to whoever the channels name. `settings.manage` is a global permission over every server and node in this respect: its holders choose the channels (one with no server list is told about every server) and see the delivery history of all of them, servers and nodes they could not otherwise see included. Give it only to those who may know about every server.

### Manifests

Privileged import, closed steps, time-bounded regexes, typed variables, argv without a shell, per-format configuration encoders (doc 04). 1.0.12: the `xml` format reads files with DTDs prohibited and no resolver (no entity expansion, no fetch); `userProfile` and log file patterns only as paths inside the server's folder (with `userProfile`, what the game keeps in its AppData, its own logins and its plugins' settings among them, is in the server's folder, so whoever has the server's file rights sees it and backups take it, as the rest of the folder); the agent alone sets `DOTNET_ROOT` (manifests still cannot name `DOTNET_` variables).

- APIs return secrets as `"***"` (write-only). Log messages never destructure objects (no `{@…}`) and never include secrets, command lines or request bodies; request logs have the method, path, status and time, never query strings, headers or cookies. Console commands are audited with sensitive commands redacted (each `;`-separated command of a line is checked).
- Accepted limitation: a secret variable a manifest writes into a configuration file (the join password into CS2's `server.cfg`) can be read by whoever may read the server's files (`server.files.view`) or download its backups. The API keeps it write-only; the game needs it in the file.
- **Important operational consequence:** a PostgreSQL backup without the Data Protection key ring cannot decrypt secrets. `Backup-Pulsar.ps1` keeps the database dump, the key ring, its certificate, the HTTPS certificate and the settings together, and `Install-Pulsar.ps1 -RestoreFrom` restores them together ([backup guide](../guides/backup.md)).
- *Packaging (Phase 9):* the panel runs as the `PulsarPanel` service under its own virtual account (`NT SERVICE\PulsarPanel`), not as SYSTEM: it can write only its data folder (`%ProgramData%\Pulsar\Panel`: keys, key ring, logs, certificate) and read its settings, which hold the database and certificate passwords and are readable only by SYSTEM, Administrators and that account. The installer writes the settings (on a first install also the single-use setup token) in a private folder next to them and moves the file into place, so they are never readable by other users, not even for a moment. It creates the panel's PostgreSQL role with a random password, sent to `psql` on standard input (command lines are visible to every process), drops that role again if the database cannot be created, and never stores the superuser's. Its self-signed HTTPS certificate is made in memory (.NET's `CertificateRequest`: no certificate store or key container ever holds it or its key) and written only to the panel's private folder; it lists `localhost`, the machine's names, `127.0.0.1`, `::1` and the machine's private-use IPv4 addresses on network adapters that are up and have a default route (so not those of virtual switches that reach only its virtual machines and WSL), each address as an IP address (browsers match addresses only against those), and `-HostName`'s names and addresses (an IPv4 address only as four decimal numbers, a name never ending in a number, which browsers would read as an address; no zone, no mapped IPv4, no unspecified, broadcast or multicast address); public and IPv6 addresses are never added on their own. The install prints them and the certificate's SHA-256 (`PULSAR-CERTIFICATE`, which the setup's last page shows) for browsers on other PCs to be checked against. It is an end entity (Basic Constraints, critical, CA=false): trusted machine-wide (`LocalMachine\Root`, on the panel's PC in all-in-one mode and on nodes with `-TrustCertificate`), a certificate that could issue others would let whoever holds its key vouch for any site to that machine, so `-TrustCertificate` refuses one whose Basic Constraints say CA=true, and one that has none (Windows may take it for a certificate authority) unless `-TrustCertificateWithoutBasicConstraints` says it is the panel's own. A certificate trusted as a root vouches for every name it lists and every use it allows, so it must list the panel's host (`-PanelUrl`'s on a node, `localhost` in all-in-one mode) in its Subject Alternative Name and no names but the panel's (that host, `localhost`, the loopback addresses and single-label machine names on a node; on the panel's machine, the names and addresses its certificate was made for): another site's name, a wildcard, a single label that is a number (decimal or `0x`, which some resolvers read as an IPv4 address), another IP address (private-use ones included: a node's router or NAS; public, link-local, carrier NAT, IPv6 but `::1`) or a name of another kind is refused unless `-TrustCertificateWithOtherNames`, so a node that reaches the panel by its name meets the panel PC's private addresses there and passes the switch, or uses the address in `-PanelUrl`; one valid for longer than 5 years and a day (the installer's own: 5 years) is trusted with a warning; its Extended Key Usage must be server authentication alone (the installer's certificate says so; one without, which allows every use, or with more is refused unless `-TrustCertificateWithOtherUses`); a DNS name with characters other than letters, digits, `.`, `-`, `_` and a leading `*.` is refused outright, and so is a certificate with an extension twice. Accepting single-label names is a trade-off: the installer's certificate always lists the panel machine's own, and such a name can only be a machine on the local network, never an internet site (trusted on a node, whoever holds the panel's key could still pass for another machine of that network to it by its name; a node code's pin vouches for nothing on the node). Private-use IPv4 addresses (RFC 1918) are not accepted that way: a certificate listing the router's or a NAS's address would vouch for it to the node, the agent's S3 client to a LAN endpoint included. The file is read once, and the certificate checked is the one added to the store (`X509Store`, not the file again), with its subject, thumbprint and names printed, control characters shown as `?`; in all-in-one mode it must also have the SHA-256 of the certificate the install just made, since the panel's service account may change `tls\panel.cer` while the panel runs. A `-CertificatePath` PFX is read with an ephemeral key (no key container written) and disposed. The install warns, in its output and its log, about each address the certificate lists that a DHCP server gave the machine, recommending a reservation in the router. What the installer trusted is marked by its friendly name, and `-Uninstall` removes only certificates with that mark, in agent and all-in-one mode: the thumbprint a former install noted in the panel's data folder is only shown in a warning, since the panel's service account may change that folder (it could name any root, and replace `tls\panel.cer` to match). It opens the panel's ports in Windows Firewall for Domain and Private networks only (`-FirewallPublic` adds Public): the rule `Pulsar-Panel-HTTPS`, and `Pulsar-Panel-Agents` for an agents' port (`-AgentsPort`); `-Uninstall` removes both. It runs Windows' own programs (`icacls`, `sc`) by full path, and runs only from a folder that nobody but SYSTEM, Administrators and TrustedInstaller can change (T33). `Backup-Pulsar.ps1` writes only into a destination that nobody but SYSTEM, Administrators and TrustedInstaller may change, rename or replace, the folders above it included (T33), makes a new folder there with SYSTEM's and Administrators' permissions in the call that creates it, and checks the result before writing anything and again before it copies the keys: a drive that keeps no permissions (FAT, exFAT) is refused. `Install-Pulsar.ps1 -Uninstall` keeps the agent when `unenroll` fails, as the MSI does. **The enrollment token** reaches the agent through the environment (`PULSAR_ENROLLMENT_TOKEN`) when `Install-Pulsar.ps1` runs `enroll`, and `Install-Pulsar.ps1 -Mode Agent` itself reads it from that variable when `-Token` is left out (a command line shows in the process list). The agent MSI cannot: Windows Installer gives an executable custom action nothing but a command line, so its `enroll` action runs as `enroll --token "[TOKEN]" …` (the alternatives, a script action or an Environment-table entry, would put the token in a script or in the machine environment in the registry, which is worse). It is kept out of the installer's log (`MsiHiddenProperties`, target not logged) but is visible to administrators while `enroll` runs, as is `TOKEN=` on `msiexec`'s own command line: for MSI deployments use a reusable token that waits for approval and expires soon. Releases are built by `.github/workflows/release.yml` when it is run by hand (`scripts/release/Build-Release.ps1`, which anyone can run: it writes the ZIP, the MSI and one `.sha256` file for each, nothing else), with a provenance attestation for the ZIP and the MSI that only the workflow makes; the install guide tells users to check the SHA-256 (the attestation can be verified with `gh attestation verify`, optional).
- *Phase 18 (easy install):* `Install-Pulsar.ps1 -Unattended` (what the setup wizards run) asks nothing and takes its secrets (the administrator's password, an existing PostgreSQL's superuser password, a connection string, a PFX password, a node code, an enrollment token) from its elevated process's environment, or from a JSON secrets file that only SYSTEM and Administrators may own or open, in a folder only they may change (otherwise refused unread: whoever could replace it would choose the administrator's password), deleted once read; never from its command line. Each variable is removed from its own environment as it is read, so no installer, `psql` or agent it starts inherits one, and it removes `DOTNET_*`, `COREHOST_*`, `COMPlus_*` and `CORECLR_*` variables too (a startup hook or a profiler would load into the .NET programs it runs as administrator). It logs every run to `%ProgramData%\Pulsar\Setup\logs` (a folder it makes for SYSTEM and Administrators only, in the call that creates it, and refuses if anyone else could change it): not a transcript, which would record the command line, but what it prints, with every secret it knows of replaced: those it was given, those it makes (the PostgreSQL passwords, the HTTPS certificate's and the key ring's PFX passwords, the setup token) and those it reads (a `-RestoreFrom` backup's certificate and key ring passwords, the enrollment token and node code the all-in-one install gets from the panel). Its SecureStrings are built character by character, never with `ConvertTo-SecureString -AsPlainText`, whose command line PowerShell's module logging would record; Script Block Logging and transcription set by policy on the machine may still see secrets (docs/guides/install.md, "Secrets and PowerShell's logging"). The PostgreSQL it installs gets a random superuser password through an options file in its private folder (deleted when EDB's installer ends) and, once it runs, another random one sent to `psql` on standard input, kept nowhere; it is checked to have no roles but its own, then made to listen on `localhost` only, and its `pg_hba.conf` rules must all be local. The ZIP's programs are framework-dependent: the script makes sure the .NET runtimes they need are in `Program Files\dotnet`, which Windows would load them from (a machine-wide `DOTNET_ROOT` elsewhere, or a registered location elsewhere, is refused), and that nobody but SYSTEM, Administrators and TrustedInstaller can change the host resolver or any 10.0 runtime there (another account able to add a newer patch folder would run code as SYSTEM in the agent). The agent MSI stays self-contained. The downloads themselves are T38; the node code, T36.
- Accepted limitation: a secret passed on the command line (e.g. GSLT with `+sv_setsteamaccount`) is visible to the node's local administrators. If a game accepts it from a file, the manifest should prefer that.

### Audit

Append-only from the application, no secrets, with IP and actor. Failed sign-ins are recorded one by one up to `Audit:FailedLoginsPerMinute` (60) a minute; beyond that they are counted and the next recorded one says how many were left out (*Phase 9*). An entry names the user only when the name typed is an existing user's (a password typed in the wrong field is never kept). Refused agent sign-ins and rotations of an existing node are audited too (`node.authentication_failed`, a session token presented without its client certificate included; a rotation's new key refused, its proof or the current key's signature invalid or the key already registered, as `node.credential_rotation_started` with outcome failure), at most once per node, reason and client address every 15 minutes with a count of those left out (up to 8 addresses per node and reason; the others share one entry), so the node's own agent being refused never hides attempts from elsewhere (doc 03). Refused enrollments that name no node (an unknown token, a malformed request: anyone can send them) are recorded up to 20 a minute for the whole panel, the next one saying how many were left out; those of a real token (used, expired, a disabled node, a reusable one used up) are always recorded. Minimum actions: successful/failed login, logout, 2FA changes, user/role/access created-changed-deleted, node created/enrolled/revoked/rotated, server created/deleted, start/stop/restart/kill, console command (redacted), file edited/uploaded/deleted/renamed, backup created/restored/deleted/downloaded, scheduled task created/changed and its runs, template imported, settings changed.

### Supply chain and releases

- Central Package Management + NuGet lock files (restored in locked mode for releases), `npm ci` with a lockfile, and Dependabot (NuGet, npm and GitHub Actions, weekly). A CodeQL workflow (C# and TypeScript) exists but runs only while the repository is public (GitHub uploads code scanning results from private repositories only with Advanced Security); there is no dependency review workflow: dependency updates (Dependabot's pull requests) are reviewed and tested before they are merged.
- Releases built by the release workflow (`.github/workflows/release.yml`, run by hand: a tag does not start it; the releases that installed panels and agents update to are built and update-signed on the maintainer's PC, where the update key stays, and published with `scripts/release/Publish-GitHubRelease.ps1`, [releasing.md](../guides/releasing.md)) with provenance attestations (GitHub artifact attestations) and published SHA-256 checksums. It has two jobs: `build`, with read-only permissions and a checkout that keeps no credentials (`persist-credentials: false`), runs the repository's code (`Build-Release.ps1`, npm, dotnet) and uploads the artifacts; `publish`, the only job with `contents`, `id-token` and `attestations` write, runs no repository code: it attests the artifacts and drafts the release. Every action is pinned by commit SHA, not by a tag its owner could move. A build run by hand with `Build-Release.ps1` has the checksums only. Authenticode signing of the Windows binaries is built into `Build-Release.ps1` and off until the project has a certificate (SmartScreen will appreciate it; doc 09, "Code signing"): the release workflow does not sign, because its build job runs repository code and must hold no signing identity.
- No agent auto-update in v1: an auto-update channel is a remote code execution channel and needs its own design (package signatures verified by the agent).
- *Phase 18:* the installer downloads, at install time, the newest .NET 10 runtimes and the newest PostgreSQL 18 rather than shipping copies that age (T38). The ZIP's programs require at least the .NET patch the release was built with (`TargetLatestRuntimePatch`, recorded in the ZIP's `release.json`); Microsoft Update keeps the runtimes patched when updates for other Microsoft products are on.
- *Phase 18:* `Build-Release.ps1` also builds the setup wizards, `PulsarSetup-<version>.exe` and `PulsarAgentSetup-<version>.exe`, with Inno Setup 7 (`scripts/release/setup`) from the same staged release, each with its SHA-256 file (a compiler warning fails the build); the agent's setup goes into the panel's `downloads` folder, so the ZIP and `PulsarSetup.exe` carry the one the panel serves (T37). The release workflow installs Inno Setup 7.1.0 from its publisher's GitHub release, checked against a pinned SHA-256 and signed by Pyrsys B.V., builds with `-RequireSetups`, and attests and publishes both setups with their SHA-256 files (`gh attestation verify`). `Build-Release.ps1` takes ISCC from Program Files before a per-user install and checks, when it finds it and again before each compile (after `npm ci` has run), that `ISCC.exe` and every DLL next to it carry a valid Authenticode signature of Pyrsys B.V. Neither setup is code-signed yet (T39); `Build-Release.ps1 -SigningThumbprint` or `-TrustedSigningMetadata` signs them (and the MSI and the programs) once there is a certificate: signtool.exe must be validly signed by Microsoft and runs in place from a folder only administrators can change (the Inno Setup compiler, which runs it, too), every signature is verified and timestamped or the build fails (and nothing reaches the output folder), and nothing secret passes through the script (T42; doc 09, "Code signing").
- *Installer and update scripts (audit of 2026-10-21):* `-RestoreFrom` refuses a backup folder that others could change (`-TrustRestoreSource` for a drive without permissions), copies it once, file by file and never through a link, into a private folder, and works only on that copy: its `backup.json` (written by `Backup-Pulsar.ps1`: the Pulsar version, the dump's migrations, the SHA-256 of every file) must match it, and a backup from a newer Pulsar is refused. `-ConnectionString` databases migrated by a newer Pulsar are refused before anything changes. Programs are replaced by building the new folder beside the old and swapping by rename, never delete-then-copy; an update writes `in-progress.json` (flushed, in the administrators-only Updates folder) before it replaces anything, and the next `-Update` rolls an interrupted one back first; the copy of the last good version (`previous`) is not replaced by a broken install; the panel is stopped before the pre-update dump. `pg_dump`, `psql` and `pg_restore` get the connection string's `SSL Mode`/`Root Certificate`, and `Backup-Pulsar.ps1` refuses to copy the panel's folders through a link (the source and the copy are searched for links before and again after each copy, and one that appeared fails it; the narrow residual is a junction made and removed again inside the copy's own window, which cannot be seen afterwards). Installers that time out are ended with their process tree and the .NET installers get a private `TEMP`; a PostgreSQL `trust` rule stops the install; `-Uninstall` deletes the settings file first and fails if a folder stays. `Build-Release.ps1` refuses a dirty tree and records the commit in the signed manifest, and `Publish-GitHubRelease.ps1` publishes only at that commit; the update-key passphrase reaches only the signer's own process.

| T30 | An agent's session token is copied (a proxy that decrypts the traffic, a memory dump, a log) and used to act as that node: report false states, take file transfers, or register a key of the thief's own to take the node over for good | Opaque 15-minute tokens, kept by the panel only as hashes. | T31 | A certificate makes the side that checks it connect where it says, or holds its handshakes: the authority information access (issuer certificate, OCSP) and CRL addresses of any certificate presented on the agents' port, chosen by whoever connects, would be fetched while the TLS layer builds its chain (blind requests to internal hosts or a cloud metadata address, each handshake held about 15 seconds, enough of them starving the panel's threads); and the agent, as SYSTEM, would fetch those of whatever certificate answers at the panel's address (a forged DNS answer, an intercepted route) before refusing it: HTTP and LDAP requests of the attacker's choosing from every node | The agents' port builds a client certificate's chain only from what the handshake carried and the machine's stores: no downloads (on Windows no automatic root update either), no revocation check, and the result is ignored (the panel compares keys, never chains); Kestrel's own revocation check is off there (`AgentsEndpointKestrelTests`, `AgentsEndpointLimitsTests`). The machine's trust rather than a custom one with no roots: the same zero network access at a twenty-fifth of the CPU per handshake. The agents' port never serves HTTP/3 (an HTTP/3 setting is dropped, the operator's other protocols kept) and holds at most `Agents:MaxConnections` connections at once (1000 by default), closing one more on arrival, before its handshake. A connection is signed in once a request on it presents a valid agent session with the key of the connection's certificate (a challenge, a token or an enrollment never signs one in). Of the connections not signed in, the port holds at most `Agents:MaxPendingConnections` (a quarter of the cap), of which addresses no agent signed in from within a day take half at most; one IPv4 address or IPv6 /64 (the whole loopback counting as one) at most `Agents:MaxPendingConnectionsPerAddress` (20), and, for addresses no agent signed in from, one IPv4 /24 or IPv6 /48 at most `Agents:MaxPendingConnectionsPerNetwork` (60). A connection is closed after 5 seconds if it never completes its handshake, and 35 seconds from its arrival at the latest otherwise unless it signed in (30, then 5 more for a request in progress), so a source cannot take more than its address's and network's share. Each node keeps its latest four addresses as known, and past the bound the node with the most loses its oldest. Signed-in connections are at most `Agents:MaxConnectionsPerNode` (16, at least 2) per node, of which those signed in by a transfer (as routing matched the request, whatever the case of its path) take all but four, kept for its hub, the hub it replaces and its rotation; they last as long as the session they presented (a transfer in progress is finished first), and revoking the node's key, disabling or deleting the node closes them at once, and so does a superseded key. | T49 | A server plants a junction or link where the agent looks for a game's log by a pattern (Space Engineers' `instance/SpaceEngineersDedicated_*.log`, 1.0.12), to make the agent read or list a folder outside the server | The folder is opened level by level through the agent's link-safe file access (a junction on the way is refused) and listed through that handle; links in it are not taken as files, and the log is opened as any other (its final path checked). The listing gives the agent names and times only, never shown |
| T51 | A uMod plugin (1.0.14) is tampered with on the way, or uMod or a plugin's author serves a malicious one, to run code as the game server; or the panel's uMod lookups are turned into requests elsewhere | The panel asks only `umod.org` over HTTPS without redirects, with slugs checked by a pattern and answers capped; the panel offers only plugins it finds there for the addon the server has; the agent takes a file from uMod only at `https://umod.org/plugins/<its name>` (it checks the address itself), only into a folder of the game's manifest that takes `.cs` files, and only when its SHA-1 is the one uMod lists for that release (Oxide and Carbon compile and run whatever is in it). An update check asks uMod about 15 plugins at most (those read longest ago first; the others as read in the last 30 minutes), so a server with many cannot spend the panel's budget with uMod (20 requests a minute, under uMod's 30 per address). The SHA-1 comes from the same site over TLS: it keeps a file changed on the way, or replaced between lookup and download, out, not one uMod itself serves. A live change kills no process and touches only `.cs` files in those folders. Residual: plugins are third-party code that runs as the game server, with its account's rights only (doc 06), installed by whoever may install the server (`server.install`) |
| T52 | A Thunderstore package or BepInEx's pack (1.0.14) is tampered with on the way, or Thunderstore or a package's author serves a malicious one, to run code as the game server | Thunderstore publishes no checksum, so nothing can be checked against one: the panel asks only `thunderstore.io` over HTTPS without redirects and keeps only downloads at its own `/package/download/` address; the agent takes zips only from `thunderstore.io`, `ccdn.thunderstore.io` and `gcdn.thunderstore.io` over HTTPS with every redirect checked, checks the zip's end record before .NET reads its list of entries, unpacks only into BepInEx's folder (relative paths, nothing under `.pulsar`, at most 5,000 entries and 1 GiB), never over a file someone else put there, records the SHA-256 of what it took, and reads a package's record back keeping only paths in the package's own folders (the server's account can write `.pulsar`, not choose what the agent deletes). Residual: a package changed on Thunderstore's side is not detected (versions are immutable there, but nothing proves it); packages are third-party code that runs as the game server, with its account's rights only, installed by whoever may install the server |
| T55 | A server's Steam branch (1.0.14) is used to put options on SteamCMD's command line, to make a node install something else, or to undo a server's world | A branch is a name SteamCMD takes as one argument (`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`: never an option, never two arguments), checked by the panel and again by the agent before it accepts a spec; only a branch the node's last check listed, and without a password, can be chosen; the list is the server account's SteamCMD's, so it decides only what that server is offered. Changing it needs the rights to update the server and to back it up, the server stopped, and a backup is taken before the branch is installed (an older version may not open a newer world) |
| T54 | The Arma Reforger Workshop list editor (1.0.14) is used to make the panel read pages elsewhere, to load Bohemia's site, or to mislead users with a mod's name | Only users who create servers or change their startup settings may ask, within their own budget of lookups; the panel reads only `reforger.armaplatform.com` over HTTPS without redirects, at most 240 pages a minute for the whole panel and 60 for each user (so that one user's lookups of made-up ids leave the others room; several such users can still keep the editor busy for a minute, never a server from starting), 2 MB each, a mod's page once an hour, with ids checked as 16 hexadecimal digits (50 at most) and the query escaped; a mod's link is made from its id, never taken from the page; names lose control and direction characters and are cut. On the node, the ids go into `server.json` as JSON strings, and the record of the panel's ids lives in the server's own `.pulsar` folder: its account can change it, which changes only which of its own mods the panel takes out, and one it cannot read or write never stops a start |
| T56 | GoldSrc's RCON (1.0.15) shares the game's UDP port, open to players; HLDS writes every RCON command with the password to its console log, and to its logs folder once logging is on; another account could bind that port before the game, or while it runs | The password is Pulsar's (32 random characters) and HLDS bans an address after 5 wrong ones (`sv_rcon_maxfailures`, `sv_rcon_banpenalty`); it is masked in the console, and the console log and the logs folder (`privatePaths`) are kept from the file manager, SFTP, zips and backups by their names and, on Windows, by where any handle leads (an 8.3 name, a junction), nor can the folders holding them be moved, so reading the server's files does not give its console; before the session opens and before every command the agent checks in Windows' UDP table that every process bound to the port, on its address or on every address, runs as the server's account. Residual: plain text on the wire (loopback, or the address the game listens on); a plugin of the game itself can read the logs, as it can the game's memory; someone who may run console commands or change the server's files can send the logs elsewhere (`logsdir`), and already runs its console |
| T53 | The CurseForge list editor (1.0.14) is used to spend the administrator's CurseForge key, to make the panel send requests elsewhere, or to mislead users with a project's name | Only users who create servers or change their startup settings may ask, within their own budget of lookups and the panel-wide CurseForge budget (120 a minute); the panel asks only `api.curseforge.com` over HTTPS without redirects, with ids checked as numbers (100 at most) and a game id as a number, and keeps a project's page only on `www.curseforge.com`; names lose control and direction characters and are cut; the key never leaves the panel |
| T50 | Soulmask always opens a line console without a password on the loopback (its echo port; `-EchoPort=0` only makes the port a random one): any program on the machine, another server's plugin included, that finds it runs that server's commands (saves, shut down, backups of its database) | Pulsar does not use it: it talks to Soulmask's own RCON, on `127.0.0.1` with the 32-character password it makes, on an internal port, and checks that the listener runs as the server's account before sending it (T18). It cannot close the echo port, and Windows Firewall does not filter loopback traffic (residual, in the game's README: on a shared node, run Soulmask beside servers whose mods you trust). Pulsar has no console protocol without a password |

## Main project risks

| Risk | Prob. | Impact | Mitigation |
|---|---|---|---|
| R1. Console behavior of `cs2.exe`/`srcds.exe`/`steamcmd.exe` on Windows (stdout vs console API) | High | High | Phase 0 spike with ConPTY and pipes before designing the console UI on assumptions. Plan B: RCON for commands. |
| R2. Complexity of per-server accounts (profiles, window stations, LSA rights, Windows editions, antivirus) | Medium | High | Phase 0 spike; implementation isolated in `Agent.Windows`; integration tests on Windows Server and Windows 11. |
| R3. Restarting/updating the agent stops servers | Low (Phase 14) | Medium | Games run in host processes and keep running through restarts, updates and crashes of the agent (doc 06, "Server hosts"); a Windows shutdown stops them gracefully; with `Pulsar:ServerHosts` false the v1 behavior (graceful stop, auto-start) remains. |
| R4. SteamCMD fragility (output format, transient errors, bootstrap) | High | Medium | Tolerant parser, bounded retries, full logs visible. |
| R5. Friction installing PostgreSQL on Windows for home users | High | Medium | Step-by-step guide, connection check with clear messages, installer that detects a local PostgreSQL and (Phase 18) installs the newest PostgreSQL 18 when there is none, checked (T38). No SQLite fallback (explicit decision). |
| R6. Single panel instance (no HA) | Certain | Medium | Accepted for v1; scheduler already multi-instance safe (`FOR UPDATE SKIP LOCKED`); a SignalR backplane would be the required change. |
| R7. Loss of the Data Protection key ring or the panel key | Low | High | `Backup-Pulsar.ps1` backs them up with the database; the key ring is encrypted with a certificate, not machine DPAPI, so the backup restores on another machine (checked in Windows Sandbox and CI: backup, panel lost, restore, nodes reconnect). Losing the panel key still forces re-enrolling nodes. |
| R8. Panel/agent version drift | Medium | Medium | Protocol versioning, capabilities, N-1 support. |
| R9. Windows Defender slows 60 GB installs | High | Low | Document exclusions; **do not** add them automatically (the administrator's security decision). |
| R10. Scope creep | High | High | Phased roadmap with a "definition of done"; nothing outside the v1 flow until it is solid. |
| R11. Windows 10 out of support (since October 2025) | Certain | Low | Best-effort support for Windows 10 22H2; focus on Windows 11 and Server 2022/2025. |
